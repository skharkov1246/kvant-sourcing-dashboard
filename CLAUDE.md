## 🎯 Куда мы идём

**Инженерный портал ремонта и сервиса динамического оборудования.** Пользователь проходит
по цепочке целиком, не выходя из портала:

```
машина → узел → признак → дефект → ремонтное решение → запчасть → исполнитель
```

То есть: по шильдику опознать машину, по машине выйти на состав и узлы, по признаку
(вибрация, температура, падение напора, металл в масле) — на дефект, по дефекту — на
ремонтное решение и на перечень деталей к закупке, а по детали — на изготовителя и на
исполнителя работ. Динамическое оборудование — вращающиеся и возвратно-поступательные
машины: турбины, компрессоры, насосы, электрические машины, ГПУ, горно-шахтное.

Спрос (`lib_demand`) — не цель, а сырьё: из него достаются машины, узлы и запчасти,
которые реально спрашивают. Поэтому его точность, глубина и широта — условие всего
остального, а не самоценность.

Каждая задача измеряется вкладом в эту цепочку. Звено, где у нас пусто, — следующая работа.
Состояние по направлениям меряется, а не оценивается на глаз: см. `gpu/tools/coverage.py`
как образец счётчика заполняемости.

## Что это за проект
**Sourcing Analyzer (КВАНТ × Bitrix24)** — внутренний дашборд анализа работы сорсеров.
По живым данным Bitrix24 (смарт-процесс «Запросы поставщикам», entityTypeId 166) считает
метрики, генерирует HTML-дашборд и деплоит его на Cloudflare Pages. Вход — через Cloudflare Access (портал КВАНТ на `/`,
дашборд на `/dashboard`; проверка подписи входа — `access/cfaccess.js`, паролей на сайтах нет).

- Точка входа: `main.py` → тянет данные из Bitrix → модули метрик → рендер HTML.
- Модули расчёта: `metrics.py`, `company.py`, `advisor.py`, `reps.py`, `kam.py`,
  `contracts.py`, `insights.py`, `stages.py`, `period.py`.
- Вёрстка: **`templates/dashboard_core.html`** — один самодостаточный HTML-шаблон
  (встроенные CSS+JS, данные подставляются плейсхолдерами `__..._JSON__`). 9 вкладок.
- Сборка HTML: `dashboard.py`.

## 🔴 Критические правила (нарушение = сломанный прод)

1. **НИКОГДА не коммить и не пушь напрямую в `main`.** Только: своя ветка → Pull Request →
   мерж. Ветка: `git checkout -b feature/<короткое-описание>`.
   **Мерж PR агент выполняет сам** (распоряжение владельца, 06.08.2026: «мерджи всегда сам») —
   но ТОЛЬКО после зелёного гейта (`.github/workflows/gate.yml`).
2. **Каждый мерж в `main` = деплой на живой сайт.** Репозиторий публичный, минуты Actions
   не тарифицируются, но батчить изменения в один PR всё равно правильно: меньше
   пересборок — меньше окон, в которых прод может оказаться сломанным.
3. **Проверяй ДО пуша.** Обязательный минимум перед PR:
   ```bash
   python -m pytest -q                       # тесты ядра (~0,2 с)
   ruff check .                              # ошибки кода
   python scripts/build_catalog.py --check   # каталог данных актуален
   python scripts/build_index.py --check     # поисковый индекс актуален
   ```
   Правки вёрстки — дополнительно smoke-рендер и валидация:
   ```bash
   python -c "import sys,types;sys.modules.setdefault('dotenv',types.SimpleNamespace(load_dotenv=lambda *a,**k:None));sys.path.insert(0,'.');import dashboard;from tests import fixture;dashboard.write(fixture.build_metrics(),{'source':'rules','items':[]},'smoke/index.html')"
   python scripts/validate_dashboard.py smoke/index.html
   ```
   Правки метрик — `python main.py --dry-run` (нужен `BITRIX_WEBHOOK_URL` в `.env`).
   Ровно эти проверки выполняет гейт на каждый PR.
4. **Не редактируй бот-файлы.** `data/chat_snapshot.json`, `data/budget_snapshot.json`,
   `gt/data/bitrix_gt.json` пишут workflow. Если они попали в дифф PR — верни их
   состоянием базовой ветки: `git checkout origin/main -- <файл>`. Иначе мерж откатит
   свежие данные и дашборд соберётся на устаревших (так уже случалось трижды в августе).

   **`gt/public/` — исключение и откатывать его НЕЛЬЗЯ.** Бот переписывает там только
   `index.html`, `rfq.html` и `lot.html`; остальные одиннадцать страниц библиотеки ГТУ
   деплой не собирает, а копирует как есть — это исходник, а не артефакт. Буквальный
   откат уносит страницы с живого сайта: так PR #168 (01.09.2026) удалил `/gt/plugs`
   целиком. Правильно: менять шаблон в `gt/site/` и пересобирать страницу её сборщиком
   `gt/tools/build_<страница>.py`, коммитя обе стороны. Гейт проверяет, что страницы
   и правки инженеров не исчезают из PR.
5. **Репозиторий публичный.** Не добавляй персональные, коммерческие и клиентские
   данные. Что уже открыто и что с этим делать — `SECURITY.md`.
6. **Новый набор данных → в каталог и индекс.** Пояснение в `data/catalog_notes.json`,
   затем `python scripts/build_catalog.py` и `python scripts/build_index.py`.

   **Для НОВЫХ файлов каталог собирается ПОСЛЕ коммита, отдельным коммитом.**
   `build_catalog.py` пишет по каждому набору дату, автора и хеш последнего коммита;
   у незакоммиченного файла они пустые, после коммита разрешаются — и `--check` в гейте
   видит расхождение. Порядок: `git commit` → `build_catalog.py` → второй коммит.
   Для правок существующих файлов порядок значения не имеет.
   Эта ошибка уронила гейт трижды за одну сессию 11–12.09.2026.

## 📐 Правила работы с данными библиотеки

Написаны по разбору конкретных ошибок 11–12.09.2026. Каждая стоила прогона,
а две — искажённых цифр в отчёте владельцу. Соблюдай при любой работе с
`lib_demand`, `lib_files` и разбором вложений.

### Измерение

1. **Эталон не может быть производным от правила.** `lib_demand.segment_id`
   наследуется от файла целиком (`indexer.py` ставит сегмент по тексту всего
   файла, а текст строки — его подмножество). Поэтому «в файле нет ни одной
   классифицированной строки» — не измерение, а тавтология: файл либо весь
   классифицирован, либо весь нет. Эталон считай по самой строке
   (`classify(item_name)`), на клиенте.
2. **Цифра из журнала прогона — это подмножество, а не итог.** Журнал
   индексатора показывает только последний проход. «548 622 позиции» из журнала
   обернулись 1 451 732 в базе. Спрашивай базу: Actions → «Библиотека — сводка
   и переклассификация» → `stats`.
3. **Правило сначала меряют, потом применяют.** Холостой прогон обязателен, а
   запись обязана отменяться сама при непройденных гейтах. Калибровка на
   придуманных корпусах показывает верхнюю границу качества, а не рабочую:
   правило с нулём ложных на 97 придуманных строках дало на живых данных охват
   1,1 % вместо ожидаемых 30–50 %.
4. **Ослабление порога меряется таблицей, а не одним прогоном.** Сетку порогов
   считай за тот же проход: счётчики уже в памяти, пересчёт — миллисекунды.

### Изменение данных

5. **Пометка, а не удаление.** Ошибочную пометку снимают одной командой,
   удалённую строку не вернуть. Пометки живут в таблице-спутнике
   (`lib_row_junk`), а не колонкой `lib_demand`: у него `fts` объявлен
   `generated always … stored` плюс GIN, и `UPDATE` трёхсот тысяч строк раздувает
   таблицу на четверть и не укладывается в `statement_timeout` при откате.
6. **Каждая запись — с ключом прогона.** `run_id` в пометках и `segment_run`
   в наследовании сегмента: без них откат невозможен.
7. **Признак либо защищает строку, либо обвиняет её.** Цена ошибки разная:
   ошибочная защита стоит полноты (мусор виден числом), ошибочное обвинение
   стоит спроса. Защищай щедро, обвиняй только закрытым списком. Глагольные
   формы обвинять не могут: русское описательное наименование по ним
   неотличимо от пункта договора.

### SQL и миграции

8. **Подзапрос внутри `CASE` не должен ссылаться на обновляемую строку.**
   `exists (select … where d.x = f.y)` коррелирован и выполняется заново для
   каждой строки; `f.y in (select …)` считается один раз и хешируется. Первая
   форма подвесила миграцию на двенадцать минут. Проверяй планом: в фильтре
   подзапроса не должно быть ссылки на внешнюю таблицу.
9. **`statement_timeout` задают в строке подключения, а не через `SET`.**
   `SET` внутри транзакции откатывается вместе с ней, а дефолт пула Supabase —
   две минуты.
10. **Вспомогательный шаг миграции ставят после главного.** Досчёт, который
    можно не делать, не должен стоять перед `create view`, ради которого
    миграция и затевалась.
11. **Снятый прогон не освобождает базу.** Отмена job в Actions убивает клиента,
    но не backend: он доработает до своего `statement_timeout` и всё это время
    держит блокировки. Следующий прогон упрётся в `lock_timeout` — это не новая
    ошибка, а хвост прежней. Дождись.
12. **`lock_timeout` обязателен для `ALTER TABLE`.** Без него `ACCESS EXCLUSIVE`
    встаёт в очередь, и за ним выстраиваются все читатели.

### Разбор файлов

13. **Отказ выносится по файлу, а не по строке.** Построчный отказ стоит до
    сорока процентов позиций даже в хорошей спецификации: продолжение
    наименования на второй строке признаков позиции не несёт.
14. **Две вставки в одну таблицу правятся вместе.** В `flush()` пакетная и
    аварийная построчная: колонка, добавленная в одну, роняет вторую на каждой
    строке, ошибка молча уходит в счётчик пропущенных, а файл уже отмечен
    разобранным — буфер до 4000 позиций теряется. На это стоит тест.
15. **Статус файла не должен врать.** «Пусто» — строго для `chars == 0`.
    Тендерный PDF с текстовым слоем, но без позиций, — «текст без спецификации»,
    иначе оценка объёма распознавания сканов завышена.
16. **Сохраняй, почему получилось значение.** `segment_rule` (строка или файл),
    `parse_path` (таблица или текст), `class_rule`. Без этого следующая ошибка
    снова будет неизмеримой.

### Каталог данных

19. **Каталог собирают ДВУМЯ коммитами, если менялся `data/catalog_notes.json`.**
    `catalog.json` хранит метаданные о самом `catalog_notes.json` — в том числе
    хеш последнего коммита, который его менял. Сборка до коммита записывает
    предыдущий хеш, а гейт пересобирает каталог уже после коммита и получает
    другой — проверка падает, хотя локально всё сходилось. Порядок:
    ```bash
    git commit -m "..."                    # код и пояснения
    python scripts/build_catalog.py        # теперь хеш верный
    python scripts/build_index.py
    git commit -am "каталог и индекс"      # вторым коммитом
    ```
    Рекурсии нет: сам `catalog.json` в каталог не входит, поэтому второй коммит
    его не инвалидирует. Если `catalog_notes.json` не менялся — хватает одного
    коммита.

### Публичный репозиторий

17. **В журнал прогона — только агрегаты.** `count`, `count(distinct)`, названия
    сегментов и собственные константы кода. Ни наименований позиций, ни номеров
    сделок, ни почт. Частотный список слов допустим при жёстком фильтре:
    кириллица, от шести букв, порог от размера выборки.
18. **Корпуса в тестах придумывают, а не копируют из базы.**

## ⏩ Правило работы: стоять нельзя

Распоряжение владельца от 12.09.2026. Работы здесь на месяцы, и простой агента —
самая дорогая потеря: пока идёт одна разведка, параллельно могут идти пять.

**Перед каждой остановкой задай себе вопрос: что ещё можно запустить параллельно?**
Остановка допустима, только когда ответ честно «ничего»: всё запущено, результатов ещё нет,
и без них следующий шаг не определён.

Что это значит на практике:

1. **Долгое — в фон, сразу.** Разведки, сборки, ожидание CI. Запускай и продолжай работать,
   а не жди. Несколько разведок по разным направлениям идут одновременно без помех.
2. **Ожидание — не работа.** Ждёшь гейт или результат разведки — в это время делается
   следующее дело: соседнее направление, проверка гипотезы, чистка данных.
3. **Вернулся результат — сразу два действия.** Разобрать пришедшее И запустить следующее,
   а не по очереди.
4. **Отчёт — не финал.** Сдал работу владельцу — назови следующий шаг и начни его.
   Вопрос «что дальше» задаёшь себе сам, а не владельцу.
5. **Пустое звено цепочки важнее улучшения заполненного.** Сверяйся с разделом «Куда мы идём».

Исключения ровно два: правка ждёт решения владельца (деплой, секреты, расписание,
удаление данных) или следующий шаг физически определяется результатом идущей работы.
В обоих случаях скажи об этом прямо и назови, что запущено тем временем.

## Числа в выгрузках владельцу
Разбор выкладки по ЛУКОЙЛу (12.09.2026) показал три ошибки, которые стоили доверия
к документу. Не повторяй:
- **Не умножай цену одного лота на всё количество.** Цена с карточки действует ровно
  на тот остаток, который продавец подтвердил. Если `covers_qty` не `full` — строка
  в сумму закупки не идёт. Иначе из 187 тыс. USD получается 1,2 млн, и четверть его —
  штучные лоты eBay.
- **«Наличие» — не одно состояние.** Подтверждённый остаток на весь объём, наличие без
  покрытия количества, «отгрузим, если есть» и запись прошлой проверки, не
  перепроверенная сейчас, — четыре разные вещи. Складывать их в одно число нельзя.
- **Не выдавай родовой адрес за адрес по детали.** «Этот поставщик работает по такому
  классу» и «у него есть эта деталь» — разные утверждения. В заголовок идёт второе.

Общее правило: если число получено экстраполяцией, домножением или подстановкой
по классу — рядом с ним обязана стоять оговорка, а в заголовок оно не идёт.

## Выгрузки для владельца (PDF, XLSX)
Сводки и отчёты часто уходят владельцу файлом. Два правила, оплаченные сломанной выгрузкой:
- **PDF** — см. `docs/ПРАВИЛА-PDF.md`. Коротко: таблица течёт сама (`thead` как
  `table-header-group`, `page-break-inside: avoid` на строке), никакой фиксированной высоты
  страницы, никакой обрезки текста вида `x[:150]`. Собирать headless-Chromium, не LibreOffice
  (он тут таймаутит). Проверять `scripts/pdf_check.py`.
- **Не обрывай генерирующие скрипты через `| head`** — SIGPIPE убьёт процесс до записи
  выходного файла, и следующий шаг молча возьмёт старые данные. Пиши в файл, потом читай.

## Стиль работы
- Коммиты — понятными сообщениями на русском, по-смыслу (что и зачем).
- Правки вёрстки держи в стиле окружающего кода (плотный inline CSS/JS шаблона).
- После нетривиальной правки — прогони визуальную проверку в браузере перед PR.
- Если правка затрагивает деплой/планировщик/секреты — сначала спроси владельца.
