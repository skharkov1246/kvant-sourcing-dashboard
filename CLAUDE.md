## 🎯 Куда мы идём

**Инженерный портал ремонта и сервиса динамического оборудования.** Пользователь проходит
по цепочке целиком, не выходя из портала:

```
машина → узел → признак → дефект → ремонтное решение → запчасть → исполнитель
```

То есть: по шильдику опознать машину, по машине выйти на состав и узлы, по признаку
(вибрация, температура, падение напора, металл в масле) — на дефект, по дефекту — на
ремонтное решение и на перечень деталей к закупке, а по детали — на изготовителя и на
исполнителя работ. Динамическое оборудование — вращающиеся и возвратно-поступательные
машины: турбины, компрессоры, насосы, электрические машины, ГПУ, горно-шахтное.

Состояние звеньев библиотеки на 12.09.2026 (после #236 и #238; по ГШО и ГПУ —
свои счётчики, см. `data/chain_coverage.json`):

Спрос (`lib_demand`) — не цель, а сырьё: из него достаются машины, узлы и запчасти,
которые реально спрашивают. Поэтому его точность, глубина и широта — условие всего
остального, а не самоценность.

Каждая задача измеряется вкладом в эту цепочку. Звено, где у нас пусто, — следующая работа.
Состояние по направлениям меряется, а не оценивается на глаз: см. `gpu/tools/coverage.py`
как образец счётчика заполняемости.

## Что это за проект
**Sourcing Analyzer (КВАНТ × Bitrix24)** — внутренний дашборд анализа работы сорсеров.
По живым данным Bitrix24 (смарт-процесс «Запросы поставщикам», entityTypeId 166) считает
метрики, генерирует HTML-дашборд и деплоит его на Cloudflare Pages. Вход — через Cloudflare Access (портал КВАНТ на `/`,
дашборд на `/dashboard`; проверка подписи входа — `access/cfaccess.js`, паролей на сайтах нет).

- Точка входа: `main.py` → тянет данные из Bitrix → модули метрик → рендер HTML.
- Модули расчёта: `metrics.py`, `company.py`, `advisor.py`, `reps.py`, `kam.py`,
  `people.py`, `contracts.py`, `insights.py`, `stages.py`, `period.py`.
- `people.py` — роли коммерческого блока: состав из Bitrix (действующие против
  уволенных), загрузка людей (проработка / реализация), просрочка по дедлайнам
  заказов, застой, гигиена карточек, руководитель роли и его табель против норм
  (`HEAD_NORMS` — предложены, не утверждены владельцем). Отдельных вкладок «КАМы»
  и «Продукт-оунеры» в плашке НЕТ: начальник у ролей один, поэтому обе живут
  подменю внутри вкладки «Коммерсанты» (Сводка · КАМы · Продукт-оунеры · человек),
  а направления по клиентам и продуктовые линии (`kam.py`) — нижними секциями
  внутри соответствующей роли. Атрибуция сделки — полем «КАМ»
  (`UF_CRM_1740390857`) или «Product leader» (`UF_CRM_1779187425`), и лишь потом
  по ответственному: ответственный — исполнитель, а не коммерсант (из 1 812 сделок
  с заполненным полем «КАМ» он отличается от КАМа у 1 601).
  Там же `hygiene()` — двенадцать замеров ведения Bitrix (нормы в `HYGIENE`): отделы без
  руководителя, сделки на уволенных, заполняемость ролевых полей, доля карточек с суммой
  и с плановой датой, застой. Это состояние справочников, а не работа людей; блок стоит
  первым разделом сводки «Коммерсантов», строки со сделками открываются кликом, а сводная
  строка пишется в журнал прогона — по нему видно динамику день ко дню.
- `reps.py` («Коммерсанты») берёт оттуда же состав и атрибуцию: список фамилий в коде
  устаревал с каждым увольнением, а счёт по ответственному показывал другую нагрузку
  тех же людей, чем вкладки ролей. На вкладку попадает действующий коммерсант с
  `reps.MIN_DEALS`+ сделками года.
- Вёрстка: **`templates/dashboard_core.html`** — один самодостаточный HTML-шаблон
  (встроенные CSS+JS, данные подставляются плейсхолдерами `__..._JSON__`). 8 вкладок.
- Сборка HTML: `dashboard.py`.

## 🔴 Критические правила (нарушение = сломанный прод)

1. **НИКОГДА не коммить и не пушь напрямую в `main`.** Только: своя ветка → Pull Request →
   мерж. Ветка: `git checkout -b feature/<короткое-описание>`.
   **Мерж PR агент выполняет сам** (распоряжение владельца, 06.08.2026: «мерджи всегда сам») —
   но ТОЛЬКО после зелёного гейта (`.github/workflows/gate.yml`).
2. **Каждый мерж в `main` = деплой на живой сайт.** Репозиторий публичный, минуты Actions
   не тарифицируются, но батчить изменения в один PR всё равно правильно: меньше
   пересборок — меньше окон, в которых прод может оказаться сломанным.
3. **Проверяй ДО пуша.** Одной командой — все проверки гейта, какие выполнимы
   без сети:
   ```bash
   python scripts/preflight.py          # компиляция, ruff, тесты, каталог,
                                        # указатель, разметка узлов, smoke, бот-файлы
   python scripts/preflight.py --fix    # то же плюс пересборка каталога и указателя
   ```
   Он написан 18.09.2026 после трёх красных гейтов подряд по одной причине: отчёт
   начал читать два новых набора, у них изменилось поле «кем используется», а
   каталог не пересобрали — при зелёных тестах и чистом ruff. Отдельные команды,
   если нужно по одной:
   ```bash
   python -m pytest -q                       # тесты ядра (~0,2 с)
   ruff check .                              # ошибки кода
   python scripts/build_catalog.py --check   # каталог данных актуален
   python scripts/build_index.py --check     # поисковый индекс актуален
   ```
   Правки вёрстки — дополнительно smoke-рендер и валидация:
   ```bash
   python -c "import sys,types;sys.modules.setdefault('dotenv',types.SimpleNamespace(load_dotenv=lambda *a,**k:None));sys.path.insert(0,'.');import dashboard;from tests import fixture;dashboard.write(fixture.build_metrics(),{'source':'rules','items':[]},'smoke/index.html',people=fixture.build_people(),reps=fixture.build_reps(),advisor=fixture.build_advisor())"
   python scripts/validate_dashboard.py smoke/index.html
   ```
   Правки метрик — `python main.py --dry-run` (нужен `BITRIX_WEBHOOK_URL` в `.env`).
   Ровно эти проверки выполняет гейт на каждый PR.

   **Правка расчёта мержится только после зелёной «Живой сверки метрик»**
   (`.github/workflows/live-check.yml`, распоряжение владельца 23.09.2026: «прежде
   чем выкатывать в прод — 3–4 проверки, что данные не биты: это сразу уходит на
   20 сотрудников»). Сверка запускается сама на каждом PR, затрагивающем модули
   расчёта (`metrics.py`, `main.py`, `config.py`, `stages.py`, `period.py`,
   `bitrix_client.py`, `company.py`, `kam.py`, `people.py`, `contracts.py`,
   `reps.py`, `advisor.py`, `insights.py`), и при правке описания PR. Прод (основа
   PR) и правка считаются полным `main.py --no-llm` на одном снимке портала:
   сборка прода записывает ответы, сборка правки читает их же, поэтому любое
   расхождение — эффект правки. Сравниваются метрики и данные всех вкладок по
   восьми правилам (`scripts/live_check.py`). В описании PR обязательна заявка
   ожидаемого эффекта строками «ожидается:» — `без изменений`, сдвиг человека
   (`#N ±X`), группы (`сорсеры ±X`), графы (`отдел`, `вне отдела`, `всего`),
   звена цепочки (`звено <название> ±X`), карточек без исполнителя
   (`не определён ±X`), разрешение разделу меняться (`меняется people, reps`),
   поле, пустое по замыслу (`пустой weekly.inb`). Незаявленный сдвиг или
   изменение раздела, заявленный, но не случившийся сдвиг, перенос больше
   половины притока или оттока на одного человека, опустевшее поле, пропавшая
   вкладка, нераспознанная строка заявки — провал. Гейт проверяет синтетику и
   такие ошибки не видит: 23.09.2026 так в прод ушли пустой столбец КП (#396),
   неверный номер служебной записи (#397) и сотни запросов робота на одном
   человеке (#400).
4. **Не редактируй бот-файлы.** `data/chat_snapshot.json`, `data/budget_snapshot.json`,
   `gt/data/bitrix_gt.json` пишут workflow. Если они попали в дифф PR — верни их
   состоянием базовой ветки: `git checkout origin/main -- <файл>`. Иначе мерж откатит
   свежие данные и дашборд соберётся на устаревших (так уже случалось трижды в августе).

   **`gt/public/` — исключение и откатывать его НЕЛЬЗЯ.** Бот переписывает там только
   `index.html`, `rfq.html` и `lot.html`; остальные одиннадцать страниц библиотеки ГТУ
   деплой не собирает, а копирует как есть — это исходник, а не артефакт. Буквальный
   откат уносит страницы с живого сайта: так PR #168 (01.09.2026) удалил `/gt/plugs`
   целиком. Правильно: менять шаблон в `gt/site/` и пересобирать страницу её сборщиком
   `gt/tools/build_<страница>.py`, коммитя обе стороны. Гейт проверяет, что страницы
   и правки инженеров не исчезают из PR.
5. **Репозиторий публичный.** Не добавляй персональные, коммерческие и клиентские
   данные. Что уже открыто и что с этим делать — `SECURITY.md`.
6. **Новый набор данных → в каталог и индекс.** Пояснение в `data/catalog_notes.json`,
   затем `python scripts/build_catalog.py` и `python scripts/build_index.py`.

   **Для НОВЫХ файлов каталог собирается ПОСЛЕ коммита, отдельным коммитом.**
   `build_catalog.py` пишет по каждому набору дату, автора и хеш последнего коммита;
   у незакоммиченного файла они пустые, после коммита разрешаются — и `--check` в гейте
   видит расхождение. Порядок: `git commit` → `build_catalog.py` → второй коммит.
   Для правок существующих файлов порядок значения не имеет.
   Эта ошибка уронила гейт трижды за одну сессию 11–12.09.2026.

## 📐 Правила работы с данными библиотеки

Написаны по разбору конкретных ошибок 11–12.09.2026. Каждая стоила прогона,
а две — искажённых цифр в отчёте владельцу. Соблюдай при любой работе с
`lib_demand`, `lib_files` и разбором вложений.

### Измерение

0. **Сумма прячет потерю. Считай не только итог, но и «у скольких стало хуже».**
   Ослабление правила шапки 23.09.2026 дало по выборке 832 файлов строк цены
   3 474 → 5 716, плюс 64,5 %, — и при этом у 63 файлов цен стало МЕНЬШЕ. По
   итогу правка отличная, а для каждого из этих 63 — потерянный ответ поставщика,
   которого в файле больше не увидят. Поэтому запись переразбора теперь
   пропускает файл, у которого цен убыло (`APPLY_ONLY_BETTER`, включено по
   умолчанию), и печатает число пропущенных. Правило общее: у всякой правки
   «в среднем лучше» спрашивай, сколько единиц стало хуже, и защищай их поимённо.
0а. **Мерь тем, ради чего правка делается, а не тем, что легче посчитать.** Та же
   правка уронила число позиций на 28 % (49 644 → 35 543) — и это НЕ убыток: файл,
   переехавший из текстового пути в табличный, перестаёт делать позиции из прозы.
   Судить надо по цене. Число найденных шапок тоже не мерило: ослабление может
   принять за шапку строку тела, и охват вырастет при упавшем качестве.

1. **Эталон не может быть производным от правила.** `lib_demand.segment_id`
   наследуется от файла целиком (`indexer.py` ставит сегмент по тексту всего
   файла, а текст строки — его подмножество). Поэтому «в файле нет ни одной
   классифицированной строки» — не измерение, а тавтология: файл либо весь
   классифицирован, либо весь нет. Эталон считай по самой строке
   (`classify(item_name)`), на клиенте.
2. **Цифра из журнала прогона — это подмножество, а не итог.** Журнал
   индексатора показывает только последний проход. «548 622 позиции» из журнала
   обернулись 1 451 732 в базе. Спрашивай базу: Actions → «Библиотека — сводка
   и переклассификация» → `stats`.
3. **Правило сначала меряют, потом применяют.** Холостой прогон обязателен, а
   запись обязана отменяться сама при непройденных гейтах. Калибровка на
   придуманных корпусах показывает верхнюю границу качества, а не рабочую:
   правило с нулём ложных на 97 придуманных строках дало на живых данных охват
   1,1 % вместо ожидаемых 30–50 %.
4. **Ослабление порога меряется таблицей, а не одним прогоном.** Сетку порогов
   считай за тот же проход: счётчики уже в памяти, пересчёт — миллисекунды.

### Изменение данных

5. **Пометка, а не удаление.** Ошибочную пометку снимают одной командой,
   удалённую строку не вернуть. Пометки живут в таблице-спутнике
   (`lib_row_junk`), а не колонкой `lib_demand`: у него `fts` объявлен
   `generated always … stored` плюс GIN, и `UPDATE` трёхсот тысяч строк раздувает
   таблицу на четверть и не укладывается в `statement_timeout` при откате.
6. **Каждая запись — с ключом прогона.** `run_id` в пометках и `segment_run`
   в наследовании сегмента: без них откат невозможен.
7. **Признак либо защищает строку, либо обвиняет её.** Цена ошибки разная:
   ошибочная защита стоит полноты (мусор виден числом), ошибочное обвинение
   стоит спроса. Защищай щедро, обвиняй только закрытым списком. Глагольные
   формы обвинять не могут: русское описательное наименование по ним
   неотличимо от пункта договора.

### SQL и миграции

8. **Подзапрос внутри `CASE` не должен ссылаться на обновляемую строку.**
   `exists (select … where d.x = f.y)` коррелирован и выполняется заново для
   каждой строки; `f.y in (select …)` считается один раз и хешируется. Первая
   форма подвесила миграцию на двенадцать минут. Проверяй планом: в фильтре
   подзапроса не должно быть ссылки на внешнюю таблицу.
9. **`statement_timeout` задают в строке подключения, а не через `SET`.**
   `SET` внутри транзакции откатывается вместе с ней, а дефолт пула Supabase —
   две минуты.
10. **Вспомогательный шаг миграции ставят после главного.** Досчёт, который
    можно не делать, не должен стоять перед `create view`, ради которого
    миграция и затевалась.
11. **Снятый прогон не освобождает базу.** Отмена job в Actions убивает клиента,
    но не backend: он доработает до своего `statement_timeout` и всё это время
    держит блокировки. Следующий прогон упрётся в `lock_timeout` — это не новая
    ошибка, а хвост прежней. Дождись.
12. **`lock_timeout` обязателен для `ALTER TABLE`.** Без него `ACCESS EXCLUSIVE`
    встаёт в очередь, и за ним выстраиваются все читатели.

### Разбор файлов

13. **Отказ выносится по файлу, а не по строке.** Построчный отказ стоит до
    сорока процентов позиций даже в хорошей спецификации: продолжение
    наименования на второй строке признаков позиции не несёт.
14. **Две вставки в одну таблицу правятся вместе.** В `flush()` пакетная и
    аварийная построчная: колонка, добавленная в одну, роняет вторую на каждой
    строке, ошибка молча уходит в счётчик пропущенных, а файл уже отмечен
    разобранным — буфер до 4000 позиций теряется. На это стоит тест.
15. **Статус файла не должен врать.** «Пусто» — строго для `chars == 0`.
    Тендерный PDF с текстовым слоем, но без позиций, — «текст без спецификации»,
    иначе оценка объёма распознавания сканов завышена.
16. **Сохраняй, почему получилось значение.** `segment_rule` (строка или файл),
    `parse_path` (таблица или текст), `class_rule`. Без этого следующая ошибка
    снова будет неизмеримой.

### Каталог данных

19. **Каталог собирают ДВУМЯ коммитами, если менялся `data/catalog_notes.json`.**
    `catalog.json` хранит метаданные о самом `catalog_notes.json` — в том числе
    хеш последнего коммита, который его менял. Сборка до коммита записывает
    предыдущий хеш, а гейт пересобирает каталог уже после коммита и получает
    другой — проверка падает, хотя локально всё сходилось. Порядок:
    ```bash
    git commit -m "..."                    # код и пояснения
    python scripts/build_catalog.py        # теперь хеш верный
    python scripts/build_index.py
    git commit -am "каталог и индекс"      # вторым коммитом
    ```
    Рекурсии нет: сам `catalog.json` в каталог не входит, поэтому второй коммит
    его не инвалидирует. Если `catalog_notes.json` не менялся — хватает одного
    коммита.

    **Каталог устаревает и от правки КОДА, а не только пояснений.** `catalog.json`
    хранит по каждому набору список ссылающихся на него скриптов: любая строка
    с путём к файлу данных внутри `.py` попадает в `referenced_by`. Поэтому
    добавление в сборщик страницы карты соответствия «файл данных → страница
    портала» (`scripts/build_chain_page.py`, 12.09.2026) обновило семь наборов
    сразу — и гейт покраснел на `--check`, хотя ни один набор не менялся.
    Правило: `build_catalog.py --check` гоняют ПОСЛЕ последнего коммита, а не
    до него. Прогон до коммита проверяет предыдущее состояние дерева.

### Публичный репозиторий

17. **В журнал прогона — только агрегаты.** `count`, `count(distinct)`, названия
    сегментов и собственные константы кода. Ни наименований позиций, ни номеров
    сделок, ни почт. Частотный список слов допустим при жёстком фильтре:
    кириллица, от шести букв, порог от размера выборки.
18. **Корпуса в тестах придумывают, а не копируют из базы.**

### Переносимость схем

20. **Роли Supabase в схеме называют только через проверку наличия.** `anon`,
    `authenticated` и `service_role` заводит платформа. На чистом PostgreSQL их
    нет, и `revoke all … from anon` роняет ВЕСЬ файл: `role "anon" does not
    exist`. Против прода это не проявляется никогда — там роли есть, — зато
    применить схему где-либо ещё нельзя, то есть проверить её негде, кроме прода.
    20.09.2026 так упал прогон сведения поставщиков, и та же мина лежала в обеих
    ступенях ужесточения ЗИП и в `schema_junk.sql`; трижды за сессию роли
    создавались руками ради локального прогона, и трижды это скрывало причину.
    Образец — `sup_роли_которые_есть` в `library/supabase/suppliers_schema.sql`.
    Роли при этом НЕ создают: это дело платформы, а не миграции.
21а. **Локальная база обязана быть в локали UTF-8, иначе кириллица не
    складывается по регистру.** `lower()` работает средствами локали: в базе с
    локалью C `lower('ШАЙБА')` возвращает «ШАЙБА», заглавные буквы вылетают
    фильтром посторонних знаков внутри `lib_pn_key`, и ключ выходит «12» вместо
    «шайба12е». Ключи артикулов на такой базе считаются ИНАЧЕ, чем на живой:
    22.09.2026 проверка замера кодов на ней насчитала пять кодов вместо четырёх,
    потому что «ВЫДУМ-101» и «выдум 101» дали разные ключи, — и это выглядело
    правдоподобно. Поднимай базу так:
    ```bash
    createdb -T template0 --locale=C.UTF-8 --encoding=UTF8 library_sql_test
    ```
    В гейте база такая уже. `tests/test_library_pnkey_sql.py` проверяет локаль
    первым делом и краснеет с названной причиной, а не строкой «assert '12' ==
    'шайба12е'».

21. **`create table if not exists` не меняет существующую таблицу.** Новый вид в
    `check (… in (…))` надо добавлять отдельным `alter … drop constraint /
    add constraint`, иначе на свежей базе всё зелено, а на живой вставка падает.

## ⏩ Правило работы: стоять нельзя

Распоряжение владельца от 12.09.2026. Работы здесь на месяцы, и простой агента —
самая дорогая потеря: пока идёт одна разведка, параллельно могут идти пять.

**Перед каждой остановкой задай себе вопрос: что ещё можно запустить параллельно?**
Остановка допустима, только когда ответ честно «ничего»: всё запущено, результатов ещё нет,
и без них следующий шаг не определён.

Что это значит на практике:

1. **Долгое — в фон, сразу.** Разведки, сборки, ожидание CI. Запускай и продолжай работать,
   а не жди. Несколько разведок по разным направлениям идут одновременно без помех.
2. **Ожидание — не работа.** Ждёшь гейт или результат разведки — в это время делается
   следующее дело: соседнее направление, проверка гипотезы, чистка данных.
3. **Вернулся результат — сразу два действия.** Разобрать пришедшее И запустить следующее,
   а не по очереди.
4. **Отчёт — не финал.** Сдал работу владельцу — назови следующий шаг и начни его.
   Вопрос «что дальше» задаёшь себе сам, а не владельцу.
5. **Пустое звено цепочки важнее улучшения заполненного.** Сверяйся с разделом «Куда мы идём».

Исключения ровно два: правка ждёт решения владельца (деплой, секреты, расписание,
удаление данных) или следующий шаг физически определяется результатом идущей работы.
В обоих случаях скажи об этом прямо и назови, что запущено тем временем.

## 🔟 Правило дробления (распоряжение владельца, 22.09.2026)

**«Никогда не бери сразу так много. Всегда дели минимум на 10, а если большие —
то и на 50 частей».**

Сказано после того, как полный переразбор 5 640 предложений пошёл ОДНОЙ частью и
упал через сорок минут на ошибке записи, потеряв всё несделанное время. Части
здесь не про скорость, а про цену ошибки: упавшая часть уносит свою долю, а не
весь прогон, и повторять надо её одну.

Что это значит на деле:

- прогон, обходящий портал или базу, обязан принимать число частей ВХОДОМ, а не
  держать его в файле. `library-index.yml`: вход `shards`, варианты 10/12/25/50;
- обход, который нельзя поделить, — не оправдание, а задача. Обход карточек
  запросов читает страницы подряд по ключу, и до 22.09.2026 делился только
  «работает часть 1, остальные выходят». Теперь часть берёт свой ДИАПАЗОН
  идентификаторов (`indexer.диапазон_части`), и один полный обход раскладывается
  на части, а не повторяется каждой;
- разбиение ровно одно. Два подряд — обход по частям и отбор по хешу файла —
  выбрасывают то, что попало в часть 3 по первому признаку и в часть 7 по
  второму: такой файл не берёт никто;
- прежде чем делить, посмотри, сколько всего. Пятьсот файлов — десять частей,
  пять тысяч — пятьдесят.

## 🚦 Битрикс не перегружать (распоряжение владельца, 24.09.2026)

Сказано после того, как холостой переразбор сделок (50 частей по 12 разом) умер
в 44 частях из 50 с HTTP 429 на `crm.deal.list`. «Можно подождать лишние 3–4
часа» — падение дороже медленного прогона.

**Лимитов два, оба на вебхук, то есть общие для ВСЕХ наших прогонов**
(https://apidocs.bitrix24.ru/limits.html):
- частота — «дырявое ведро»: +1 за запрос, −2 в секунду, порог 50 → **503
  `QUERY_LIMIT_EXCEEDED`**. Устойчиво — не больше 2 запросов в секунду на портал;
- время метода — не больше 420 с работы одного метода за скользящие 10 минут →
  **429 `OPERATION_TIME_LIMIT`**, метод заблокирован до `time.operating_reset_at`
  (до 10 минут). 24.09.2026 упали именно на нём: 50 частей читали список
  смещением, а смещение считает `total` на каждой странице.

Как держать:
1. **Одна точка правды — `bitrix_client.интервал_портала()`**: пауза процесса =
   `BITRIX_PARALLEL / BITRIX_RPS`. `BITRIX_RPS` — на ВЕСЬ портал (умолчание 1,5;
   тяжёлым прогонам 1,2 — остаток деплою). `BITRIX_PARALLEL` = min(частей,
   max-parallel) — прогон частями обязан его передать. Своих `min_interval`,
   `sleep(0.3)` и циклов повторов против лимита в коде не заводить.
2. **Скачивание по `urlMachine` — тоже REST** (`crm.controller.item.getFile`):
   идёт через `BitrixClient.before_request()` и считается в бюджете.
3. **На лимите ждать, а не падать.** 429/503 пережидаются бюджетом
   `BITRIX_WAIT_BUDGET` (30 мин на вызов), пауза 5 → 180 с, у 429 — до
   `operating_reset_at`. С 60 % времени метода клиент тормозит сам. Попытками
   меряются только сеть и 5xx.
4. **Полный обход в каждой части запрещён.** Часть читает свой диапазон
   (`indexer.диапазон_части`) по ключу `>ID`/`>id` с `start=-1` (без подсчёта
   `total`). Смещение (`start=50…`) — только для справочников в пару страниц.
5. **Перед постановкой прогона посчитай запросы**: записей/50 на обход плюс по
   одному на файл, раздели на `BITRIX_RPS` — это время прогона. Сверь с
   расписанием: деплой дашборда 00:07/06:07/12:07/18:07 UTC (~1 750 запросов,
   ~20 мин), скан чатов 21:00; cron GitHub опаздывает до 5 ч. Проверь Actions на
   идущие прогоны и помни: в группе `bitrix-portal` ожидающий ОДИН.
6. **Журнал прогона кончается строкой «портал: запросов … · отказов (503) … ·
   (429) … · ждали … с»** — у упавшего тоже. Отказы есть — бюджет велик.
7. **Ежедневное пополнение — только инкрементом** (`library-daily.yml`,
   `library/increment.py`): сделки и карточки, изменённые после прошлого
   успешного прохода, плюс новые по номеру; отметка — в `lib_metric_runs`
   последним шагом. Десятки запросов, а не тысячи; сплошной обход — руками и
   по делу.
8. **Лиды — не больше пятой части ёмкости портала** (распоряжение владельца
   24.09.2026). Всё, что идёт «на пятую часть», — `BITRIX_RPS=0.3`, вне очереди
   `bitrix-portal`, в своей группе `bitrix-fifth` и по одному: вместе с самым
   тяжёлым прогоном общей очереди (1,5/с) выходит 1,8/с из 2. Первый такой
   прогон — письма лидов (`library-mail.yml`, группа `mail-lead`: 0,3 прибито
   в шаге, вход не действует). Остальные источники, письма сделок и
   поставщиков тоже, — в общей очереди.

## Числа в выгрузках владельцу
Разбор выкладки по ЛУКОЙЛу (12.09.2026) показал три ошибки, которые стоили доверия
к документу. Не повторяй:
- **Не умножай цену одного лота на всё количество.** Цена с карточки действует ровно
  на тот остаток, который продавец подтвердил. Если `covers_qty` не `full` — строка
  в сумму закупки не идёт. Иначе из 187 тыс. USD получается 1,2 млн, и четверть его —
  штучные лоты eBay.
- **«Наличие» — не одно состояние.** Подтверждённый остаток на весь объём, наличие без
  покрытия количества, «отгрузим, если есть» и запись прошлой проверки, не
  перепроверенная сейчас, — четыре разные вещи. Складывать их в одно число нельзя.
- **Не выдавай родовой адрес за адрес по детали.** «Этот поставщик работает по такому
  классу» и «у него есть эта деталь» — разные утверждения. В заголовок идёт второе.

- **Не строй прогноз на `CLOSEDATE`.** Поле проставляется автоматически: замер 17.09.2026 —
  заполнено у всех 2 695 открытых сделок, у 2 624 прошедшей датой, будущая дата лишь у 71
  (2,6 %). Раскладка по нему строила прогноз на эти два процента, а 98 % пайплайна уходило
  в строку «без плановой даты» — график был почти пуст и молчал об этом почти год.
  Месяц закрытия считается двумя источниками (`advisor.py`): дата из карточки, если она в
  будущем, иначе оценка от медианного срока «создана → вошла в реализацию» по воронке —
  и в интерфейсе видно, сколько карточек попало планом, а сколько оценкой.
- **Вкладка без данных в smoke-рендере — это непроверенная вкладка.** Советник уходил в
  проверку с `advisor=None`, поэтому вырожденный график никто не ловил. Новая вкладка обязана
  получить корпус в `tests/fixture.py` и попасть в smoke-команду гейта.

Общее правило: если число получено экстраполяцией, домножением или подстановкой
по классу — рядом с ним обязана стоять оговорка, а в заголовок оно не идёт.

## Выгрузки для владельца (PDF, XLSX)
Сводки и отчёты часто уходят владельцу файлом. Два правила, оплаченные сломанной выгрузкой:
- **PDF** — см. `docs/ПРАВИЛА-PDF.md`. Коротко: таблица течёт сама (`thead` как
  `table-header-group`, `page-break-inside: avoid` на строке), никакой фиксированной высоты
  страницы, никакой обрезки текста вида `x[:150]`. Собирать headless-Chromium. Проверять
  `scripts/pdf_check.py`.
- **LibreOffice «таймаутил» не от медлительности — это дефект вызова.** Разобрано
  23.09.2026: `soffice` — shell-скрипт, он запускает oosplash, а тот `soffice.bin`.
  `subprocess.run(timeout=…)` убивает только верхний процесс, `soffice.bin` остаётся
  сиротой, держит профиль и канал в /tmp, и следующий вызов с тем же профилем ждёт
  его — отсюда серии 119 → 499 → 899 с в `ove/tools/build_rfq_pdf.py`. Ещё две
  ловушки: код возврата 0 бывает и при «source file could not be loaded» (успех —
  только по выходному файлу), а в локали POSIX выгрузка листов с кириллическими
  именами в CSV молча не пишет ничего. Правильный вызов — в
  `library/convert_office.py`: свой профиль на вызов, своя группа процессов и
  `killpg` по таймауту, `LC_ALL=C.UTF-8`. Сама конвертация быстрая: около 1 с на
  файл, 0,43 с в четыре потока.
- **Не обрывай генерирующие скрипты через `| head`** — SIGPIPE убьёт процесс до записи
  выходного файла, и следующий шаг молча возьмёт старые данные. Пиши в файл, потом читай.

## Стиль работы
- **Сравнивай с эталоном, записанным в тех же условиях.** Холостой переразбор
  сравнивает новый разбор с тем, что лежит в базе. Цены в базе 23.09.2026 записал
  переразбор с ослабленной шапкой (header_relax), а холостые прогоны каскада шли
  без неё — и показали «потерю» даже у таблиц PDF, чей путь не менялся вовсе.
  Прежде чем читать разницу, выясни флаги прогона, писавшего эталон, и повтори
  их; точнее всего — сравнение A/B на одних байтах в одном проходе.
- **Идентификаторы бери из файла или ответа, а не вписывай.** 23.09.2026 я
  запустил сводку пятидесяти журналов с номерами, набранными по памяти, а
  настоящие лежали в файле рядом; заметил до результата. Номер прогона, задания,
  файла — только копированием из вывода инструмента.
- **База в режиме только чтения не даёт и временных таблиц, а кончившийся диск —
  и временных файлов.** «create temp table» в read-only транзакции запрещён
  (так падает codes_with_prices.py), а большая группировка, не влезшая в
  work_mem, пишет временный файл и падает с «No space left on device». Замер на
  такой базе — только выборки, ключи по хешу на части, без параллельных процессов
  (scripts/codes_dynamics.py).
- **Новый читатель проверяется сравнением с прежним на ОДНОМ корпусе форматов,
  а не только своими тестами.** 23.09.2026 у всех десяти читателей тесты были
  зелёными (2 400 проверок), а сравнение «прежний путь против каскада» на одном
  придуманном КП в двенадцати форматах (`scripts/cascade_corpus.py`) за минуту
  нашло три дефекта: раскладка pdftotext ломала сборку таблицы PDF (цена из
  колонки «№», количество 1 381 762 — и ворота шапки это пропустили); RTF от
  LibreOffice читался «Н?а?с?о?с?»; починка кодировки превращала такой текст в
  псевдографику и засчитывала себе улучшение. Свои тесты проверяют то, что автор
  знал; общий корпус — то, чего не знал никто. Больше цен — не значит лучше:
  проверяй правдоподобие значений, а не только их число.
- **Не пиши в команде буквальный «обратный слэш + u + четыре цифры».** Слой
  передачи команды развернул `\u1053` в символ ещё до bash, и в тест легли
  байты не-ASCII вместо RTF-разметки. Такие последовательности собирай кодом:
  `b"\\" + b"u%d" % ord(ч)`.
- **Читай ВЫЗОВ, а не только объявление.** 23.09.2026 я объявил причиной 69 %
  таймаутов распознавания вход прогона `workers: 12`, посмотрев вход и `env`
  задания. Строку запуска не посмотрел, а в ней стояло `WORKERS=4 python
  library/ocr.py`: четвёрка прибита в шаге и перекрывает окружение. Прогон шёл на
  четырёх потоках всегда, диагноз был неверен, и повторный прогон, который должен
  был его подтвердить, его опроверг. Обратная сторона правила «разбор исходника
  читает код, а не комментарии»: объявление — ещё не то, что исполняется. И
  зеркальное следствие для своего кода: шаг прогона не имеет права молча
  подменять значение входа, иначе журнал врёт о том, на чём прогон шёл.
- **Внешние потоки — не все потоки.** tesseract собран с OpenMP и берёт все ядра
  сам, сколько бы его копий ни запустили. Четыре процесса по четыре потока на
  четырёх ядрах дают шестнадцать потоков, крутящихся на барьерах: замер 23.09.2026
  — один процесс 1,2 с, четыре тех же 400,1 с (ни один не дочитал), четыре с
  `OMP_THREAD_LIMIT=1` снова 1,2 с. Прежде чем множить процессы, посмотри в
  `/proc/<pid>/task`, сколько потоков у одного. Держи произведение «процессов ×
  потоков внутри» около числа ядер.
- **В общей группе `concurrency` ждёт ОДИН прогон.** Следующая постановка в ту же
  группу ОТМЕНЯЕТ предыдущую ожидающую, а не встаёт за ней, — `cancel-in-progress:
  false` защищает только идущий прогон. 23.09.2026 разведка, поставленная в 08:10,
  была снята постановкой распознавания в 08:16, и я полчаса считал её ждущей.
  Ставить второе задание в группу `bitrix-portal`, пока первое ждёт, нельзя;
  сначала дождись, чтобы предыдущее пошло.
- **Код возврата конвейера — это код ПОСЛЕДНЕЙ команды.** `python scripts/preflight.py
  | tail -3 && git commit` коммитит при проваленной проверке: `tail` завершился
  успешно, строка «НЕ ПРОЙДЕНО: 1 из 11» ушла в вывод, и `&&` пропустил дальше.
  23.09.2026 так ушёл пуш с упавшей проверкой. Пиши вывод в файл и проверяй код
  самой проверки: `preflight.py > /tmp/pf.txt 2>&1; echo $?; tail /tmp/pf.txt` —
  или `set -o pipefail` в начале.
- **Правка, меняющая основание, ломает то, что на нём стоит, и это не видно до
  запуска.** За один день 23.09.2026 так сломались четыре вещи: три проверки
  цеплялись за имя прежней функции или прибитое число подстановок и падали от
  перестановки кода при сохранном поведении, а замер — инструмент ЧТЕНИЯ — упал
  на запросе к колонке, которой в базе ещё нет (миграция не применена). Правило:
  проверка держится за поведение, а не за спелинг; инструмент чтения спрашивает
  у базы, какие колонки есть, прежде чем их запрашивать.
- **Имена переменных в bash — только латиницей.** Кириллическое имя bash за имя
  переменной не считает и пытается выполнить строку как команду: прогон падает с
  «файл=...: No such file or directory», код 127. За сессию 20.09.2026 я наступил
  на это трижды — в workflow и дважды в проверочных командах. Комментарии и
  сообщения на русском, имена латиницей.
- **Проверка мутацией требует чистки `__pycache__`, если мутация не меняет
  длину файла.** Python сверяет исходник с байт-кодом по паре «время правки и
  размер». Замена `10 ** 14` на `10 ** 18` размер не меняет, и на быстрых
  правках подряд поднимается старый `.pyc`: проверка говорит, что код верен,
  когда он сломан, и что мутация выжила, когда она снята. Поймано 22.09.2026 на
  пределе правдоподобия цены. Между мутациями:
  `find . -name __pycache__ -type d -not -path "./.git/*" -exec rm -rf {} +`
- - **Разбор исходника читает код, а не комментарии.** Регулярка по файлу обязана
  сначала снять `//` и `--`: пояснение вида «было `X || КЛЮЧ`» она найдёт раньше
  настоящей строки и отчитается о том, чего в коде уже нет (поймано 20.09.2026 на
  `scripts/zip_rls_readiness.py`).
- Коммиты — понятными сообщениями на русском, по-смыслу (что и зачем).
- Правки вёрстки держи в стиле окружающего кода (плотный inline CSS/JS шаблона).
- После нетривиальной правки — прогони визуальную проверку в браузере перед PR.
- Если правка затрагивает деплой/планировщик/секреты — сначала спроси владельца.

## Стиль всех документов для заказчиков и владельца (ТКП, КП, письма, отчёты)
Распоряжение владельца, 04.09.2026: строгий текст в Times New Roman, «стиль ведомости, но на
белой бумаге». Чёрный текст на белом, тонкие чёрные линии таблиц, обычное начертание —
без цветных плашек, тегов-статусов, жирных выделений в строках, маркированных списков с
«жирными» лид-инами и прочих признаков сгенерированного текста. В ТКП заказчик должен
прямо видеть, что предлагается оригинал либо изделие, максимально приближенное к оригиналу
(первой строкой — оригинал, далее — рекомендуемый вариант). Правила и каркас —
навык `tkp-vedomost` (см. ниже); печать в PDF — `pdf-analysis/scripts/html2pdf.sh`.
