## 🎯 Куда мы идём

**Портал управления поставщиками**: заявка → спецификация → подбор адресатов → запрос →
котировка → выбор → заказ → поставка. Опора подбора — инженерная библиотека
динамического оборудования, пройденная цепочкой целиком:

```
машина → узел → признак → дефект → ремонтное решение → запчасть → исполнитель
```

Каждая задача измеряется вкладом в эту цепочку. Звено, где у нас пусто, — следующая
работа. Состояние меряется счётчиком (`data/chain_coverage.json`, `gpu/tools/coverage.py`),
а не на глаз. Спрос (`lib_demand`) — сырьё, а не цель.

## Что это за проект

Sourcing Analyzer (КВАНТ × Bitrix24): по живым данным Bitrix24 (смарт-процесс «Запросы
поставщикам», entityTypeId 166) считает метрики и деплоит портал на Cloudflare Pages за
Cloudflare Access. `main.py` → модули расчёта (`metrics.py`, `company.py`, `advisor.py`,
`reps.py`, `kam.py`, `people.py`, `contracts.py`, `insights.py`, `stages.py`, `period.py`)
→ `dashboard.py` → `templates/dashboard_core.html` (8 вкладок). Подробности модулей —
LESSONS, «Что это за проект».

## 🔴 Критические правила (нарушение = сломанный прод)

1. **Не коммить и не пушь в `main`.** Своя ветка → PR → мерж. Мерж агент делает сам
   (распоряжение 06.08.2026), только после зелёного `.github/workflows/gate.yml`.
2. **Каждый мерж в `main` = деплой на живой сайт.** Батчь правки.
3. **Проверяй ДО пуша:** `python scripts/preflight.py` (или `--fix`). Вывод — в файл,
   код возврата — самой проверки (`preflight.py > /tmp/pf.txt 2>&1; echo $?`).
   Правка расчёта мержится только после зелёной «Живой сверки метрик»
   (`live-check.yml`); в описании PR — строки «ожидается:». Правила сверки — LESSONS.
4. **Не редактируй бот-файлы** `data/chat_snapshot.json`, `data/budget_snapshot.json`,
   `gt/data/bitrix_gt.json`: попали в дифф — `git checkout origin/main -- <файл>`.
   `gt/public/` — исходник, откатывать нельзя: правь `gt/site/` и пересобирай.
5. **Репозиторий публичный.** Ни персональных, ни коммерческих, ни клиентских данных:
   цены, поставщики поимённо, контакты, условия — только в Notion. `SECURITY.md`.
6. **Новый набор данных → каталог и индекс** (`data/catalog_notes.json`,
   `build_catalog.py`, `build_index.py`). Для новых файлов и правок `catalog_notes.json`
   каталог собирается ПОСЛЕ коммита, вторым коммитом; `--check` — после последнего коммита.

## 🔒 Агентские сессии: запрещено (распоряжение владельца 30.09.2026)

- держать у агента закрытые ключи (сервисные ключи баз, приватные ключи, токены
  с правом записи вне секретов прогона);
- заводить, скачивать или хранить зашифрованные выгрузки базы;
- расшифровывать что-либо у агента — ни выгрузки, ни секреты.

Замеры по закрытым данным — только внутри прогона Actions, наружу — только агрегаты
(`count`, доли, названия сегментов). Нужны строки — прогон пишет их в закрытое
хранилище (Supabase, KV, Notion), а не в журнал и не в сессию агента.

## ⏩ Как работаем

- **Стоять нельзя** (12.09.2026). Перед каждой остановкой спроси:
  что ещё можно запустить параллельно? Долгое — в фон, ожидание — не работа, отчёт — не финал.
- **Дробление** (22.09.2026): прогон делится минимум на 10 частей, большой — на 50;
  число частей — вход прогона; разбиение ровно одно.
- **Битрикс не перегружать** (24.09.2026): ≤ 2 запросов/с на портал, одна точка правды —
  `bitrix_client.интервал_портала()`; на 429/503 ждать, а не падать; полный обход в
  каждой части запрещён; лиды — не больше пятой части ёмкости.
- **Качество прежде скорости** (26.09.2026): каждая правка данных проверяется минимум
  дважды разными способами; расхождение — остановка и разбор. Слияние вкладок — после
  сведения правил карточки, цены и роли.
- **Сумма прячет потерю:** у всякой правки «в среднем лучше» считай, у скольких стало хуже.
- **Правило сначала меряют, потом применяют:** холостой прогон, запись сама отменяется
  при непройденных гейтах; пометка, а не удаление; каждая запись — с ключом прогона.
- Деплой, планировщик, секреты, удаление данных — сначала спросить владельца.
