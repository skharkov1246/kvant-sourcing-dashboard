# Инженерная библиотека

На портале выберите «Библиотека оборудования и знаний». Внутри: тип оборудования,
узлы и детали, поставщики, цены, знания и источники. Поиск работает по опубликованным
материалам, включая артикулы. Историческая цена, роль компании и подтверждённая
применимость — отдельные сведения; карточки сохраняют даты и ограничения источников.

Владелец добавляет сведения через форму «Добавить запись»: выбирает оборудование
и тип записи, заполняет описание и источник. После сохранения виден статус записи.
Повторная отправка при сбое использует тот же идентификатор. Неопубликованная запись
не выдаётся за сохранённую в основной базе. Просмотр управляется отдельным правом
`knowledge` в существующей панели доступов. Ранее сохранённые роли не расширяются.

## Хранение и обновление

Основная база — существующая закрытая Supabase. Публикуются только строки
`lib_knowledge` с `researched_by = 'Codex/private-library-v1'` и
`sources.publication_approved = true`. Тип карточки хранится в `sources.kind`:
`knowledge`, `component`, `supplier`, `price`; дополнительные поля остаются в
`sources.component_fields`, `sources.supplier_fields`, `sources.price_fields`.
Направления читаются из `lib_segments`. Сырые извлечённые строки `lib_demand`
не превращаются автоматически в проверенные знания.

Статическая HTML-оболочка находится в публичном репозитории и не содержит материалов.
Worker проверяет Cloudflare Access и права, затем читает закрытую копию из существующего
KV (`ACL`, резервная привязка `VISITS`). Серверные ключи Supabase в браузер не передаются.

Workflow «Библиотека — публикация проверенных материалов» переносит одобренные записи
из Supabase в KV. Запускается при изменении своего кода, вручную или по сигналу
`library-update` после добавления записи владельцем. Используются уже существующие
секреты `SUPABASE_DB_URL`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`.
Токен Cloudflare должен иметь доступ к проекту Pages и чтению/записи привязанного KV.
Workflow не создаёт привязки и не расширяет права токенов.

Добавленные через форму записи сохраняются в отдельных ключах `library:draft:*`.
Синхронизация проверяет их, идемпотентно добавляет в Supabase, проверяет обратным
чтением, публикует и только затем отмечает завершение. Если сигнал обновления не
отправился, запись остаётся в очереди; workflow можно запустить вручную.

Предыдущие версии публикации сохраняются в `library:history:*` до смены `library:v1`.
Публикации выполняются последовательно; KV не предоставляет межрегиональных транзакций.
Снимок ограничен 4 МиБ, 100 направлениями и 5000 карточками. Превышение останавливает
публикацию с ошибкой и сохраняет предыдущую версию. Для большего объёма потребуется
разделить выдачу на страницы или сегменты; исходный архив от этого не ограничивается.

Прямой JSON-импорт в расширенной форме обновляет только копию портала; для постоянных
изменений используйте обычную форму или Supabase. В публичные журналы и артефакты
GitHub Actions выводятся только количество записей и коды результата.
