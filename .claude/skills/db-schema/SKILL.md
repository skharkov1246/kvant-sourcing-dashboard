# Схема и миграции Supabase

Одна база, staging нет: «проверить негде, кроме прода» (LESSONS, правило 20). Поэтому
каждый файл схемы обязан применяться на чистом PostgreSQL и проверяться тестом на
одноразовой базе гейта. Номера правил — `docs/agents/LESSONS.md`.

## 1. Файл схемы

- **Повторяемость (21).** `create table if not exists`, `add column if not exists`,
  функции — `create or replace`. `create table if not exists` НЕ меняет существующую
  таблицу: новый вид в `check (… in (…))` — отдельным `drop constraint` / `add constraint`.
- **Вид — сносом перед созданием.** `drop view if exists …; create view …` — иначе на
  живой базе «cannot change name of view column». Это проверяет
  `tests/test_schema_views_droppable.py`.
- **Роли платформы — только через проверку наличия (20).** `anon`, `authenticated`,
  `service_role` есть в Supabase и нет на чистом PostgreSQL. Образец —
  `sup_роли_которые_есть` в `library/supabase/suppliers_schema.sql`
  (`pricebook_schema.sql` — своя копия `pb_роли_которые_есть`). Роли НЕ создавать.
- **RLS на каждой таблице:** `enable` + `force row level security`, `revoke all from
  public` и от `anon`/`authenticated`, `grant` — `service_role`. Виды — тоже `revoke`.
- **Схема из `search_path`, а не `public`:** тест применяет файл в своей схеме.
- **Деньги — `numeric`**, не `float` (`DATA_MODEL.md`). В каждой записи — `run_id`, в
  записи правила — `method_ver`.
- **Новый файл — строкой в `.github/workflows/zip-db.yml`** в правильном месте порядка
  (зависимости выше; ужесточение доступа ЗИП — последним и всегда).

## 2. SQL, который не повесит базу

- **Подзапрос внутри `CASE` не ссылается на обновляемую строку (8):**
  `f.y in (select …)` считается один раз; `exists (select … where d.x = f.y)` — на каждую
  строку и вешал миграцию на 12 минут. Проверять планом.
- **`statement_timeout` — в строке подключения (9)**, а не `SET`: `SET` откатывается
  с транзакцией, дефолт пула Supabase — 2 мин.
  `psycopg2.connect(dsn, options="-c statement_timeout=… -c lock_timeout=10000")`.
- **`lock_timeout` обязателен для `ALTER TABLE` (12)**: без него `ACCESS EXCLUSIVE`
  встаёт в очередь, и за ним все читатели.
- **Вспомогательный шаг — после главного (10).**
- **Снятый прогон не освобождает базу (11):** backend дорабатывает до своего
  таймаута и держит блокировки — следующий упрётся в `lock_timeout`. Дождаться.
- **`UPDATE` сотен тысяч строк `lib_demand` запрещён:** у неё `fts generated always …
  stored` + GIN; пометки — в таблице-спутнике `lib_row_junk` (5).

## 3. Запись данных

- **Холостой по умолчанию**, запись — `APPLY=1`; запись сама отменяется при
  непройденных гейтах (3).
- **Пометка, а не удаление (5); каждая запись с ключом прогона (6)** — откат
  `delete … where run_id = …` снимает ровно свои строки.
- **Ключ строки не терять:** проверить уникальность естественного ключа на настоящих
  данных до `on conflict do nothing` — прайс-бук 01.10.2026: пара (документ, номер
  позиции) повторялась у 417 строк.
- **`rowcount` у `execute_values` — счёт последней пачки.** Итог — запросом по `run_id`.
- **Две вставки в одну таблицу правятся вместе (14)** — пакетная и аварийная построчная.
- **В журнал — только агрегаты (17).** Строки закрытых данных — только в базе.
- **Ключ артикула** — `lib_pn_key` в SQL и `part_key` в Python совпадают; сверка — тест.

## 4. Проверка до PR

1. Одноразовая база в локали UTF-8 (21а) — иначе `lower()` не складывает кириллицу:
   ```bash
   /usr/lib/postgresql/16/bin/initdb -D /var/tmp/pgtest -A trust -U postgres --locale=C.UTF-8 --encoding=UTF8
   export LIBRARY_SQL_TEST_DSN=postgresql://postgres:synthetic-library-ci@127.0.0.1:5432/library_sql_test
   ```
   (полностью — подсказка `scripts/preflight.py` при пустом DSN).
2. SQL-тест (`tests/test_*_sql.py`): схема дважды, без ролей платформы; запись,
   повтор без задвоения, откат по `run_id`; Python против SQL на каждой строке.
3. Мутация каждого исправленного дефекта ловится тестом; между мутациями —
   `find . -name __pycache__ -type d -not -path "./.git/*" -exec rm -rf {} +`.
4. `python scripts/preflight.py` с заданным `LIBRARY_SQL_TEST_DSN`.

## 5. Чего агент не делает

Закрытых ключей у агента нет; строки подключения к рабочей базе в сессии агента нет
(CLAUDE.md, «Агентские сессии»). Схему к рабочей базе применяет прогон
`zip-db.yml` после мержа; данные пишет владелец или прогон с секретом. Коннектор
Supabase допустим только к отдельному проекту с придуманными данными.
