# Чтение из Bitrix24

Правила собраны из `CLAUDE.md` («Битрикс не перегружать», 24.09.2026) и
`docs/agents/LESSONS.md`. Справка по методам — коннектор документации Bitrix24
(`b24-dev-mcp`, `.mcp.json`): он читает только документацию, доступа к порталу у него нет.

## 1. Один клиент, одна пауза

- Все вызовы — через `bitrix_client.BitrixClient`. Своих `requests.post`,
  `sleep(0.3)`, `min_interval` и циклов повторов против лимита не заводить.
- Пауза процесса — `bitrix_client.интервал_портала()` = `BITRIX_PARALLEL / BITRIX_RPS`.
  `BITRIX_RPS` — на ВЕСЬ портал (умолчание 1,5; тяжёлым прогонам 1,2). Прогон частями
  обязан передать `BITRIX_PARALLEL = min(частей, max-parallel)`.
- Скачивание по `urlMachine` (`crm.controller.item.getFile`) — тоже REST, идёт через
  `before_request()` и считается в бюджете.
- Лиды и всё «на пятую часть» — `BITRIX_RPS=0.3`, группа `bitrix-fifth`, по одному.

## 2. Два лимита, оба на вебхук

| лимит | порог | ответ | что делать |
|---|---|---|---|
| частота («дырявое ведро») | +1 за запрос, −2 в секунду, предел 50 | 503 `QUERY_LIMIT_EXCEEDED` | ждать; устойчиво — ≤ 2 запросов/с на портал |
| время метода | 420 с работы метода за скользящие 10 мин | 429 `OPERATION_TIME_LIMIT` | ждать до `time.operating_reset_at`; клиент тормозит сам с 60 % |

На лимите ждать, а не падать: бюджет `BITRIX_WAIT_BUDGET` (30 мин на вызов), пауза
5 → 180 с. Попытками меряются только сеть и 5xx. 24.09.2026 из 50 частей умерли 44 —
все читали список смещением, а смещение считает `total` на каждой странице.

## 3. Обход по ключу, а не смещением

- Полный обход в каждой части запрещён. Часть читает свой диапазон
  `indexer.диапазон_части(макс, shard, shards)` по ключу `>ID` / `>id` с `start=-1`
  (без подсчёта `total`). Смещение `start=50…` — только для справочников в пару страниц.
- Разбиение ровно одно: обход по частям И отбор по хешу файла вместе выбрасывают
  то, что попало в разные части по двум признакам.
- Число частей — вход прогона (`shards`: 10/12/25/50), а не константа в файле.
- Чтение СП-166 обрывалось на 7 150–8 250 записях из 21 865 без сообщения об
  ошибке, а `base/fetch_rfq.py` читал одну страницу (50 из 127, И-1): итог обхода
  всегда сверяется с ожидаемым числом.

## 4. Приращение вместо сплошного обхода

`library/increment.py`: сделки и карточки, изменённые после прошлого УСПЕШНОГО
прохода (`DATE_MODIFY`, `updatedTime`), плюс новые по номеру выше прошлого
наибольшего — фильтр по дате у карточек однажды молча съел две трети записей.
Отметка прохода — в `lib_metric_runs`, ПОСЛЕДНИМ шагом: упавший прогон её не двигает.
Подписки на события (`event.bind`) и исходящих вебхуков в проекте нет: обновление
только опросом.

## 5. Перед постановкой прогона

1. Посчитать запросы: записей / 50 на обход + по одному на файл; разделить на
   `BITRIX_RPS` — это время прогона.
2. Сверить с расписанием: деплой дашборда 00:07, 06:07, 12:07, 18:07 UTC
   (~1 750 запросов, ~20 мин), скан чатов 21:00; cron GitHub опаздывает до 5 ч.
3. Проверить Actions на идущие прогоны: в группе `bitrix-portal` ожидающий ОДИН —
   вторая постановка снимает первую ожидающую.
4. Журнал прогона кончается строкой «портал: запросов … · отказов (503) … · (429) …
   · ждали … с» — у упавшего тоже. Отказы есть — бюджет велик.

## 6. После прогона

Итог — из базы (прогон «Библиотека — сводка и переклассификация» → `stats`), а не
из журнала: журнал показывает последний проход. В журнал — только агрегаты.
