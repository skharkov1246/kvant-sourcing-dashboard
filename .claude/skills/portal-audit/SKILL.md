# Ревизия вкладок портала

Распоряжение владельца 24.09.2026: «на ещё одну пятую ресурса постоянно просто
проходиться по всем вкладкам и смотреть, насколько адекватна информация там и
насколько она полезна». Принцип владельца: ничего не ломаем, улучшаем постепенно.

Эта работа — фоновая. Она не отнимает ресурс у главной задачи сессии: **одна
сессия — одна вкладка, одна правка**. Больше пятой части ресурса на неё не
тратится; Битрикс и база ревизией не читаются вовсе.

## 1. Что меряется

`scripts/portal_audit.py` читает те же ключи KV, что показывают страницы, и по
каждой вкладке печатает две таблицы:

- **проверки** — код (`s.name_key`, `n.k_class`, `b.s_cur_case`, …), подпись,
  сколько значений проверено, сколько дефектных, доля; рядом — сколько было в
  прошлой ревизии (из `audit:v1`). Для кодов печатается образец формы дефекта:
  цифры → `9`, латиница → `a`, кириллица → `я` (`aa999` — это «SS316»);
- **польза** — доли того, что нужно сорсеру: настоящее имя и верный ИНН
  компании, бренд рядом с кодом, выбор из двух поставщиков, сравнимая цена с
  датой, свежесть. Строки «(справочно)» в среднюю пользу не входят.

Внизу — сводка «где работа»: вкладки по числу дефектных штук, средней доле
дефектов и средней пользе и строка «следующая вкладка для правки» — по штукам:
средняя доля по сотне проверок с равным весом размывает массовый дефект
(тысячи строк «карточка N в Битриксе» сдвигают её меньше чем на процент).

Список проверок закрытый: словари `ПРОВЕРКИ_*` и `ПОЛЬЗА_*` в начале каждой
секции скрипта. Каждой проверке соответствует мутация в
`tests/test_portal_audit.py`; чистый выдуманный корпус обязан давать ноль
дефектов.

| вкладка | ключи KV | кто собирает | страница |
|---|---|---|---|
| suppliers | `suppliers:v1` + `crossref:v1`, `crossref:list:NN` | `scripts/publish_suppliers.py` | `public/suppliers.html` |
| nomenclature | `crossref:v1`, `crossref:list:00..07`, `crossref:offers:00..31` | `library/crossref.py`, `scripts/publish_crossref.py` | `public/nomenclature.html` |
| brands | `brands:v1`, `brands:links:v1`, `brands:pairs:v1`, `brands:codes:00..15` | `library/brands.py`, `library/codes_sql.py`, `scripts/publish_brands.py` | `public/brands.html` |
| counters | `counters:v1` | `scripts/publish_counters.py` (точки пишет `scripts/codes_with_prices.py`) | `public/counters.html` |
| library | `library:v2:current` и блобы | `scripts/publish_library_v2.py` | `public/library.html` |
| dict | файл `dict/oem.json` | `scripts/build_dict.py` | эталон бренда для `library/brands.py` |

## 2. Процедура одной сессии

1. **Итог ревизии.** Прочитай журнал последнего прогона «Ревизия вкладок
   портала»: https://github.com/skharkov1246/kvant-sourcing-dashboard/actions/workflows/portal-audit.yml
   (`gh run list --workflow portal-audit.yml -L 3`, затем `gh run view <id> --log`).
   Номер прогона — копированием из вывода, не по памяти. Свежего прогона нет —
   запусти его руками (`workflow_dispatch`, apply выключен) и, пока он идёт,
   занимайся главной задачей сессии.
2. **Выбери одну вкладку**: больше всего дефектных штук или наименьшая
   польза («следующая вкладка для правки» в сводке). Внутри неё — одну
   проверку: ту, где дефектных больше всего **в штуках, которые видит сорсер**
   (строка таблицы, карточка), а не в процентах редкого поля. Пустое звено
   цепочки важнее улучшения заполненного (CLAUDE.md, «Куда мы идём»).
3. **Найди причину в коде**, а не в данных: сборщик снимка → SQL запроса →
   страница. Опись известных дефектов кода — в разделе 4 ниже. Читай вызов, а
   не только объявление (CLAUDE.md, стиль работы).
4. **Замерь до правки, у скольких станет хуже** (правило 0): правка «в среднем
   лучше» не имеет права молча уронить отдельные карточки. Для номенклатуры —
   `--prev-dir` со снимком до правки: ревизия поимённо посчитает, сколько позиций
   потеряли бренд, цену, компанию или выбор. Снимок «после» — выгрузкой
   публикатора с `--out` (вхолостую, без `--apply`) в прогоне Actions, где есть
   `SUPABASE_DB_URL`, и в том же шаге `portal_audit.py --from-dir` по нему:
   файлы с данными из прогона не выносятся (артефакты публичны), наружу — только
   таблицы ревизии.
5. **Исправь по правилам CLAUDE.md**: пометка, а не удаление; обвинять только
   закрытым списком (правило 7); правило чтения — в одном месте для Python и SQL;
   ничего не переписывать в базе ради страницы, если можно поправить сборку.
6. **Проверь**: новая проверка или поправленная — с мутацией в
   `tests/test_portal_audit.py` и нулём на чистом корпусе;
   `python scripts/preflight.py > /tmp/pf.txt 2>&1; echo $?` — только «всё чисто».
7. **PR** с числами «было → стало» по коду проверки и ссылкой на прогон
   ревизии. Мерж — после зелёного гейта. После мержа — следующий прогон
   ревизии покажет в столбце «было» прежнее число: это и есть проверка правки.

## 3. Как запускать

```bash
# живые снимки (Actions, секреты CLOUDFLARE_ACCOUNT_ID и CLOUDFLARE_API_TOKEN)
python scripts/portal_audit.py
AUDIT_APPLY=1 python scripts/portal_audit.py         # и записать итог в audit:v1
# снимки файлами: ключ с «_» вместо «:» плюс .json (как у публикаторов с --out)
python scripts/portal_audit.py --from-dir DIR [--prev-dir ПРОШЛЫЙ] [--only brands,dict] [--out итог.json]
```

- Прогон `.github/workflows/portal-audit.yml` — только ручной, вход `apply`
  (по умолчанию выключен) и `only`. Расписание подключает владелец.
- Своя группа `portal-audit`; в `bitrix-portal` не ставить никогда — постановка
  туда снимет ожидающий ночной разбор.
- Запись в `audit:v1` отказывает, когда итог неполный или не про живую KV:
  `--from-dir`, `--only`, `--prev-dir`, упавшая вкладка, обход библиотеки,
  вставший на пределе блобов, ключ, не разобравшийся как JSON, и ветка без
  `docfilter.класс_не_кода` (проверки «марка, размер, стандарт» тогда не
  применяются вовсе и уходят в «не к чему применить», а не в «0 дефектных»).
- Прогон ждёт до 20 минут, пока идут публикаторы KV (library-publish,
  suppliers-publish, suppliers-quotes, counters-publish), и держит 0,5 с между
  запросами: токен Cloudflare общий, предел — 1200 запросов за 5 минут, а PUT
  публикатора, получивший 429, не повторяется.
- Клиент чтения пускает только GET (запрет — в `call()`, а не в имени метода) и
  только закрытый список ключей, у библиотеки тоже: указатель и блобы по sha256,
  без черновиков `library:draft:*`, истории и `library:v1`.
- Из песочницы агента KV Cloudflare недоступен (прокси): живые цифры — только
  журналом прогона.

Правило 17 здесь главное: репозиторий и журналы Actions публичные. Ни имени,
ни кода, ни ИНН, ни домена, ни номера карточки — ни в журнал, ни в PR, ни в
тест. Поимённые примеры, если понадобятся, — отдельным закрытым ключом KV за
Access (маршрута для этого в воркере пока нет), не артефактом.

## 4. Опись: дефекты, найденные чтением кода

Снимок их не ловит — это очередь правок, по одной на сессию.

- **/nomenclature**: имя компании в таблице предложений ведёт на `/suppliers`
  без `#e=` — у предложения есть `o.e`, а переход теряет компанию; `#k=` с
  ключом, которого нет в снимке, молча показывает список; номер карточки
  запроса `o.f` не показан и не ведёт в Битрикс; бренды не ссылаются на
  `/brands#n=`; `cat_name`, `category`, `unit` (это target_equipment, а не
  единица), `kv`, `alts[].conf`, `makers[].conf` лежат в снимке, но не показаны;
  «сравнимы» (`cmp`) ставится и при двух КП одной компании (проверка `n.cmp_co`).
- **/suppliers**: `legal_form` и `parts` публикатор не пишет, а карточка рисует
  «Нет данных» (проверка `s.dead_labels`); `country` не пишет никто
  (`s.country_dead`); идентификатор карточки Битрикса в запись не выгружается —
  из основной таблицы в Битрикс не попасть (польза `u.bitrix_link`); котировки
  слитых и ждущих ИНН сущностей не видны (`x.ent_missing`); сумма parts по двум
  ключам портала даёт ложную тревогу «снимок отдаёт не все предложения»
  (`x.false_alarm`); ИНН-противоречие не подсвечивается, в отличие от домена.
- **/brands**: запрос 2 берёт имя поставщика из `display_name` и
  `deferred_names` без отсева ключей — «bitrix:2002», сжатый ключ, JSON-массив
  (`b.s_name_key`, `b.s_name_json`); валюты без `upper/btrim` — «usd» рядом с
  «USD» (`b.s_cur_case`); `card_brands[].k` без проверки наличия бренда
  (`b.cb_link`); каталожный путь `ключи_ячейки()` называет бренд целой ячейкой
  («SKF/FAG», `b.name_cell`); усечение реестра и изготовителей до 25 не видно
  (`b.registry_trunc`, `b.alts_trunc`); коды из `part_id` не проверяются на
  правдоподобие и не попадают в номенклатуру (`b.c_fmt`, `b.x_k`); плитка
  «Поставщиков с ценой» не считает «(не указан)», а таблица его показывает.
- **/counters**: страница рисует только замер «коды_и_цены»; «реестр_брендов»,
  инкременты и почта лежат в том же ключе, но их никто не видит; правдоподобность
  «цифра, 4–25 знаков» считает марку, размер и стандарт кодом — нужен разряд
  `not_code` по `docfilter.класс_не_кода`.
- **/library**: столбца бренда в таблице компонентов нет (бренд спрятан в
  заголовке); карточка показывает сырое `family`, таблица — переведённое;
  «Требуют проверки» не видит hypothesis, partial, medium, med
  (`l.conf_hidden`); урезанной краткой карточкой считается почти каждая —
  из-за `publication_approved` в sources, — и подсказка «Описание доступно в
  полном материале» стоит и там, где описания нет и в полной записи
  (`l.desc_hint`); ИНН в контракте библиотеки нет.
- **dict/oem.json** (сделано 25.09.2026): у записи вид `kind` — бренд,
  указание, несколько, описание, номер (`library/oem_kind.py`, одно правило
  для сборщика и проверок `d.*`); читатели берут бренд только у вида «бренд».
  Проверки `d.*` считают теперь записи вида «бренд» с признаком не-бренда;
  остаток — защищённые записи (признак без доказательства из словаря: «MTU /
  Rolls-Royce Power Systems», «Rochester Sensors (ранее …)»), их разбор —
  человеком или разведкой брендов. Склейка разных компаний обрезкой `nkey` до
  40 знаков не найдена (`d.key_glue`); реестр базы, засеянный до пометок,
  понижается повторным засевом (строки словаря повторяют файл, откат по
  `run_id`).
- **/nomenclature, изготовители по каталогу**: таблица выводит роль, страну,
  «что делает» и вердикт как есть — коды разведки `pn_not_found`, `oem_only`,
  `in_stock`, `pn_found_no_stock`, `available_lead` (`gt/data/ship_*.json` через
  `library/load_parts.py`), а в «что делает» — сырая заметка до 1000 знаков
  (проверки `n.mk_raw`, `n.mk_note`). Нужен словарь вердиктов по-русски.
- **/nomenclature, список**: столбцы «Машины» и «Аналоги» рисуются в каждой
  строке, а заполнены только у позиций каталога; надпись «Нет связи» читается
  как сбой сети (статичный текст страницы, снимок его не видит; `n.col_dead`,
  `u.col_models`, `u.col_alts`).
- **/brands, написание кода**: `code_written` — мода `part_number` по ВСЕМ
  строкам кода, в том числе тем, чей номер отвергнут правилом и заменён на
  `part_id` (`codes_sql.price_code`). Страница показывает `k[1] || k[0]` — то
  есть отвергнутую марку («SS316») вместо кода (`b.c_written`).
- **Правило кода (`docfilter`, база `e97ed60`)**: класс «стандарт» судит ключ
  целиком, поэтому «ГОСТ 9833-73 020-025-30», «DIN 471 25», «GB 276 6205»
  (номер детали по стандарту с размером) — «не код», и в номенклатуру такие
  позиции не попадают вовсе. Ревизия их не обвиняет (`класс_написания`), а
  правка самого правила — отдельная задача: у него SQL-двойник
  `lib_pn_plausible`, и менять их надо вместе.
- **dict/oem.json, покрытие**: FAG, NSK, Timken, Emerson, Pall, 3M в словаре не
  записаны — бренд компонента библиотеки разрешается только через /brands
  (`u.oem_queue` — справочно, не дефект компонента).
- **Счётчики не показывают ревизию**: `audit:v1` пишется, но маршрута в
  воркере (`public/_worker.js`, закрытый список ключей) и блока на
  `public/counters.html` ещё нет — это отдельная правка.

## 5. Как добавить проверку

1. Код и подпись — в словарь `ПРОВЕРКИ_<вкладка>` (или `ПОЛЬЗА_<вкладка>`);
   неизвестный код скрипт не примет.
2. Счёт — `т.счёт("код", дефект, вес=1, форма=None)`; форма — только для кодов
   и ключей, и печатается образцом, а не значением.
3. Мутация — в `МУТАЦИИ` теста; чистый корпус остаётся без дефектов, а если
   проверке на нём нечего проверять — в `НЕ_ПРИМЕНИМЫ` с причиной.
4. Обвинять — только закрытым списком: нормальные «NU 316», «ООО Ромашка»,
   «SKF» не должны стать дефектом (на это стоит отдельный тест). Разбор
   скептиков 24.09.2026 нашёл 27 проверок, ругавшихся на нормальное; их формы
   теперь в `test_нормальные_*` и `test_склейка_ячеек_одним_правилом` — новая
   проверка обязана их не задеть:
   - номер подшипника с пробелами («NU 316 ECP», «NJ 2312 ECML C3») — номер:
     наименованием считается два слова от четырёх букв;
   - название с кавычками из Битрикса («ООО "Ромашка"») — имя, JSON — только «[…]»;
   - правовая форма у изготовителя («Bosch Rexroth GmbH», «АО Силовые машины») —
     дефект, только если имя без формы не знают ни словарь, ни /brands;
   - тёзки с разными верными ИНН и группа компаний на одном домене — не дубли:
     сведение держит их раздельно нарочно;
   - «3M», «igus», «ifm» — имена; год вместо цены — только год даты КП;
     размеры и мощности («3х2,5 0,66 кВ», «ЦНС 300 180») — не склейка ячеек;
   - порог по валюте, а не один на все; даты — с сутками запаса (Китай);
   - порог «больше 25 знаков», средняя по каталогу как порог (узлы) — справочно,
     а не дефект: это правило проекта, а не ошибка значения.
