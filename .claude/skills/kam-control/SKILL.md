# КАМ: что делать сегодня

КАМ отвечает за клиента. Его очередь — не отчёт, а список разговоров с клиентом на
сегодня: у каждого пункта КАМ, сделка, сколько дней, сумма сделки и что сделать.
Расчёт — `kamqueue.py` (чистые функции, портал не читает); данные едут в
`people["kamQueue"]` (main.py, после реализации и пресейла) и в живую сверку
(`modules.json`, раздел `people`).

## 1. Откуда пункты

| код | откуда | что сделать КАМу |
|---|---|---|
| `late` | очередь реализации (`lifecycle.EXC`) | письменно согласовать новый срок с клиентом и внести его |
| `risk` | то же | предупредить клиента о риске срока; если сдвиг — новый срок письменно |
| `forecast` | то же | письменно согласовать новый срок с клиентом и внести его |
| `ballKam` | пресейл (`presale.openDeals`, мяч у КАМа по `presale.BALL_RULES`) | по стадии: подать ТКП, закрыть квалификацию, узнать ход тендера, получить решение |
| `planAfterDl` | очередь реализации | письменно согласовать новый срок с клиентом и внести его |
| `prodDev` | то же: бюджетный конец производства прошёл, «Заказ готов» не было (КАМ в копии) | предупредить клиента о риске срока; если сдвиг — новый срок письменно |
| `payNoContract` | то же: оплачено поставщику, договор с заказчиком по стадии не подписан (КАМ в копии) | довести подписание договора с заказчиком |
| `unpaid` | то же: долг клиента — КАМ хозяин, ОСС в копии (решение 26.10.2026, п. 4) | урегулировать долг: получить у клиента оплату или дату оплаты |
| `noUtd` | то же: 11-й р.д. от доставки (КАМ в копии) | получить подписанный УПД |
| `s1Over`, `noOrder`, `noDl` | то же: приёмка у руководителя ОРК, КАМ в копии | ответить руководителю ОРК: срок клиента, всё для приёмки и заказа |
| `noPayPlan` | то же: ОСС хозяин, КАМ в копии | сообщить ОСС срок оплаты клиента по договору |
| `noKam` | сделки без поля «КАМ»: открытые реализации и пресейла и любая сделка реализации (в том числе закрытая) с пунктом для КАМа | назначить КАМа — хозяин пункта «руководитель КАМ» |

Какие пункты реализации — КАМу: где КАМ хозяин или в копии по регламенту ОРК (`role` /
`copyRole` пункта, `ork.ITEM`, решение владельца 26.10.2026, п. 1; `kamqueue.kam_involved`);
`kamCopy` — пункт ведёт хозяин, КАМ держит разговор с клиентом. Пункты реализации одной сделки одного вида сводятся в один: заказов несколько —
разговор с клиентом один (`orders` — сколько заказов, `days` — наибольшее), а заказы пункта —
каждый своей строкой `ords` по номеру: «№486/1 · поставщик · срок · дни» (владелец 29.10.2026:
«сделка одна — заказы разные 1/2/3 — разные поставщики и сроки»; у сигнала сделки без КАМа —
номера `ordLbls`). Пункт
реализации без КАМа не дублируется: такая сделка приходит одним пунктом `noKam`, а её
сигналы (срок сорван, неоплата, УПД, мяч у КАМа сверх порога) — в `also` этого пункта,
по важности; важность (`sev`) и `days` пункта — по самому важному сигналу, дни в стадии —
`stageDays`. Без этого сорванный срок сделки без КАМа уходил в самый низ, а закрытая
сделка без КАМа и без УПД из очереди пропадала. Порядок — по важности, затем по дням и
по сумме сделки.

**Отступление от решения 26.10.2026, п. 1 (записано):** очередь КАМа берёт только пункты
очереди реализации (`life.queue`). Пункты чатов и договоров (`dealctx`: `chatDue:доставка`,
`chatDue:оплата`, `contractMissing:customer`, `contractMissing:both` — КАМ хозяин; `chatRisk`,
`chatDue` прочих видов — КАМ в копии) живут в закрытом массиве `DEALCTX` под правом
«Поставщики: договоры и деньги» и в «КАМы» не попадают: вывести их в очередь КАМа — значит
отдать содержание чатов и договоров без этого права. КАМ видит их во вкладке «Реализация»
при праве. Дни сигналов в `also` — с пометкой «р.д., без пауз», если у сигнала `inWd`.

Рядом с очередью — `upcoming14`: живые недоставленные заказы со сроком клиента от
сегодня до 14 дней. Это не отклонение, а «сверить с ОСС и подтвердить клиенту».

## 3. Золотое правило чата (решение владельца 19.10.2026)

Простой по стадии — лишь кандидат: «стоит» — только если и в чате сделки тихо.
`chat_activity.Reader` — один читатель на сборку: реализация читает первой (там деньги),
пресейл — остатком бюджета (400 запросов на сборку, ≤ 2 запросов/с через
`BitrixClient`); первый лимит портала останавливает чтение для всех.

В пресейле (`presale.compute(..., chat_reader=...)`) у сделок в стадии дольше
`ЗАСТОЙ_ДНЕЙ` (14):

- тихо — `stale` (стоит, чат подтвердил);
- человек писал за неделю — `staleChat` (в чате работа, действия не требует);
- чат не прочитан, нет id чата, не хватило бюджета — `staleUnverified` (серая корзина,
  сделка видна, в «стоят» не входит).

Сверка: `head.staleStage = stale + staleChat + staleUnverified` — инвариант живой сверки.
Без читателя (`chat_reader=None`) — прежнее поведение (старые тесты).

В очереди КАМа сделка пресейла с живым чатом (`chat.status = active`) пунктом
`ballKam` не становится (`head.chatActive` — сколько снято); чат не проверен — пункт
остаётся с пометкой «чат не проверен». Порог мяча у КАМа (3–7 дн.) меньше
`ЗАСТОЙ_ДНЕЙ`, поэтому `main.py` передаёт в пресейл `chat_also=kamqueue.chat_wanted`:
чаты таких сделок читаются тем же читателем, флагов простоя они не получают, только
`chat`. Порядок чтения общий — дольше всех стоящие первыми, так что простой по стадии
бюджет получает раньше.

## 4. Поля

- **КАМ сделки** — только поле «КАМ» `UF_CRM_1740390857` (в реализации — запасное
  «KAM (старое)» `UF_CRM_1736926032`). Ответственный сделки — исполнитель (сорсер или
  коммерсант), не КАМ: подставлять его нельзя. Пусто — «КАМ не указан».
- **Ключ КАМа** — id (`rows.kamId`, `openDeals.kamId`, `life.queue.kamId`): подписи
  реализации («Имя Фамилия (должность)») и пресейла («Фамилия Имя») из разных
  справочников. Подпись — из справочника людей (`main._people`).
- **Сумма сделки** — `saleEur` строки «Реализации»; у пресейла суммы нет (заполнена у 4 %).
- **ID чата по сделке** — `UF_CRM_1734380921` (`chat_activity.CHAT_FIELD`), есть в
  `presale.DEAL_SELECT` и в выборке реализации.

## 5. Вёрстка

Раздел «КАМы» (`renderPeople`, роль `kam`) открывается очередью (`_kqHtml`/`_kqWire`,
как очередь реализации `lfQb`). У роли доступа «КАМ» (`public/_worker.js`) вкладки
«Реализация» нет: воркер вырезает `__CONTRACTS__` в пустышку `__kvNoData()` (Proxy).
Поэтому наличие данных реализации — только `Array.isArray(__CONTRACTS__.rows)`
(`_kqHasCt`): есть — строка реализации открывает карточку сделки; нет — № реализации
ссылка на сделку в Bitrix. Давать роли «КАМ» `CONTRACTS` — решение владельца (это
маржа и вся реализация). Четыре плитки (мяч у КАМа сверх порога, срок клиента
≤ 14 дн., не оплачено, без КАМа) — они же фильтры; чипы по коду; фильтр по КАМу;
строки «что случилось · № · клиент · КАМ · дней · сумма сделки · что сделать»; таблица
«По КАМам» с неоплатой 1–30 / 31–90 / 90+. Справка — `p.kamq`. На вкладке «Сорсинг»
блок пресейла пишет «стоят Q (чат подтвердил) · в чате работа A · чат не проверен U».

## 5а. «Доход» (решения владельца 25.10.2026, `kaminc.py`)

Вкладка называется «Key-аккаунты и продукты» (id `reps`), первое подменю — «Доход»: где
формируется доход ключевых клиентов и продуктов и когда он придёт. Чистые функции поверх
`contracts`, `lifecycle` (раздел `life.pay` — только вход дохода, main.py его забирает),
`people` (сырьё: `comp`, `line`, `pl`, `kamSrc`), `presale`, `kamqueue`, `premia`.

- **Деньги — только класс A**: строка «Реализации» с `saleSrc == "file"` (пишет «файл
  экономики первым»; поля нет — `bitrix`). Остальное — счёт, причина, хозяин, действие.
  R — `premia.result_of` над `premia.pz_of`; поправка — при калибровке ≥ 30 сделок.
- **K1–K7**: получено (`paidStage`, дата — сборка − дни в стадии, платёжка во всех заказах;
  нарастающим — закрытая потом сделка остаётся, дата по `timeline`), «оплачено по
  платёжке» без перевода стадии — отдельно (`paidFile`, ни K1, ни K2), к получению
  (`lifecycle.pay_eta`: прогноз — только от даты заказа + медианы звеньев, из одних медиан
  даты нет), под угрозой (клиент / срок, не складываются), выигрыши квартала (`wonAt`),
  пайплайн по `stage_class`, в цифрах, своя часть — в закрытом массиве.
- **Сумма в плитке** — при доле класса A ≥ 70 % блока, иначе «в цифрах A из n»; результат
  посчитан меньше чем у 70 % — «результат посчитан у R из n», без суммы. K7 — тот же порог
  по сделкам человека (`n`, `nA`, `nR` — по сделкам, не по ролям).
- **Атрибуция одна** — `kaminc.credit`; уволенный в поле — «не закреплено». Доли K7 —
  по настоящим держателям ролей (`premia._parts`), «не закреплено» — уже после раскладки.
- **Права**: открытая часть `KAMINC_HEAD` — всем с вкладкой; деньги `KAMINC` — право
  `kam_money` (`access/acl.js`, копия в `public/_worker.js`, `access/gate.js`); роли —
  только «Руководителю» и админской (`kamMoneyRoleOk`), людям — поимённо.
- **Остальные разделы вкладки без денег**: PEOPLE, KAM, PRODUCT, REPS идут в страницу через
  `dashboard._no_money` (решение 25.10: деньги на вкладке — только сверенные файлом).
  Продажа в очереди КАМа — из `KAMINC` (класс A), без права — столбца нет.
- **Двойная проверка** разными путями (по сделкам = по людям; K7 = Σ пулов; итог = Σ
  значений сделок по корзине; счёт плиток = список; Σ строк разреза = итог); расхождение —
  `money = None`. K1 по платёжкам — пометка `poLow`. Живая сверка — инварианты «доход: …».
- Тесты — `tests/test_kaminc.py`; smoke — `fixture.build_kaminc()`; валидатор требует
  кнопку «Доход» и таблицу разреза.
