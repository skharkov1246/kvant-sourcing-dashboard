# Кампания запросов ТКП поставщикам

Навык описывает проверенный на проекте ОВЭ-75 (сделка Bitrix 23008) порядок:
позиции закупки → карточки в смарт-процессе → двуязычные ТЗ → отправка писем →
контроль ответов. Здесь собраны и рабочие приёмы, и ошибки, которые уже стоили
времени, — читай раздел «Грабли» до того, как что-то запускать.

## 1. Что должно получиться

Одна карточка = один запрос одному изготовителю по одной позиции. В карточке:

| Элемент | Где лежит | Чем становится в письме |
|---|---|---|
| Название карточки | поле `title` | тема письма |
| Текст письма | пользовательское поле «Individual letter text» | тело письма |
| Файл ТЗ | пользовательское поле «Request file» | вложение |
| Компания | `companyId` | адрес получателя |
| Привязка к сделке | `parentId2` **и** UF-поле сделки | связь с проектом |

Отправку делает **робот смарт-процесса** на стадии «Отправлено»: REST-вебхук
письма отправлять не умеет (см. «Грабли»). Человек настраивает робота один раз,
дальше отправка = перевод карточки на стадию.

## 2. Порядок работы

### Шаг 1. Список позиций и кандидатов
Источник — справочник поставщиков проекта (`ove/data/suppliers.json`):
`positions[]` с классом оборудования (`cls`), лотом и названием; `profiles[]` с
контактами. Правило покрытия: **не меньше трёх кандидатов на позицию**, иначе
цену не с чем сравнивать.

### Шаг 2. Строгая проверка пар «класс → изготовитель»
Кандидат берётся **только** из списка своего класса. Нечёткое сопоставление имён
по токенам недопустимо: оно склеивает несвязанные компании (реальный случай —
поставщик автоматики получил запросы на горелки, разливку анодов и весы).
Схема проверки: имя компании карточки должно строго входить в список кандидатов
класса; иначе — переназначить на свободного кандидата класса или снять карточку.

### Шаг 3. Тексты
Два разных документа, не путать:

- **Письмо** — короткое сопроводительное, 1200–1800 знаков, ~25 строк: кто мы,
  что за проект (без раскрытия заказчика), что запрашиваем, одна фраза о
  масштабе, ссылка на приложение, список требований к предложению (объём
  поставки, опросные листы и подтверждение соответствия, срок изготовления, срок
  действия цены, условия поставки, референции), срок ответа, адрес для ответа,
  подпись. **Технику в письмо не выкладывать.**
- **Приложение** — техническое задание файлом. Все параметры, таблицы, количества
  живут здесь.

Язык — язык получателя. Для зарубежных изготовителей: английский, к нему
китайская часть в том же файле (в карточке один слот вложения). Числа, единицы,
марки материалов переносятся 1:1 с исходника; русские марки транслитерируются
(12Х18Н10Т → 12Kh18N10T).

### Шаг 4. Формат вложения — PDF
Отправляем PDF, а не DOCX: он одинаково открывается у получателя и не даёт
править содержание. Конвейер проекта: `ove/tools/rfq_en_clean.py` (снять шапку
письма и поля под ручное заполнение) → `ove/tools/build_rfq_pdf.py` (DOCX → PDF
через LibreOffice, штамп метаданных, манифест для сайта).

### Шаг 5. Посев карточек и загрузка
Создать карточки, заполнить поля, приложить PDF, привязать к сделке **двумя**
полями. Проверить чтением: поле файла должно вернуть объект с `id` и `url`, а не
`0`.

### Шаг 6. Отправка
Настройка робота (делает человек, один раз): канбан смарт-процесса → «Роботы» →
на стадии отправки добавить «Отправить письмо клиенту»; от кого — почтовый ящик
компании; тема — поле «Название»; текст — поле письма; вложение — поле файла.
Дальше рассылка = перевод карточек на эту стадию, партиями, с проверкой первой
партии по факту доставки.

### Шаг 7. Контроль
Номер вида `<сделка>-<карточка>` в теме позволяет привязывать ответы. Регулярная
проверка: молчуны через 5 / 10 / 15 рабочих дней, черновики напоминаний —
комментарием в карточку, отправку подтверждает человек.

## 3. Bitrix REST: рабочие приёмы

Вебхук хранится в `.env` (`BITRIX_WEBHOOK_URL`), в репозиторий не попадает.
Вызовы — JSON POST на `crm.item.{list,get,add,update}`, паузы 0.2–0.4 с.

```python
# файл в пользовательское поле: массив [имя, base64] — НЕ {"fileData": [...]}
fields = {"ufCrm18_1727423346": [name, base64.b64encode(data).decode()]}

# привязка к сделке: ОБА поля, иначе робот портала очистит одиночное
fields = {"parentId2": DEAL_ID, "ufCrm18_1723386389": DEAL_ID}
```

- Список: `total` лежит на верхнем уровне ответа, не внутри `result`.
- Комментарий в ленту: `crm.timeline.comment.add`, `ENTITY_TYPE: "dynamic_166"`.
- `crm.activity.list` с фильтром по подстроке темы по всей таблице уходит в
  таймаут — сужать по `OWNER_TYPE_ID` / `OWNER_ID` / дате.
- Удаление карточек вебхуку обычно запрещено (`ACCESS_DENIED`): бракованные
  помечать префиксом в названии и стадией «Провал», удаляет человек в интерфейсе.

## 4. Грабли (проверено на живой кампании)

1. **Письма через REST не уходят.** `crm.activity.add` с `PROVIDER_ID:
   CRM_EMAIL` создаёт запись в ленте, но письмо не отправляется — проверено
   дважды, включая доставку на собственный ящик. Отправляет только робот или
   человек из интерфейса. SMTP напрямую из рабочей среды тоже может быть
   недоступен (исходящие порты закрыты).
2. **Вложение молча не сохраняется**, если писать его как `{"fileData": [...]}`.
   Ошибки не будет — поле просто останется пустым. Всегда перечитывать карточку
   после записи.
3. **Привязка к сделке слетает**, если заполнено только UF-поле: робот портала
   его очищает. Заполнять вместе с `parentId2`.
4. **Поле «Тема» перезаписывается шаблоном портала.** Опираться на «Название»
   карточки — его портал не трогает.
5. **Нечёткий матчер компаний врёт.** Смотри шаг 2.
6. **Черновик ≠ готовое письмо.** Текст ТЗ, вываленный в тело письма, и
   шаблонные поля `[____]` в приложении — признак недоделанной работы.
   Перед отправкой открыть один готовый экземпляр целиком и прочитать глазами.
7. **Мессенджер вместо почты.** В справочниках попадаются «адреса» вида
   `<номер>@whatsapp.<сервис>` — отсеивать проверкой формата почты.

## 5. Ограничения по содержанию

- Имя заказчика и площадки во внешних документах не раскрывается ни на одном
  языке (включая написание иероглифами); вместо него — обезличенная формулировка.
- Партнёры и конкуренты по имени не упоминаются.
- Слово «санкции» не употребляется: пишем «поставка в РФ недоступна».
- Цены в запросах не проставляются — их даёт поставщик, вносит владелец.
- Язык документов — прямой инженерный, без рекламных оборотов, новояза,
  фамильярностей и аналогий.
- Метаданные всех DOCX/PDF — реквизиты компании, без следов инструментов сборки.
- Письма реальным поставщикам уходят **только по прямому распоряжению владельца**.
