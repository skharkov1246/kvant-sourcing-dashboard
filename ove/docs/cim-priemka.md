# Приёмка ЦИМ (IFC) за минуты — ove/tools/ifc_check.py

«Кнопка приёмки»: САПРщик сдаёт IFC-модель — инструмент за минуты прогоняет её по
требованиям ТЗ на ЦИМ ред.2 (Прил.4 к ТЗ на БИ v4.1, Таблица 3 «Проверки») и Прил.1
(LOD G/LOI, стадия БИ) и выдаёт акт: в консоль и в DOCX. Замечание адресное —
GlobalId + имя элемента, САПРщик находит его у себя поиском за секунды.

## Запуск

```bash
pip install ifcopenshell                                  # один раз, локально
python3 ove/tools/ifc_check.py путь/к/модели.ifc          # один файл
python3 ove/tools/ifc_check.py папка_с_моделями/          # все .ifc в папке (рекурсивно)
python3 ove/tools/ifc_check.py --selftest                 # самопроверка на синтетике
```

Ключи: `--out акт.docx` — куда положить DOCX-акт (по умолчанию — рядом с моделями,
`akt-priemki-cim-<дата>.docx`); `--no-docx` — только консоль. Коды выхода: `0` —
принято (в т.ч. с замечаниями), `1` — возврат на доработку, `2` — ошибка запуска.
В сборку сайта инструмент не входит; без ifcopenshell мягко сообщает и выходит.

## Шесть проверок

| № | Что проверяем | Основание | Серьёзность |
|---|---|---|---|
| 1 | Имя файла по блокам `шифр_стадия_объект_марка_содержание_разработчик_ПО`, без пробелов; размер ≤ 500 МБ | ТЗ разд. 7.2, табл. 4 | критично; код стадии не CONCP/PD/BI — существенно (C-79) |
| 2 | Иерархия IfcProject → IfcSite → IfcBuilding → IfcBuildingStorey; единицы СИ (мм/м, м², м³); схема IFC 2x3/4/4x3 | ТЗ разд. 4.3, «Требования к файлам IFC» | критично |
| 3 | Каждый элемент привязан к этажу и имеет непустой Name (не заглушка) | «Общие требования к ЦИМ» (разбивка по этажам) | существенно / инфо |
| 4 | LOI-атрибуты Прил.1 для стадии БИ: у элемента есть Pset с полями группы (ТХ: местоположение, наименование, геометрия, характеристики системы и оборудования; ЭОМ/СС/АК: + нагрузки, напряжение, мощность, тип системы, масса) | Прил.1, листы «Стадия БИ_ТХ» и «Стадия БИ_ЭОМ,СС,АК» | существенно |
| 5 | Геометрия: нет вырожденных/пустых тел (габарит < 0,1 мм); все элементы в габарите площадки (< 2 км от начала координат) | ТЗ разд. 4.3 (СК: пересечение первых осей и 0,000) | критично |
| 6 | GlobalId: без дубликатов, формат 22 символа | «Проверка на дублирование компонентов» | критично / существенно |

Профиль LOI берётся по марке из имени файла (`TX` → ТХ; `ES`/`SS`/`AK` → ЭОМ/СС/АК);
если имя не разобрано — профиль ТХ с пометкой в акте. Правила читаются из данных
проекта: `ove/data/bim_plan.json` (шифр, марки, перечни LOI) и `ove/data/deliverables.json`
(живые позиции реестра по ЦИМ — идут в шапку акта как основание).

## Вердикты

- **ПРИНЯТО** — замечаний нет;
- **ПРИНЯТО С ЗАМЕЧАНИЯМИ** — только «существенно»/«инфо»: модель берём, замечания на устранение к следующей выгрузке (цикл — раз в 4 недели в СУИД);
- **ВОЗВРАТ НА ДОРАБОТКУ** — есть хотя бы одно «критично»: файл Заказчику не передаём.

Пример корректного имени: `OVE-75_CONCP_2.8.3_TX_MM_KVANT_MSCS2024.ifc`
(шифр · стадия · объект · марка · содержание MM/FM · разработчик · ПО).

## Самотест

`--selftest [папка]` генерирует ifcopenshell-ом два синтетических файла — эталонный и
с 5 намеренными дефектами (имя не по ТЗ, нет IfcSite, элемент без LOI, элемент в 25 км
от нуля, дубль GlobalId) — и проверяет: эталон принят без замечаний, все 5 дефектов
пойманы, ложных срабатываний нет, DOCX-акт собрался.

## Что инструмент НЕ делает

Не заменяет проверку коллизий (Model Studio CS / CADLib по Таблице 3), сверку модели
с документацией и визуальную оценку LOD G — это ручные пункты перед сдачей.
Инструмент — входной фильтр: снимает формальный брак до того, как модель уйдёт
в сводную и к Заказчику.
