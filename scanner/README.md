# КВАНТ Скан

Мобильная платформа сбора первичных данных о единицах товара на складе:
фотофиксация, обмер, чтение кодов маркировки, трассировка до оригинального
поставщика. Android + iOS, offline-first, мультитенантная.

> **Статус:** архитектура + рабочий каркас. Бэкенд запускается и проходит тесты
> локально; мобильные модули — структура и ключевая логика, без сборки под
> устройство (нужны Android SDK / Xcode).

## Что это решает

Складская система порождает задания на сканирование. Задание прилетает на
телефон кладовщика. Приложение ведёт человека по шагам, сразу проверяет качество
каждого кадра и складывает результат в локальную базу — **даже если сети на
складе нет вообще**. Данные уезжают на сервер надёжно и в фоне. На сервере из
сырья собирается карточка единицы товара: габариты с классом точности, медиа,
коды, связи «код → партия → поставщик». Пользуются и наши сотрудники, и
сотрудники компаний-заказчиков; каждый видит только свой периметр.

## Пять несущих решений

| # | Решение | Зачем |
|---|---|---|
| 1 | **Offline-first, устройство — источник истины** | Склад — бетон, металл и холодильные камеры. Ни одно действие пользователя не ждёт сеть. |
| 2 | **Сценарий съёмки — данные, а не код** | Новая категория товара = работа технолога в web-консоли, а не релиз в сторах. |
| 3 | **Append-only события вместо CRUD** | Повторная доставка безопасна, работа не теряется, есть полный аудит. |
| 4 | **Храним сырьё, а не выводы** | Через год модель станет точнее — пересчитаем архив вместо повторного выхода бригады. |
| 5 | **Лестница деградации везде** | У каждой критичной способности есть ступень, которая работает всегда. |

Подробное обоснование — в [журнале архитектурных решений](docs/adr/).

## Структура

```
scanner/
├── docs/                 Проектная документация (10 разделов + ADR + контракты)
│   ├── api/openapi.yaml            Контракт REST API — валидируется в CI
│   ├── schemas/                    JSON Schema протокола съёмки + рабочий пример
│   └── adr/                        Журнал архитектурных решений
├── shared/               Kotlin Multiplatform: общее ядро Android и iOS
│   └── src/commonMain/kotlin/ru/kvant/scan/
│       ├── domain/       Доменные модели, классы точности, инварианты
│       ├── protocol/     Модель протокола съёмки + интерпретатор условий
│       ├── sync/         Outbox, движок синхронизации, проекция сессии
│       └── measure/      Граница с сенсорами + лестница деградации обмера
├── androidApp/           Compose UI, CameraX, ARCore, ML Kit
├── iosApp/               SwiftUI, AVFoundation, ARKit, Vision
└── backend/              FastAPI: приём событий, медиа, задания, трассировка
    ├── app/schema.sql    Схема PostgreSQL с RLS
    └── tests/            40 тестов: идемпотентность, изоляция, докачка, протокол
```

## Быстрый старт

### Бэкенд

```bash
cd scanner
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt

# тесты
cd backend && ../.venv/bin/python -m pytest -q

# локальный запуск
../.venv/bin/python -m uvicorn app.main:app --reload
# → http://127.0.0.1:8000/docs
```

### Проверка контрактов

```bash
cd scanner
# протокол съёмки валиден против своей схемы
.venv/bin/python -c "
import json, jsonschema
s = json.load(open('docs/schemas/capture-protocol.schema.json'))
d = json.load(open('docs/schemas/examples/pallet_general_v7.json'))
jsonschema.Draft202012Validator(s).validate(d); print('протокол OK')"

# OpenAPI валиден
.venv/bin/pip install -q openapi-spec-validator
.venv/bin/python -c "
from openapi_spec_validator import validate
from openapi_spec_validator.readers import read_from_filename
validate(read_from_filename('docs/api/openapi.yaml')[0]); print('OpenAPI OK')"
```

## Связь с Sourcing Analyzer

Проект живёт в одном репозитории с дашбордом анализа работы сорсеров и
переиспользует его наработки:

- `bitrix_client.py` — обкатанный клиент Bitrix24 с батчингом, троттлингом и
  ретраями под лимиты портала; на нём строится первый адаптер приёма заданий;
- `company.py` — справочник контрагентов, из которого берётся справочник
  поставщиков для подсказок в приложении (работает офлайн из локальной копии).

Обратная связь тоже есть: фактическое качество поставок со склада — доля
повреждённых единиц, отклонения габаритов от каталога, доля нечитаемых кодов —
дополняет картину работы сорсеров реальными фактами, а не только историей
переписки.

## Правила разработки

Действуют правила корневого `CLAUDE.md`: не коммитить в `main`, батчить
изменения в один PR, тестировать до пуша. Дополнительно для этого подпроекта:

- изменения контракта (`openapi.yaml`, `capture-protocol.schema.json`) — только
  аддитивные внутри версии; ломающие изменения = новая версия URL;
- логика, продублированная в KMP-ядре и в бэкенде (интерпретатор протокола,
  проекция сессии), меняется **одновременно в обоих местах**, иначе клиент и
  сервер начнут расходиться в данных;
- новая функция не принимается без описанной ступени отказа (§08.2).
