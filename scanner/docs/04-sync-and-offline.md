# 04 · Офлайн и синхронизация

> Раздел, отвечающий на требование «система никогда не должна падать».
> Склад — это бетон, металл, холодильные камеры и подвалы. Проектируем так,
> будто сети нет никогда, а её появление — приятный бонус.

## 4.1 Правило нулевого ожидания

**Ни одно действие пользователя не ждёт сеть.** Нажатие затвора, ввод поставщика,
завершение задания — всё пишется в локальную БД синхронно и возвращает управление
UI за миллисекунды. Сеть обслуживается отдельным фоновым процессом, о котором
пользователь узнаёт только из ненавязчивого индикатора «N заданий ожидают отправки».

Из этого правила вытекает всё остальное в этом разделе.

## 4.2 Три канала обмена

| Канал | Что несёт | Объём | Требования |
|---|---|---|---|
| **Pull** | Задания, протоколы, справочники, отзывы контроля | Килобайты | Курсор, дельты, дешёвый |
| **Push событий** | Факты сессии (шаги, обмеры, коды) | Килобайты | Идемпотентность, порядок |
| **Медиа** | Кадры, видео, карты глубины | Десятки–сотни МБ | Чанки, докачка, дедуп, Wi-Fi-политика |

Разделение критично: **метаданные не должны застревать за гигабайтом видео.**
Сервер узнаёт, что паллета обмерена, через секунды после появления сети; кадры
догружаются часами, если надо. Карточка единицы товара создаётся сразу и живёт в
состоянии `media_pending`.

## 4.3 Outbox: как устроена очередь

```
┌──────────────┐   пишет    ┌────────────────┐   читает   ┌──────────────┐
│  UI / домен  │──────────▶ │  SQLite: outbox│ ──────────▶│ SyncWorker   │
└──────────────┘  синхронно │  (события)     │  батчами   │ (WorkManager/│
                            │  media_queue   │            │  BGTask)     │
                            └────────────────┘            └──────┬───────┘
                                    ▲                            │
                                    └──── подтверждения ─────────┘
```

Свойства очереди:

- **Строгий порядок в рамках сессии** (`seq`), свободный порядок между сессиями.
  Так одна залипшая сессия не блокирует остальные.
- **Экспоненциальный backoff с джиттером**: 2с → 4с → 8с → … → 15 мин, потолок.
  Джиттер обязателен: иначе после восстановления сети сто телефонов смены ударят
  в сервер одновременно (thundering herd).
- **Классификация ошибок**: `retryable` (сеть, 5xx, 429) → повтор;
  `permanent` (4xx-валидация) → карантин + видимый пользователю статус.
  Молча ретраить невалидные данные вечно — самый частый способ «потерять» данные.
- **Карантин, а не удаление.** Событие, отвергнутое сервером навсегда, уходит в
  `dead_letter` с причиной и остаётся доступным для выгрузки в поддержку.
- **Ограничение по диску.** При достижении порога (по умолчанию 80% свободного
  места или 20 ГБ) приложение переходит в режим экономии: понижает качество видео,
  требует подключения к сети, предупреждает пользователя. Оно **не удаляет
  неотправленное сырьё** (инвариант I-1).

## 4.4 Протокол синхронизации

### Pull

```http
POST /v1/sync/pull
{
  "cursor": "eyJ0IjoxNzE4...",         // null при первом запуске
  "device_id": "...",
  "capabilities": { "schema_version": 1, "app_version": "1.4.0", "depth": "ar_depth" },
  "scopes": ["tasks", "protocols", "directories"]
}
→ 200
{
  "changes": [
    { "type": "task.upsert",     "data": { ... } },
    { "type": "task.revoke",     "data": { "id": "..." , "reason": "cancelled" } },
    { "type": "protocol.upsert", "data": { ... } },
    { "type": "directory.patch", "data": { "name": "supplier_directory", "ops": [ ... ] } }
  ],
  "next_cursor": "eyJ0IjoxNzE4...",
  "has_more": false,
  "server_time": "2026-07-28T09:14:02Z"
}
```

- Курсор непрозрачен для клиента (внутри — `(updated_at, id)`), чтобы схему пагинации
  можно было менять на сервере.
- `capabilities` — то, за счёт чего сервер **не выдаёт** заданий, которые устройство
  не сможет выполнить (§3.7, правило 4).
- `has_more` позволяет тянуть большие дельты кусками, не держа длинный запрос.

### Push событий

```http
POST /v1/sync/events
{
  "device_id": "...",
  "events": [
    { "client_event_id": "01917f...", "session_id": "...", "seq": 12,
      "type": "step.completed", "device_ts": "...", "payload": { ... } }
  ]
}
→ 200
{
  "results": [
    { "client_event_id": "01917f...", "status": "accepted" },
    { "client_event_id": "01917e...", "status": "duplicate" },
    { "client_event_id": "01917d...", "status": "rejected",
      "error": { "code": "protocol_version_gone", "message": "...", "retryable": false } }
  ],
  "server_time": "..."
}
```

Ключевые решения:

- **`client_event_id` — UUIDv7**, генерируется устройством. Сортируемый по времени,
  не требует координации, уникален глобально. Это единственный ключ идемпотентности.
- Ответ **по каждому событию отдельно**. Батч не может «частично упасть» непонятно
  как: клиент точно знает, что удалять из outbox, что повторять, что в карантин.
- `duplicate` — это **успех**, а не ошибка. Повтор после потери ответа — норма.
- HTTP 200 при наличии отвергнутых событий: транспорт отработал, семантика — в теле.

### Медиа: чанковая загрузка

```
POST   /v1/assets                        → { asset_id, upload_url, chunk_size }
PUT    /v1/assets/{id}/chunks/{n}        → 204   (идемпотентно по (id, n))
POST   /v1/assets/{id}/complete          → { status: "verified" | "checksum_mismatch" }
GET    /v1/assets/{id}/status            → { received_chunks: [...] }   ← для докачки
```

- Размер чанка адаптивный: 256 КБ на 3G, 4 МБ на Wi-Fi. Определяется по замеру
  скорости последней успешной загрузки.
- `sha256` считается на устройстве **до** отправки и проверяется сервером на
  `complete`. Несовпадение → повтор целиком, данные не принимаются молча.
- Дедупликация по `(tenant_id, sha256)`: повторная отправка того же кадра не занимает
  место и мгновенно завершается.
- Политика сети настраивается: «только Wi-Fi», «Wi-Fi + мобильная», «без ограничений».
  По умолчанию видео и облака точек — только Wi-Fi, фото — всегда.

## 4.5 Конфликты и их разрешение

Событийная модель убирает большинство конфликтов, но не все. Полный список
реальных случаев и правил:

| Ситуация | Правило |
|---|---|
| Задание отозвано источником, пока кладовщик снимает | Сессия завершается, данные **принимаются и сохраняются**, задание помечается `cancelled_after_work`. Работа человека никогда не выбрасывается. |
| Два устройства начали сессию по одному заданию | Обе сессии валидны. Сервер выбирает основную по правилу «первая завершённая», вторая привязывается как `duplicate_of`. Контролёр видит обе. |
| Локальная версия протокола устарела | Идущая сессия доживает на пинованной версии (I-4). Новые сессии берут актуальную. |
| Часы устройства врут | Порядок определяется `seq`, не `device_ts`. `device_ts` сохраняется как есть, рядом пишется `server_ts` и вычисленный `clock_skew`. |
| Событие ссылается на неизвестный сервером asset | Событие принимается, карточка в состоянии `media_pending`; медиа догружается позже. Обратная зависимость запрещена. |
| Одно и то же событие с разным payload | Побеждает первое принятое. Второе → `rejected: conflicting_duplicate` + алерт: это признак бага клиента. |

Общий принцип: **при сомнении сохраняем всё и эскалируем человеку**, а не выбираем
автоматически и не удаляем. Стоимость лишней записи в БД пренебрежимо мала по
сравнению со стоимостью повторного выхода бригады на склад.

## 4.6 Продолжение сессии на другом устройстве

Требование реальной смены: телефон разрядился, работу дочитывает коллега.

1. Сессия помечается `PAUSED` (явно или по таймауту неактивности).
2. Устройство A дотягивает свой outbox при первой возможности.
3. Устройство B запрашивает `GET /v1/sessions/{id}/log` — получает лог событий.
4. B доигрывает лог локальной проекцией (`SessionProjection`) и продолжает с `seq+1`.
5. Медиа, не выгруженное с A, помечается `orphan_pending`; сервер ждёт его до
   истечения retention и напоминает, если A так и не появилось в сети.

Пункт 5 — честное признание ограничения: **если устройство утеряно физически, не
выгруженное с него сырьё потеряно.** Смягчаем это агрессивной выгрузкой фото
(сразу при любой сети) и оставляем тяжёлое видео единственным реальным риском.
Полностью проблему решает только требование сдавать смену онлайн — оно вынесено
в организационный регламент, а не в код.

## 4.7 Бюджеты и SLO синхронизации

| Метрика | Цель | Почему столько |
|---|---|---|
| Задержка UI на запись шага | p99 < 50 мс | Ниже порога заметности |
| Задержка «событие → видно на сервере» при наличии сети | p95 < 30 с | Диспетчер видит прогресс почти в реальном времени |
| Доля событий, доставленных без ручного вмешательства | > 99.9 % | Ручной разбор — дорогая операция |
| Время полной выгрузки смены (200 заданий, ~6 ГБ) по Wi-Fi | < 40 мин | Успеть в пересменку |
| Автономность приложения без сети | ≥ 3 смены | Реальный худший случай на удалённых складах |

## 4.8 Что делает синхронизацию хрупкой (и как мы это исключили)

- ❌ **Синхронный вызов при нажатии кнопки** → ✅ outbox, правило нулевого ожидания.
- ❌ **Один общий канал для метаданных и медиа** → ✅ три независимых канала.
- ❌ **Ретрай без ограничения и без классификации ошибок** → ✅ backoff + карантин.
- ❌ **Идемпотентность по «первичному ключу сущности»** → ✅ отдельный `client_event_id`.
- ❌ **Батч, падающий целиком** → ✅ результат по каждому событию.
- ❌ **Удаление локальных данных по факту отправки** → ✅ удаление по факту
  подтверждённой сверки контрольной суммы.
- ❌ **Push как транспорт данных** → ✅ push только как сигнал «сходи за обновлениями»;
  потеря push ничего не ломает, потому что есть периодический pull.
