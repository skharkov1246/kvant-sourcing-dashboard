# 07 · Безопасность, мультитенантность и доступ

> Система с самого начала обслуживает два класса пользователей: наших сотрудников
> и сотрудников заказчиков. Это архитектурное требование, а не будущая доработка —
> «добавить мультитенантность потом» на практике означает переписать хранилище.

## 7.1 Модель тенантов

```
Tenant
├─ kind: internal          — КВАНТ, полный доступ к своим данным
├─ kind: customer          — заказчик, изолированный периметр
└─ kind: partner           — подрядчик, работающий на площадке заказчика
```

Между тенантами возможна **явная делегация**: заказчик разрешает нашему тенанту
видеть свои задания на площадке X до даты Y. Делегация — это запись
`tenant_grant(from_tenant, to_tenant, scope, expires_at)`, а не хардкод «мы видим
всё». Без этого невозможно честно ответить заказчику на вопрос «кто из ваших
сотрудников видел наши данные».

## 7.2 Изоляция данных: три рубежа

Один рубеж всегда пробивается ошибкой в коде. Поэтому их три:

**Рубеж 1 — Row Level Security в PostgreSQL.** Каждая доменная таблица несёт
`tenant_id`, на каждой включён RLS:

```sql
ALTER TABLE scan_task ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON scan_task
  USING (tenant_id = current_setting('app.tenant_id')::uuid
         OR tenant_id IN (SELECT from_tenant FROM tenant_grant
                          WHERE to_tenant = current_setting('app.tenant_id')::uuid
                            AND expires_at > now()));
```

Приложение выставляет `app.tenant_id` из проверенного токена в начале транзакции.
Забытый `WHERE tenant_id = ...` в запросе перестаёт быть уязвимостью — он просто
не вернёт чужих строк.

**Рубеж 2 — ABAC на уровне сервиса.** Решение о доступе принимает единая функция
по атрибутам субъекта (тенант, роли, площадки), объекта (тенант, площадка,
состояние) и действия. Никаких `if user.is_admin` по коду.

**Рубеж 3 — изоляция хранилища объектов.** Ключи вида
`{tenant_id}/{yyyy}/{mm}/{session_id}/{asset_id}`, доступ — только через
короткоживущие presigned URL (TTL 15 мин), выдаваемые после проверки рубежа 2.
Прямого листинга бакета у клиента нет.

## 7.3 Роли

| Роль | Назначение | Ключевые права |
|---|---|---|
| `operator` | Кладовщик, замерщик | Выполнять назначенные задания, вносить `declared`-трассировку |
| `lead` | Бригадир | Всё от `operator` + переназначать задания внутри площадки |
| `reviewer` | Контролёр качества | Принимать/возвращать сессии, ставить `verified` |
| `technologist` | Технолог | Создавать и публиковать протоколы съёмки |
| `integrator` | Интеграционный аккаунт | Только API: приём заданий, забор результатов |
| `tenant_admin` | Администратор тенанта | Пользователи и настройки своего тенанта |
| `platform_admin` | Наш админ | Кросс-тенантные операции, каждая — в неизменяемом журнале аудита |

Роли аддитивны и всегда действуют **в границах тенанта**. `platform_admin` — единственная
кросс-тенантная роль, и каждое её действие пишется в append-only журнал с указанием
причины. Технически: журнал в отдельной схеме, права `INSERT` без `UPDATE`/`DELETE`
даже у владельца БД-роли приложения.

## 7.4 Аутентификация

| Субъект | Механизм |
|---|---|
| Наш сотрудник | OIDC (корпоративный провайдер) → короткоживущий access-токен (15 мин) + refresh (30 дней, привязан к устройству) |
| Сотрудник заказчика | OIDC заказчика, если есть; иначе логин/пароль + TOTP, парольная политика на стороне тенанта |
| Устройство | Собственный `device_id` + ключевая пара в аппаратном хранилище (Android Keystore / iOS Secure Enclave) |
| Интеграция | OAuth2 client credentials, при желании заказчика — mTLS |

**Почему refresh-токен привязан к устройству.** Склад — среда с высокой текучкой и
потерянными телефонами. Токен, работающий с любого устройства, при утере телефона
даёт доступ к данным заказчика. Привязка к ключу в Secure Enclave/Keystore делает
украденный токен бесполезным без самого устройства.

**Аттестация устройства.** При регистрации — Play Integrity API (Android) /
DeviceCheck + App Attest (iOS). Провал аттестации не блокирует работу жёстко
(кастомные прошивки на складских устройствах встречаются), но помечает устройство
`untrusted`, и тенант в своих настройках решает, допускать ли такие.

## 7.5 Защита данных

- **В транзите:** TLS 1.3, certificate pinning в мобильном приложении с двумя
  пинами (текущий + запасной) и аварийным отключением через remote config —
  иначе ротация сертификата превращается в мгновенный отказ всего парка устройств.
- **На устройстве:** SQLCipher для локальной БД, медиа в приватной директории
  приложения, ключ — в Keystore/Secure Enclave. Экран блокировки обязателен
  политикой; без него приложение работает в ограниченном режиме.
- **На сервере:** шифрование дисков, шифрование объектного хранилища (SSE-KMS),
  отдельный ключ на тенанта для тех, кто это требует по договору.
- **Удалённое стирание:** `platform_admin` или `tenant_admin` помечает устройство
  `revoked`; при следующем контакте приложение стирает локальные данные. Если
  контакта нет — данные всё равно зашифрованы, а токены протухают.

## 7.6 Персональные данные и локализация

Система собирает: ФИО сотрудника, идентификатор устройства, геолокацию (если
включена протоколом), время работы. Это персональные данные по 152-ФЗ.

- Хранение — в РФ (требование 152-ФЗ для ПДн граждан РФ).
- Геолокация выключена по умолчанию, включается протоколом и только с явным
  информированием пользователя в интерфейсе. Тихая геолокация сотрудников —
  это не техническое решение, а трудовой конфликт.
- Права субъекта ПДн: выгрузка и удаление данных сотрудника при увольнении.
  При этом **производственные данные обезличиваются, а не удаляются**: карточка
  товара остаётся, `user_id` заменяется на псевдоним. Иначе удаление одного
  сотрудника рушит трассируемость всех его приёмок.
- Для тенантов-заказчиков — отдельное соглашение об обработке; наш тенант
  выступает обработчиком, заказчик — оператором.

## 7.7 Аудит

Пишется в append-only журнал, отдельно от прикладных данных:

- вход/выход, регистрация и отзыв устройства;
- любой кросс-тенантный доступ;
- изменение ролей и грантов;
- публикация и отзыв протокола;
- изменение вердикта контроля качества;
- выгрузка данных (кто, что, сколько строк, в каком формате).

Срок хранения журнала — минимум 3 года, дольше прикладных данных. Формат
рассчитан на экспорт в SIEM заказчика.

## 7.8 Модель угроз (коротко)

| Угроза | Митигация |
|---|---|
| Утеря телефона с данными заказчика | Шифрование БД, привязка токена к устройству, remote wipe, короткий TTL access-токена |
| Сотрудник заказчика пытается прочитать данные соседнего тенанта | RLS (рубеж 1) + ABAC (рубеж 2) + presigned URL (рубеж 3) |
| Подмена протокола съёмки для сбора «нужных» результатов | Ed25519-подпись протокола, проверка на устройстве |
| Фальсификация приёмки (снял стену вместо товара) | Серверные анализаторы: детекция объекта, перцептивный дедуп, сверка веса с объёмом, EXIF-аномалии |
| Массовая выгрузка данных скомпрометированным интеграционным ключом | Rate limiting по ключу, алерт на аномальный объём, обязательный аудит выгрузок |
| Компрометация нашего бэкенда | Изоляция ключей шифрования по тенантам, WORM для сырья, отсутствие у сервиса прав `DELETE` на журналы |
| Отказ внешнего OIDC заказчика | Локальный резервный вход для `tenant_admin`, работа устройств продолжается на нерастухшем refresh-токене |
