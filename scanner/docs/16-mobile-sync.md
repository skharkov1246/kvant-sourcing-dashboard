# 16. Мобильная синхронизация: как устроена и что проверено вживую

Короткая записка для владельца и будущих разработчиков: состояние
мобильной вертикали на момент закрытия каталога протоколов. Детальные
принципы — в [04-offline-sync.md](04-offline-sync.md); здесь — что из них
уже реализовано, где лежит код и чем доказано, что это работает.

## 16.1 Три канала — три независимых судьбы данных

| Канал | Код (shared) | Что едет | Судьба при обрыве сети |
|---|---|---|---|
| pull | `SyncEngine.pullOnce` + `PullApplier` + `TaskStore`; курсор — `SyncStateStore` (переживает рестарт) | задания, протоколы, справочники, вердикты, поставщики (килобайты) | список работает по последней копии; плашка «не обновилось» |
| события | `Outbox` + `InMemoryOutboxStore` + `SyncEngine.pushOnce` | факты сессии, идемпотентно по client_event_id | копятся в outbox; «голова сессии держит хвост», сессии друг друга не держат |
| медиа | `MediaQueue` + `MediaWorker` + `AssetUploader` (чанки, resume, дедуп по sha256) | кадры и видео чанками | догружаются часами, метаданные их не ждут; файл удаляем только после подтверждения сервера |

Поверх каналов — очередь заявок трассировки (`TraceLinkQueue`: без сети
заявка ждёт и уезжает следующим проходом) и сводка `SyncStatus`
(«не синхронизировано: N» на списке заданий; ноль = устройство можно
выключать без потери данных).

Разделение — принцип §04.2: сервер узнаёт «паллета обмерена» через секунды
после появления сети, даже если гигабайт видео поедет всю ночь.

## 16.2 Слои и их место

```
UI (Compose / SwiftUI)          TaskListScreen, CaptureView, TaskDetailScreen
  │   тонкие двойники: контракт и поведение — одно на обе платформы
KMP-ядро (commonMain)           CaptureSessionController, ProtocolInterpreter,
  │                             Outbox, TaskStore, DirectoryStore, Geometry
KtorSyncTransport               единственная граница форматов:
  │                             Instant(epoch ms) ↔ ISO-8601, ETag ↔ кэш
HTTP /v1/*                      FastAPI: приёмка, очередь ревью, экспорт
```

Правило границы: ядро не встречается ни с метрами ARCore, ни с ISO-датами
API — все конвертации живут в адаптерах (`ArCoreSessionAdapter`,
`KtorSyncTransport`), и у каждой есть тест.

## 16.3 Чем доказано (по состоянию на этот PR)

- **Юнит-тесты обеих половин: 498 Python + 112 Kotlin**; ключевые наборы:
  `OutboxStoreTest` (семантика очереди, которую обязана повторить
  SQLDelight-реализация), `PullApplierTest` (дельта и аддитивность),
  `KtorSyncTransportTest` (MockEngine: заголовки, ISO, 304, обрывы),
  `TraceLinkQueueTest`/`SyncStateStoreTest` (офлайн-надёжность и рестарт),
  `CrowdApiTest` (карточка кампании, реестр участника).
- **Девять живых смоков** `jvm-check/.../LiveBackendSmokeTest` — обе
  половины PR разговаривают реальным HTTP через локальный uvicorn
  (`python -m uvicorn app.devserver:app --port 8077`): событие → очередь
  контролёра; полный цикл оператора (inbound → pull → съёмка → REWORK →
  pull видит REWORK); загрузка ассета с проверкой sha256 против hashlib и
  дедупом; MediaWorker с файлом до «удаляемого»; подсказки поставщиков
  через pullOnce; карточка товара из принятой сессии (verified-коды);
  заявка трассировки через очередь; крауд-контур (скан → баланс → остаток
  кампании); ETag-цикл справочника. Без запущенного сервера смоки честно
  печатают SKIPPED.

## 16.4 Честные границы текущего состояния

- Персистентность устройства: SQLDelight-схема написана
  (`outbox_event.sq`, `pending_asset.sq`, `directory_cache.sq`,
  `sync_state.sq`), но драйверы подключаются при сборке APK — до неё
  очереди и курсор живут в памяти процесса за теми же интерфейсами
  (`OutboxStore`, `MediaQueue`, `SyncStateStore`), эталонная семантика
  закреплена тестами: драйвер встанет, граф не изменится.
- Аутентификация: заголовки тенанта (контракт локальной сборки);
  поле bearer-токена в `SyncConfig` готово под промышленный OIDC (§07).
- Движок краудсорсинга на сервере in-memory на процесс; персистентность
  поверх `schema_crowd.sql` — при подключении managed PostgreSQL.

## 16.5 Данные, которые ждёт владелец реестра (Р-03 разд. 6)

Код готов их принять — нужен только контент; расширение справочника не
требует релиза. Открытые позиции:

| Справочник | Где | Что нужно |
|---|---|---|
| Ряд d1 колец | `series_directory.json` → `oring_d1_iso3601` | сейчас пуст: match_oring честно отвечает «d1 не сверялся» |
| Среды (`media_directory.json`) | файл-затравка есть | сверить перечень рабочих сред с реальными объектами |
| СИ (`si_directory.json`) | файл-затравка есть | реальный парк СИ с номерами и сроками поверок вместо примера |
| Бренды (`brand_directory.json`) | файл-затравка есть (+«БРЕНД НЕ ОПРЕДЕЛЁН») | полный список производителей заказчиков |
| Имена рядов (`std_directory.json`) | файл-затравка есть | сверить названия каталожных рядов с рабочими каталогами |
| Полный сортамент | `sortament_directory.json` | затравка из ходовых типоразмеров — полные таблицы ГОСТ |
| Полные ряды ГОСТ 6636 и модулей | `series_directory.json` | затравки 1-го ряда — полные при необходимости |
| Поставщики (`suppliers`) | динамический снапшот | наполняется сам из CRM поллером Bitrix — нужен только вебхук |

## 16.6 Что разблокирует инфраструктура владельца

| Появится | Первое действие |
|---|---|
| ANTHROPIC_API_KEY | живой прогон acceptance-экстрактора (вместо NullTransport) |
| Android build-машина | первый APK: SQLDelight-драйвер, ARCore на устройстве |
| Managed PostgreSQL | применить schema.sql + schema_ri.sql + schema_crowd.sql |
| Вебхук Bitrix24 | подставить URL в `connectors/bitrix_poller.py` — обе стороны уже обкатаны: поллер (опрос → inbound, курсор в файле, повторы не дублируют) и экспорт-воркер (UF-поля + комментарий с маркером) проверены против HTTP-эмулятора портала (`app/bitrix_emulator.py`) |
