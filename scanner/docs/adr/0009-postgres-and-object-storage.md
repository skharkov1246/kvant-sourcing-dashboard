# ADR-0009 · PostgreSQL + объектное хранилище

**Статус:** принято · **Дата:** 2026-07-28

## Контекст
Нужно хранить: структурированные сущности (задания, сессии, карточки, трассировка),
append-only лог событий, полуструктурированные полезные нагрузки шагов и
терабайты бинарного сырья.

## Решение
PostgreSQL для всего структурированного, включая лог событий (`session_event`) и
JSONB для payload шагов. Объектное хранилище (S3-совместимое) для бинарных
активов, с ключами вида `{tenant_id}/{yyyy}/{mm}/{session_id}/{asset_id}` и
доступом только через короткоживущие presigned URL.

## Последствия
- Одна транзакционная база — ссылочная целостность, RLS, честные транзакции.
- JSONB покрывает нерегулярные payload'ы шагов без схемы на каждую версию протокола.
- Объектное хранилище даёт дешёвые классы хранения и политики жизненного цикла.
- Эксплуатация проста: одна СУБД, известные инструменты, понятный бэкап.
- Цена: при большом объёме событий понадобится партиционирование `session_event`
  по времени и вынос холодных партиций. Это плановая работа, не сюрприз.

## Отвергнутые варианты
- **Документная БД (MongoDB и т.п.).** Гибкая схема выглядит удобной для
  разнородных payload'ов, но здесь нужны транзакции, ссылочная целостность и
  построчная изоляция тенантов — всё это в PostgreSQL сильнее.
- **Отдельная система для событий (Kafka как хранилище).** Kafka уместна как
  транспорт между сервисами, но не как источник истины, из которого web-консоль
  делает выборки с фильтрами.
- **Бинарные данные в БД (bytea/BLOB).** Транзакционно удобно, но раздувает базу,
  ломает бэкапы и лишает дешёвых классов хранения.
