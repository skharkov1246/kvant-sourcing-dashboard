# ADR-0010 · Python/FastAPI для бэкенда первой версии

**Статус:** принято · **Дата:** 2026-07-28

## Контекст
Бэкенд должен принимать события, раздавать протоколы и задания, обслуживать
чанковую загрузку медиа, оркестрировать анализаторы и говорить с внешними
системами. Отдельный вопрос — с чем он уже обязан состыковаться.

## Решение
Python 3.11 + FastAPI + SQLAlchemy для API и оркестрации. Тяжёлые анализаторы —
отдельные воркеры, язык которых выбирается по задаче (CV-конвейер на Python,
при необходимости нативные модули).

## Последствия
- **Прямое переиспользование существующего кода.** В репозитории уже работает
  `bitrix_client.py` с батчингом, троттлингом и ретраями под лимиты Bitrix24, и
  `company.py` со справочником контрагентов. Адаптер Bitrix24 — первый и опорный
  (§09); писать его заново на другом языке означало бы заново набивать те же шишки.
- Экосистема CV/ML в Python — родная среда для серверных анализаторов (§05).
- Одна команда и один набор инструментов на весь серверный периметр.
- Цена: на очень высокой нагрузке Python дороже по CPU, чем JVM или Go. Смягчается
  тем, что горячий путь (приём событий, выдача presigned URL) лёгкий, а тяжёлое
  вынесено в воркеры и масштабируется горизонтально. Точка расширения оставлена:
  контракт зафиксирован в OpenAPI, отдельный сервис можно переписать не трогая
  клиентов.

## Отвергнутые варианты
- **Kotlin/Ktor** — соблазн «один язык с мобильным ядром» и возможность разделить
  доменные модели с KMP. Но домен на клиенте и на сервере всё равно расходится
  (у сервера нет UI-состояний, у клиента нет мультитенантности), а интеграции с
  Bitrix пришлось бы писать заново. Выгода оказалась меньше стоимости.
- **Go** — лучший профиль по нагрузке и простой деплой, но CV/ML-экосистема слабее,
  и переиспользовать существующий код не получится.
- **Node.js/TypeScript** — общий язык с web-консолью, но работа с бинарными
  данными и CV-обвязкой хуже, чем в Python.
