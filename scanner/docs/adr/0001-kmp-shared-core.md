# ADR-0001 · Kotlin Multiplatform для общего ядра, нативный UI

**Статус:** принято · **Дата:** 2026-07-28

## Контекст
Нужны Android и iOS. Критичная часть функциональности — камера, ARCore/ARKit,
карты глубины, on-device ML — доступна только через платформенные API и
чувствительна к производительности: обработка кадров идёт в реальном времени.
Одновременно доменная логика (протокол съёмки, состояния сессии, outbox,
синхронизация, валидации) обязана вести себя **идентично** на обеих платформах:
расхождение здесь = расхождение данных.

## Решение
Kotlin Multiplatform для общего ядра: домен, интерпретатор протокола, проекция
сессии, outbox, sync-клиент, локальная БД (SQLDelight). UI и весь доступ к
камере/AR/ML — нативные: Compose + CameraX + ARCore на Android, SwiftUI +
AVFoundation + ARKit на iOS. Граница проходит по интерфейсам в ядре
(`MeasurementEngine`, `CameraController`, `CodeScanner`), реализуемым платформенно.

## Последствия
- Логика, которая обязана совпадать, физически одна. Тесты ядра пишутся один раз.
- Работа с сенсорами — без прослоек, полный доступ к нативным возможностям.
- Цена: два UI-слоя, iOS-разработчик обязан читать Kotlin, сборка сложнее
  однородного проекта.
- Требуется дисциплина границы: логика не должна протекать в UI-слои, иначе
  платформы разъедутся именно там.

## Отвергнутые варианты
- **Flutter.** Один UI дешевле, но доступ к ARCore/ARKit и потоку кадров — через
  плагины и platform channels. Обмер и on-device CV — ядро продукта; отдавать их
  в прослойку означает бороться с фреймворком там, где важнее всего точность.
- **React Native.** Те же проблемы плюс более слабая работа с бинарными данными
  (карты глубины, облака точек) через мост.
- **Полностью нативно, два приложения.** Максимум контроля, но логика синхронизации
  и интерпретации протокола пишется дважды и неизбежно разъезжается. Именно эта
  логика — источник самых дорогих багов (потеря данных).
