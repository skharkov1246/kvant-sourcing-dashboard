# ADR-0007 · Push — сигнал, а не транспорт данных

**Статус:** принято · **Дата:** 2026-07-28

## Контекст
Задания на сканирование должны «прилетать» на устройство как триггеры от складской
системы. Очевидное решение — слать содержимое задания в push-уведомлении.

## Решение
Push (FCM/APNs) содержит только `{"type": "sync_hint", "scopes": ["tasks"]}` —
сигнал «сходи в `/v1/sync/pull`». Данные задания едут по обычному защищённому
каналу синхронизации. Гарантию доставки даёт периодический pull (15 мин на
переднем плане, 1 ч в фоне), pull при появлении сети и ручное обновление.

## Последствия
- Потеря push не приводит ни к чему хуже задержки в 15 минут.
- Скомпрометированный push-токен не даёт доступа к данным заказчика.
- Формат задания не ограничен лимитом размера уведомления.
- Цена: задание доезжает не мгновенно, а за секунды-минуты. Для складской приёмки
  это приемлемо; для аварийного оповещения — нет, но такой задачи здесь нет.

## Отвергнутые варианты
- **Данные в push.** Ни FCM, ни APNs не гарантируют доставку; на Android с
  агрессивным энергосбережением (Xiaomi, Huawei, Oppo) потери массовые. Плюс это
  обход всех рубежей изоляции тенантов и утечка при компрометации токена.
- **Постоянное WebSocket-соединение.** Мгновенная доставка, но батарея, обрывы,
  переподключения и сложность на клиенте, который и так обязан уметь офлайн.
  Логика pull всё равно нужна — значит, WebSocket был бы вторым механизмом
  поверх первого.
