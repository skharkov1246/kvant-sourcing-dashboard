# ADR-0003 · Сценарий съёмки — данные с сервера, а не код приложения

**Статус:** принято · **Дата:** 2026-07-28

## Контекст
«Кладовщики должны следовать инструкциям приложения». Инструкции различаются по
категориям товара, по заказчикам и меняются часто — по опыту, несколько раз в
месяц на старте эксплуатации. Каждое изменение через релиз в сторах — это дни
ожидания ревью плюс недели на обновление парка устройств.

## Решение
`CaptureProtocol` — версионируемый подписанный JSON-документ: шаги, инструкции,
критерии качества, условная логика, критерии автоприёма. Приложение исполняет
восемь примитивов (photo, video, measure, code, form, weight, note, confirm) и
интерпретирует документ. Версия иммутабельна после публикации и пинуется в сессию
на старте. Условная логика — декларативная, без скриптов.

## Последствия
- Новый сценарий = работа технолога в web-консоли, не разработка.
- Изменения доезжают за минуты и работают офлайн (протокол лежит в локальной БД).
- Возможны тенант-специфичные протоколы без ветвления кода.
- Цена: нужен редактор протоколов, валидатор и строгая дисциплина совместимости
  (§3.7). Отладка «на месте» сложнее — нужен просмотрщик исполнения.
- Ограничение декларативной логики: редкие сложные сценарии придётся разбивать
  на два протокола. Принято сознательно — интерпретатор обязан быть
  верифицируемым и никогда не зависать.

## Отвергнутые варианты
- **Сценарии в коде приложения.** Каждое изменение — релиз. Через полгода
  накапливается ветвление `if (customer == "X")`, которое невозможно поддерживать.
- **Встроенный скриптовый движок (JS/Lua).** Максимум гибкости, но исполнение
  недоверенного кода на устройстве, непредсказуемая производительность и
  расхождение поведения между платформами.
- **WebView-формы.** Ломает нативную работу с камерой и офлайн-режим.
