# 10 · План реализации

## 10.1 Принцип нарезки

Этапы нарезаны так, чтобы **каждый заканчивался работающим на реальном складе
продуктом**, а не «готовым слоем». Слоёная нарезка («сначала бэкенд, потом
приложение») даёт первую обратную связь от кладовщика через полгода — то есть
поздно, чтобы что-то исправить дёшево.

## 10.2 Этапы

### Этап 0 · Каркас и решения — 2 недели

- Проектная документация (этот каталог), ADR, контракты API и протокола.
- Монорепозиторий, CI, схема БД, каркас KMP-ядра.
- Прогон 3–5 моделей телефонов на эталонных объектах → первый
  справочник `device_capability`.

**Готово, когда:** контракты зафиксированы, `device_capability` заполнен,
CI собирает пустое приложение на обеих платформах.

### Этап 1 · Тонкая вертикаль, Android — 5 недель

Одна категория товара, один протокол, одна площадка, 3–5 кладовщиков.

- Список заданий, гид по шагам, фото + проверки качества.
- Обмер: только классы C (маркер) и D (ручной). AR пока нет.
- Offline-first, outbox, чанковая загрузка.
- Бэкенд: задания, протоколы, события, медиа, карточка.
- Адаптер Bitrix24 на приём заданий.

**Готово, когда:** кладовщик проходит полный цикл на реальном складе, включая
работу без сети всю смену.

**Почему обмер начинается с класса C, а не с AR:** маркер работает на 100 %
устройств и даёт предсказуемую точность. Начав с AR, мы бы полгода отлаживали
разброс между вендорами Android и не узнали бы главного — как люди на самом деле
пользуются приложением.

### Этап 2 · Глубина обмера — 4 недели

- ARCore Depth (класс B): сегментация, облако точек, OBB, мультикадр.
- Сохранение сырья: карты глубины, интринсики, позы.
- Серверный конвейер: перекрёстная проверка вес↔объём, дедуп, оценка качества.
- Web-консоль контроля качества.

**Готово, когда:** доля обмеров класса B ≥ 60 % на сертифицированном парке,
расхождение с эталоном в пределах заявленного допуска.

### Этап 3 · iOS и мультитенантность — 5 недель

- iOS-приложение на общем KMP-ядре, ARKit + LiDAR (класс A).
- Тенанты, RLS, ABAC, внешние пользователи, гранты между тенантами.
- Внесение трассировки внешними сотрудниками (`declared`).
- Аудит, аттестация устройств.

**Готово, когда:** первый заказчик работает в своём тенанте, его данные
недоступны другим тенантам (подтверждено тестом изоляции и пентестом).

### Этап 4 · Трассировка и обратная связь — 4 недели

- Разбор GS1 и «Честного знака», сверка с ГИС МТ.
- Разрешение сущностей поставщиков, дедупликация.
- Обратная запись в Bitrix24 / WMS, состояние `EXPORTED`.
- Аналитика качества поставщиков, стык с существующим Sourcing Analyzer.

**Готово, когда:** по коду партии находятся все единицы товара, а качество
поставщиков видно в дашборде.

### Этап 5 · Промышленная эксплуатация — 4 недели

- Фотограмметрия и уточнение габаритов на сервере.
- Детекция повреждений, OCR шильдиков.
- Хаос-тесты, нагрузочный профиль «пересменка», отработка восстановления.
- Мониторинг, алерты, дежурство.

**Готово, когда:** SLO из §8.1 держатся месяц подряд без ручных вмешательств.

### Итого до промышленной эксплуатации: ~24 недели

## 10.3 Команда

| Роль | Загрузка | Основная зона |
|---|---|---|
| Архитектор / техлид | 0.5 FTE весь проект | Контракты, ревью, решения |
| Android-разработчик | 1.0 FTE, этапы 1–5 | Приложение, KMP-ядро |
| iOS-разработчик | 1.0 FTE, этапы 3–5 | iOS UI, ARKit |
| Backend-разработчик | 1.5 FTE весь проект | API, конвейер, интеграции |
| CV/ML-инженер | 0.5 FTE, этапы 2, 5 | Обмер, анализаторы |
| Frontend (web-консоль) | 0.5 FTE, этапы 2–4 | Контроль качества, протоколы |
| DevOps | 0.3 FTE весь проект | Инфраструктура, наблюдаемость |
| QA | 0.5 FTE с этапа 1 | Полевые и хаос-тесты |

Пиковая загрузка — 5.3 FTE на этапе 3.

## 10.4 Риски

| Риск | Вероятность | Влияние | Что делаем |
|---|---|---|---|
| Разброс точности Depth API между вендорами Android | Высокая | Высокое | Сертификация парка (§5.8), класс C как база, честный класс точности в данных |
| Кладовщики саботируют инструкции ради скорости | Высокая | Высокое | `warn` вместо `block` по умолчанию, серверный контроль качества, короткие протоколы, замер времени прохождения |
| Объёмы хранения растут быстрее прогноза | Средняя | Среднее | Политика жизненного цикла с первого дня, удаление видео через год, мониторинг ГБ/приёмка |
| Заказчик требует хранение данных у себя | Средняя | Высокое | Изоляция ключей по тенантам заложена сразу; экспорт в хранилище заказчика — точка расширения |
| Bitrix24 упирается в лимиты API | Средняя | Среднее | Батчинг и троттлинг уже в существующем клиенте, очередь экспорта с backoff |
| Утеря устройства с невыгруженным медиа | Средняя | Среднее | Приоритетная выгрузка фото, регламент сдачи смены онлайн |
| ГИС МТ недоступна | Средняя | Низкое | Проверка асинхронная, не блокирует приёмку |
| Растягивание объёма («ещё одна категория») | Высокая | Среднее | Протоколы съёмки настраиваются технологом — новая категория не является разработкой |

Первые два риска — главные, и оба не технические. Ответ на них заложен в
архитектуру (честный класс точности; мягкие проверки + серверный контроль), а не
оставлен на «потом договоримся».

## 10.5 Что даёт архитектура на длинной дистанции

| Изменение через год | Что придётся сделать |
|---|---|
| Новая категория товара со своим сценарием | Технолог собирает протокол в web-консоли. Разработки нет |
| Новое требование заказчика к съёмке | Новая версия протокола для его тенанта |
| Новый заказчик со своей WMS | Адаптер на сервере либо generic-контракт |
| Более точная модель обмера | Новый анализатор + пересчёт по архиву сырья |
| Новый тип кода маркировки | Парсер на сервере + запись в `symbologies` протокола |
| Новый сенсор в телефонах | **Релиз приложения** — единственный случай, когда он нужен |

Последняя строка и есть проверка качества проектирования: релиз мобильного
приложения зарезервирован только под новые аппаратные возможности.
