# Текущее состояние: что уже есть под раздел `/suppliers`

Замер 20.09.2026. Аудит: 14 направлений + 6 подпроектов вне манифеста, 84 агента,
каждый риск проверен отдельным скептиком на опровержение. Из 64 заявленных рисков
**13 опровергнуто**, 51 подтверждено (3 critical, 18 high, 27 medium, 3 low).

Всё ниже — с точной ссылкой. Где установить не удалось — сказано прямо.

## 1. Два независимых контура данных с противоположным поведением

Это главное, что определяет архитектуру раздела.

| | контур «база знаний» | контур «библиотека» |
|---|---|---|
| код | `base/*.py` | `library/*.py` |
| хранилище | SQLite `base/kvant.db` → CSV → PostgreSQL `kb_*` | PostgreSQL `lib_*` (Supabase) |
| режим записи | **уничтожающий** | **upsert** |
| DDL | `DROP TABLE IF EXISTS` на каждую из 12 таблиц (`base/export_kb.py:141`) | `create table if not exists` (`library/supabase/schema.sql`) |
| загрузка | применяет схему с DROP, затем `\copy` (`base/load_kb.py:55-60`) | `on conflict … do update` (`library/load_suppliers.py:235`, `load_parts.py:329`) |
| внутри SQLite | `DELETE FROM` по шести таблицам ядра (`base/build_db.py:65-66`); `file_cards`, `kb_catalog`, `suppliers`, `match_prices` роняют свои таблицы целиком | — |

**Вывод, обязательный к исполнению.** Ручная корректировка человека, положенная
в любую таблицу контура `base/`, исчезает при следующем прогоне безвозвратно.
Durable operational data раздела `/suppliers` обязана жить в контуре библиотеки
или рядом с ним. Исключение в библиотеке одно и оно осознанное: `lib_prices`
удаляет строки по ключу фида (`library/load_parts.py:444`, пояснение на :440).

Отдельно: сид `zip/supabase/seed_r1700.sql` удаляет строки пяти таблиц `mach_*`
по `machine_key` перед вставкой (`:1595`, `:1864`, `:1944`) — правки в них
теряются на каждом прогоне.

## 2. Одна база Supabase на всё, защита несовместимо разная

Проект один — `vpjliavuuxjcvtxbthlp`. Один секрет `SUPABASE_DB_URL` применяет
пять схем подряд (`.github/workflows/zip-db.yml:66-70`). В `public` живут
56 таблиц четырёх семейств плюс 12 `kb_*`.

| семейство | таблиц | защита |
|---|---:|---|
| `archive_*` | 21 | FORCE RLS, полный REVOKE, гранты только `service_role`, таблицы неизменяемы триггерами (`library/supabase/archive_schema.sql:541-574`) |
| `lib_*` | 20 (+2) | RLS включён, политик **нет** → только `service_role` (`schema.sql:506-508`). REVOKE для `lib_*` отсутствует |
| ЗИП / `mach_*` / `gt_notes` | 13+1 | `for all to anon using (true) with check (true)` — 13 таблиц (`zip/supabase/migrations.sql:79-85`, `:344-350`, `:417-419`; `gt/supabase/migrations.sql:40-42`) |
| `kb_*` | 12 | ни одного оператора RLS, policy или revoke (`base/supabase/kb_schema.sql`, grep → 0) |

`zip/supabase/migrations_rls.sql` — ужесточение — **не применяется ни одним
workflow**, файл целиком закомментирован, и причина записана в нём самом
(`:9-11`): сайт ЗИП писал в базу из браузера тем же ключом.

Публикуемый ключ и адрес проекта лежат открытым текстом в публичном репозитории:
`zip/site/_worker.js:63`. Из браузера ключ убран — страница ходит через прокси
`/db` того же origin (`zip/site/index.template.html:115-116`), и воркер
ограничивает прокси белым списком из восьми таблиц (`zip/site/_worker.js:73-83`),
куда `mach_*` и `lib_*` не входят. Но политики `anon` действуют в базе, а не в
воркере: ключ из репозитория даёт прямой доступ к 13 таблицам в обход портала.
Гейт ищет секреты, но шаблон не знает ключей Supabase
(`.github/workflows/gate.yml:168` — ни `sb_publishable_`, ни `sb_secret_`).

## 4. Подтверждённые дефекты, обесценивающие метрики поставщиков

**4.1. Выгрузка СП-166 забирала одну страницу из двадцати одной тысячи.**
`base/fetch_rfq.py:147` — `while not items:`. Условие проверяется перед каждым
проходом; после первой страницы `items` перестаёт быть пустым и цикл выходит.
Шапка модуля сама называет корпус: «21 193 записи». Измерено на придуманном
корпусе 127 карточек: прежний код давал **50**. Исправлено в этом изменении,
закрыто тремя тестами (`tests/test_rfq_pagination.py`). Когда сломалось — из
shallow-клона не установить.

**4.2. `days_med` — не срок ответа поставщика.** Это медиана календарных суток
между `createdTime` и `movedTime` карточки RFQ (`base/suppliers.py:111-117`),
то есть срок до последнего изменения стадии, которое двигает **наш** сотрудник.
Та же подмена в `metrics.py:23-27`. Приложение А ТЗ прямо запрещает считать
изменение стадии ответом поставщика.

**4.3. Поставщики агрегируются по текстовому названию.** `agg[sup.strip()]`,
`supplier TEXT PRIMARY KEY` (`base/suppliers.py:47`). При этом `rfq.supplier_id`
— Bitrix `companyId` — **уже есть в таблице** (`base/fetch_rfq.py:52`), просто не
попал в SELECT модуля. Стабильный ключ доступен; чинится дёшево.

**4.4. `brand_suppliers` зачитывает поставщику наш собственный исходящий файл.**
Джойн идёт без стороны документа (`base/suppliers.py:126-128`), поэтому в
доказательство «возит эту марку» попадает наш «Request file».

**4.5. `positions` и `file_cards` схлопывают дубликаты по `sha1` по РАЗНЫМ
правилам**, а джойн между ними идёт по `fid` — по выбранному представителю
(`base/extract_positions.py:434-439`). Три расхождения, каждого достаточно для
потери строк.

**4.6. Классификация стадий запроса построена на отображаемых названиях**
(`base/suppliers.py:30-34`), а в `rfq.stage` пишется человекочитаемое имя из
портала (`base/fetch_rfq.py:182`). Переименование стадии в Bitrix молча ломает
все пять разрядов.

**4.7. Шесть несовместимых правил нормализации артикула**, ни у одного нет
версии. Исправление кириллических двойников от 18.09.2026 доведено только до
`gt/tools` и `scripts`: в `base/` «917427С1» и «917427C1» до сих пор дают два
разных `pn_key`.

**4.8. `CAP_RATE = 0.20` — жёсткая константа** в заголовочном KPI «Потери от
просрочки» (`contracts.py:49`).

## 5. Инкрементальности нет нигде

Единственный фильтр — по дате **создания** (`DATE_CREATE` / `createdTime`).
`DATE_MODIFY` и `updatedTime` сохраняются в базу, но ни разу не используются в
фильтре. Курсоров и сравнения хешей нет; «инкремент» — это пагинация по
возрастанию id внутри одного прогона. Возобновляемость сделана таблицами-
отметками (`files.status`, `chat_done`, `act_done`).

## 6. Что из требуемого ТЗ есть, а чего нет

| факт | есть? | источник / чем проверено |
|---|---|---|
| RFQ отправлен | **частично** | только текущая стадия (`stages.py:30`). Отдельного timestamp отправки нет ни в одной таблице |

## 7. Что работает хорошо и подлежит переиспользованию

**7.1. Вход и права — настоящие, серверные.** Cloudflare Access, перепроверка
подписи JWT RS256 по ключам команды, из токена берутся `email`, `sub`, `exp`
(групп код не читает). Права — `access/acl.js`, копия вшита в `public/_worker.js`,
живут в KV под `acl:v1`. Чужие вкладки **вместе с массивами данных вырезаются из
HTML до отдачи** (`cutDashboard`) — это не сокрытие элементов, а серверная резка.
Есть журнал доступа (`audit()`), админка `/admin`, `/api/rights`, письмо
владельцу по пяти признакам.

Ограничение: гранулярность — сайт и вкладка. Скоупа по юрлицу, направлению или
строке данных нет. Роли по умолчанию в коде дают **всё всем**
(`access/acl.js:73-91`); живое состояние в KV из репозитория не видно.

**7.2. Образец архитектуры страницы уже есть** — `/library`:
браузер → `/api/library/v2/*` на воркере → KV-блобы. Ключей в браузере нет,
ACL проверяется на сервере, стоят лимиты ответа, `no-store`, `noindex`
(`public/library_v2.js`, `public/library.html`). Это готовый шаблон для
`/suppliers`.

**7.3. Модель доказательства выработана на живой заявке** (451 строка ТКП →
1 642 артикула ЛУКОЙЛ), `gt/docs/ЗАКУПКА-ЛУКОЙЛ-МЕТОД.md`:

- `verdict`: `pn_not_found` 782 · `oem_only` 340 · `pn_found_no_stock` 229 · `in_stock` 217 · `available_lead` 74
- `stock_grade`: `твёрдый` 93 · `частичный` 82 · `условный` 42
- `covers_qty`: `full` / `partial` / `no` / `unknown`
- основание адресата: `по этой детали` 856 · `кластер` 775 · нет 11
- `line_value_full_volume = unit_price × qty` **только если** `covers_qty == full`

Цена метода оплачена: прежний расчёт давал 1 212 346 USD, из них 1 024 659 —
строки с неподтверждённым объёмом. Правильных чисел **два и складывать их
нельзя**: 144 445 USD твёрдого склада и 190 972 USD подтверждённого объёма.

**7.4. Вечный внутренний номер уже спроектирован и работает** —
`pnw/НУМЕРАЦИЯ.md`: `KV-NNNNNN-C`, контрольная цифра Луна, 13 164 занято,
номер **не несёт смысла** (обоснование на четырёх наших же случаях: деталь на
нескольких машинах, ребрендинг Atlas Copco → Epiroc, смена заказчика,
переполнение сегментов), ревизия буквой при взаимозаменяемости, номера-спутники
шести типов (свой / бренд / изготовитель / поставщик / аналог / заказчика),
нормализация поиска до букв и цифр. Проверено: три пересборки, 13 164 из 13 164
сохранили номер.

**Противоречие, которое надо снять.** Этот регламент запрещает осмысленный ключ —
а поставщики в `pnw/data/supplier_master.json` ключуются слагом от сайта, а в
`lib_suppliers` — `norm(имя)`. То есть ровно та ошибка, от которой регламент
отговаривает, применена к поставщикам вместо деталей.

**7.5. Механика разбора файлов выучена на ошибках** — `library/indexer.py`:
отказ выносится по файлу, а не по строке; статус «пусто» строго для `chars == 0`;
сохраняется, ПОЧЕМУ получилось значение (`segment_rule`, `parse_path`,
`class_rule`); пометки живут в таблице-спутнике `lib_row_junk` с `run_id`, а не
колонкой основной таблицы. Это готовый образец слоя ручных корректировок.

## 8. Инженерная обвязка

Гейт `.github/workflows/gate.yml` — один job, 15 минут, сервис postgres:16,
11 шагов: ruff, компиляция всех `.py`, pytest, node-тесты доступов, `node --check`
шести воркеров, smoke-рендер с валидацией, актуальность каталога и указателя,
порог разметки узлов, неизменность бот-файлов, неудаление страниц ГТУ, поиск
секретов.

Деплой — семь независимых workflow, по одному проекту Cloudflare Pages, все с
`--branch=main`. **Staging и preview нет ни одного.** Версионируемых миграций
нет: SQL — идемпотентные файлы-схемы. Materialized view во всей схеме — ни одного.

Базовая линия на 20.09.2026: pytest зелёный, ruff чистый, каталог актуален
(256 наборов), указатель актуален (41 592 значения).

## 9. Маршрута `/suppliers` не существует

Ни в воркере, ни в `public/`. «Поставщики» — восьмая вкладка дашборда
(`id: "suppliers"`, `public/_worker.js:72`), своего URL у неё нет: переключение
вкладок чисто джаваскриптовое, без хеша и истории. Содержимое вкладки — список
поставщиков по обороту закупок из СП-172
(`templates/dashboard_core.html:1695-1702`), payload у неё общий с «Реализацией»
(`pay: ["CONTRACTS"]`), поэтому серверная резка не может отдать одну без другой.
