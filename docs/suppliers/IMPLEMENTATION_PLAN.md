## Этап 1. Канонический Supplier Master (25–40 ч)

1. **Сделано.** Таблицы `sup_entity`, `sup_identifier`, `sup_fact`, `sup_override`,
   `sup_review`, `sup_number_registry`, `our_entity` и представление
   `sup_effective` — `library/supabase/suppliers_schema.sql`. Защита по образцу
   `archive_*`: `FORCE RLS`, полный `REVOKE`, гранты только `service_role`.
   Применена на чистой базе, идемпотентна, закрыта восемью тестами
   (`tests/test_suppliers_schema_sql.py`). Автоматически ни одним workflow не
   применяется: сведение делается только после замера.
2. Выдача вечных номеров `KV-S-…` по алгоритму `pnw/tools/kv_number.py`, реестр
   по устойчивому ключу — номера не переиздаются.
3. Сведение шести реестров: Bitrix `companyId` → `lib_suppliers` → `pnw` →
   `dossiers` → `ship_sellers` → `supplier_crm`. Все совпадения — строками
   `sup_identifier`, ни одно имя не перезаписывается.
4. **Измерено 20.09.2026** — `scripts/supplier_registry_overlap.py`, пять файловых
   реестров (шестой, Bitrix, ждёт прогона владельца):

   | что | число |
   |---|---:|
   | строк во всех файловых реестрах | 3 874 |
   | разных нормализованных имён | 2 890 |
   | схлопнулось бы по имени | 984 |
   | досье ГТУ ∩ pnw по имени | 878 |
   | ship_sellers ∩ pnw по имени | 17 |
   | ship_sellers ∩ pnw **по домену** | **41** |
   | доменов с несколькими написаниями | 61 (144 написания) |
   | имён с разными доменами | 4 из 2 394 — 0,17 % |

   **Правило сведения выведено из этих чисел, а не придумано:**

   1. совпал домен → слияние, `evidence` = домен, `status` = `verified`;
   2. совпало имя и домены не противоречат → слияние, `status` = `inferred`;
   3. совпало имя, а домены разные → **не слияние**: строка в `sup_review`,
      `kind` = `ambiguous_match`. Таких 4;
   4. совпало только имя, домена нет ни у одной стороны → `status` = `candidate`,
      ждёт подтверждения человеком.

   Домен обязателен как основной признак: он находит 144 написания, которых
   сведение по имени не видит (`parkerhannifincorporation` и
   `parkerhannifingasturbine` — одна компания, один сайт). Обратная опасность
   мала, 0,17 %, но не нулевая, поэтому пункт 3 существует.

   **Самое слабое место — досье ГТУ:** 878 совпадений по имени и ни одного сайта
   во всём наборе, то есть проверить их доменом нечем. Это разряд `candidate`
   целиком, и он же самый крупный.
5. Холостой прогон обязателен; запись отменяется сама при непройденных гейтах
   (`CLAUDE.md`, правило 3).

**Готово, когда:** у каждого поставщика из шести реестров есть один `sup_id`,
пересечение измерено числом, а не на глаз, и повторный прогон не создаёт дублей.

## Этап 2. Раздел только на чтение (20–30 ч)

Маршрут `/suppliers` в `public/_worker.js` по образцу `/library`, страница без
данных, `/api/suppliers/*` с серверной фильтрацией по правам. Список, карточка,
хронология из `rfq` и `activities`.

Права `suppliers`, `suppliers_pii`, `suppliers_fin`, `suppliers_edit` в

**Готово, когда:** сотрудник открывает поставщика, видит историю запросов и
ответов, а человек без `suppliers_pii` не получает контакты ни через экран, ни
прямым обращением к API.

## Этап 3. Котировка как документ и артикулы (30–45 ч)

`sup_quote`, `sup_quote_line` с `doc_side`, оригинальным артикулом, валютой,
единицей и `price_basis`. Одно правило нормализации артикула **с версией**, вместо
шести нынешних; обратная совместимость проверяется на существующем корпусе.

Перенос трёх осей наличия целиком — `verdict`, `stock_grade`, `covers_qty` — с
датой проверки. Обе недостающие колонки заводятся сразу.

**Готово, когда:** строка с неизвестной валютой или базисом цены видна, но
исключена из сравнения с текстовой причиной; сумма по `covers_qty = full`
воспроизводит замер 144 445 USD.

## Этап 4. Рабочая таблица спецификации (25–40 ч)

Главный рабочий экран: вставка сотен артикулов из Excel, поиск по многим номерам
сразу, закреплённые заголовки и колонки, клавиатура, устойчивое выделение при
виртуализации, сортировка по всей выборке, возврат из карточки с сохранением
позиции, боковая панель с источником.

Образца в репозитории нет: `library.html` — это карточки, не таблица на сотни
строк. Делается заново.

**Готово, когда:** сотрудник вставляет 100+ номеров, работает клавиатурой,
уходит в карточку и возвращается без потери фильтров, прокрутки и выделения.

## Этап 5. Подбор адресатов с объяснением (20–30 ч)

Иерархия доказательств из ТЗ §8.2, наполненная нашим методом: exact PN →
verified manufacturer → машина/семейство → изготовитель узла → внутренние
исследования → внешний поиск. Уровни не смешиваются.

У каждого кандидата: почему попал, уровень доказательства, последнее событие,
числитель и знаменатель отзывчивости, что известно и чего не хватает.

**Готово, когда:** по строке заявки система называет адресатов, и по каждому
числу можно дойти до породившей записи.

## Этап 6. Условия, юрлица, очередь решений (30–50 ч)

`our_entity`, `sup_terms` с областью действия и сроком, очередь решений
руководителя. Заполняется, когда владелец назовёт список юрлиц; колонки
заложены раньше.

## Этап 7. Инкрементальное обновление (25–40 ч)

Сегодня инкрементальности нет нигде: фильтр только по дате создания,
`DATE_MODIFY` сохраняется, но не используется. Вводится фильтр по изменению, кеш
по хешу содержимого и версии правила, `run_id` в каждой записи, отчёт прогона:
получено / создано / обновлено / пропущено / ошибок / в проверку.

**Готово, когда:** повторный прогон даёт тот же результат, один битый документ
не роняет пакет, корректировка человека переживает обновление, а противоречие
попадает в очередь, а не выбирается молча.

## Этап 8. Карточки бренда, ODM-поставщика и трейдера (96–149 ч; с частью 8.9 — дата квотации и индексация)

Поставлен распоряжением владельца 23.09.2026, сверх оценки ТЗ: «Мне будут нужны
карточки, аналогичные карточке товара, но по брендам (какие агрегаты входят,
какие машины, применение), по ODM-поставщикам, предлагающим аналоги, и по
поставщикам-трейдерам, чтобы не терять всю информацию».

Образец — карточка товара `/nomenclature` (22.09.2026, `library/crossref.py`,
`public/nomenclature.html:415-520`). От неё берутся три правила: у каждого
утверждения подписан источник; четыре утверждения об изготовителе (каталог,
слово поставщика в файле, наша карточка запроса, «чей это номер на самом деле»)
не сводятся в одно поле; применимость по машине показывается с оговоркой, что
она не подтверждена.

**Место в цепочке.** Бренд стоит над звеньями «машина» и «узел»: по шильдику
сначала опознаётся бренд, от него — машины (`lib_models`, 132), узлы

коды закрывают — и через неё на «машину». В потоке сделки карточки работают на

адресата. Из вопросов ТЗ закрывают часть вопросов 7 («кто OEM и реальный

### Одна карточка компании с разделами по роли

ODM-поставщик и трейдер — не две сущности, а роли одной компании, и роль берётся
относительно бренда: одна компания бывает дилером по одной марке и трейдером по
другой. Поэтому «карточка ODM» и «карточка трейдера» — разделы карточки компании
на `/suppliers`, которые включаются фактом роли. К ним — два списка: «ODM-поставщики
аналогов» и «трейдеры», с фильтром по бренду и по статусу роли. Витрины одного
оператора (`gt/data/ship_seller_groups.json`: 14 групп и общий складской пул)
сводятся в одну сущность `sup_entity(kind='group')` с дочерними через
`parent_id` (8.4): иначе список трейдеров покажет одного оператора несколько раз.

Отдельные страницы отвергнуты по той же причине, по которой у номенклатуры один
снимок на две карточки: две сборки расходятся, и карточка ODM покажет котировку,
которой нет в карточке компании. У бренда свой объект, поэтому карточка бренда —
отдельная страница `/brands`.

### Не терять информацию

Каждый факт из КП и из файлов поставщика привязывается хотя бы к одной из двух
карточек — бренда или компании, лучше к обеим. Если компания не установлена,
факт остаётся у бренда с пометкой «поставщик не установлен». Если не установлен
бренд — у компании с пометкой «бренд не установлен». Факт, не привязанный ни к
одной карточке, не отбрасывается: он считается потерянным и виден числом в
счётчике.

Что теряется сейчас и что для этого дописать:

Правка разбора идёт обычным порядком: холостой прогон, сетка порогов за один
проход, запись только с ключом прогона. Кроме итога считается, у скольких файлов
стало хуже (правило 0), и такие файлы запись пропускает (`APPLY_ONLY_BETTER`).
Этап 3 тоже трогает разбор КП (одно правило нормализации артикула), поэтому
обе правки сводятся в один переразбор, а не в два подряд.

Новые поля — свойства строки котировки, и их место — `sup_quote_line`, которую
заводит этап 3. До неё они пишутся в `lib_prices`, а перенос `lib_prices` →
`sup_quote_line` в этапе 3 берёт их вместе с остальными полями. Двух моделей
одного и того же без ссылки друг на друга не заводится.

### Признак типа поставщика

**Словарь один.** Оба прежних словаря, 230 значений `lib_suppliers.kind` и уровни
`tier` со страниц машин ГТУ и из `gt/data/research_suppliers.json` отображаются в
него закрытой таблицей в коде. Незнакомое значение получает «не определена» и
считается числом, а не угадывается. Колонку `sup_entity.roles` не пишут и не
читают: роли компании — вид поверх `sup_effective` (`field='role'`).

| роль | что значит | относительно чего |
|---|---|---|
| `oem` | владелец конструкции, продаёт под своим брендом | бренда |
| `dealer` | авторизованный продавец OEM | бренда |
| `licensee` | производит машину или узел по лицензии владельца конструкции; в `zip/data/oem_atlas.json` 58 связей «лицензия или СП» | бренда |
| `component_maker` | реальный изготовитель узла под брендом OEM (`docs/ПЛАН-КП-И-ЗАПРОСОВ.md`, §1.9) | бренда и узла |
| `odm` | изготовитель аналога под своим или частным брендом | бренда, который замещает |
| `packager` | собирает агрегат из чужой машины и своей обвязки (пакет ГТУ) | машины |
| `distributor` | официальный канал изготовителя компонента | бренда изготовителя |
| `trader` | перепродаёт без авторизации: независимый склад, торговец | — |
| `marketplace` | площадка штучных лотов | — |
| `service` | ремонт и восстановление | — |
| `logistics` | перевозка и таможенное оформление | — |

Таблица соответствия прежних значений (закрытая, в коде):

| прежнее значение | роль |
|---|---|
| `oem` | `oem` |
| `authorized`, «дилер OEM» | `dealer` |
| `licensee` | `licensee` |
| `component_maker`, `oem_sub`, `component_specialist` | `component_maker` |
| `indep_proven_maker` | `odm` |
| `packager` | `packager` |
| `trader`, `surplus`, «независимый сток» | `trader` |
| `mro`, `indep_service` | `service` |
| `oem_or_user`, `unknown`, `other` | не определена |

`maker`, `aftermarket` и `indep_proven` соответствия пока не получают: одним словом
в разведке названы и изготовитель аналога, и продавец чужой детали. До замера в
8.3 они идут в «не определена», и их доля печатается отдельно.

**Роль — факт, а не колонка:** `sup_fact(subject_kind='entity', field='role',
value, scope={"brand": …}, status, source_type, method, method_ver, run_id)`.
Причин три: у роли есть источник и степень доказанности; роль у одной компании
разная по брендам; противоречие двух источников должно быть видно, а не
затираться правилом «первая запись навсегда», как сейчас у `lib_suppliers.kind`
(`library/load_suppliers.py:243`).

**Кто ставит и с каким статусом:**

- загрузчик из разведки или из файла самой компании — `stated`: это слово
  разведки или компании;
- вывод по поведению — `inferred`. Таможня (экспортёр не совпадает с брендом, у
  экспортёра много брендов, страна отправления отличается от страны
  происхождения) даёт `trader`. КП с `offer_kind='аналог'` под собственным брендом
  компании даёт `odm`. Реестр ODM идёт как `odm` со статусом `candidate`: в
  офлайн-копии у всех 4 309 строк статус «кандидат»; статус и уверенность
  (`confidence` → `sup_fact.confidence`) берутся из живой таблицы;
- человек с правом `suppliers_edit` — `verified`. Колонки `evidence` у `sup_fact`
  нет (`library/supabase/suppliers_schema.sql:95-117`): подтверждение пишется
  поправкой `sup_override` (`reason`, `evidence`, `approved_by`), и тогда
  `sup_effective` отдаёт `verified`; либо сам факт несёт доказательство в
  `source_id` / `source_span` и `verified_by`.

**Роль по бренду и слой поправок.** `sup_effective` сводит поправку с фактом по
`(subject_kind, subject_id, field)` без `scope`, а индекс `sup_override_one_active`
допускает одну действующую поправку на поле. Подтверждение роли по одному бренду
легло бы на все бренды компании. В 8.3 выбирается одно из двух: бренд входит в
имя поля (`field='role:<ключ бренда>'`) либо сравнение `scope` добавляется в вид
и в уникальный индекс — правкой схемы с прогоном «схема main, поверх неё новая».

**Чем подтверждается `verified`:**

- `dealer` — страница дилерской сети OEM или письмо OEM;
- `oem` и `component_maker` — собственный каталог с номерами или производственная
  площадка; для изготовителя узла — ребро `dict/chain.json` с `proof`;
- `odm` — каталог с кроссами на номера OEM и хотя бы одна наша котировка или
  образец;
- `trader` — умолчание для компании, давшей цену без подтверждения производства.
  По одному КП роль не ставится.

**Противоречие ролей — закрытым списком пар.** По одному бренду несовместимы
`dealer` и `trader`, `oem` и `odm`, `oem` и `trader`. Такая пара не разрешается
молча: она уходит строкой в `sup_review` с `kind='role_conflict'`. Новый вид
вписывается в список do-блока `sup_review_kind_check`
(`library/supabase/suppliers_schema.sql:180-187`), который пересоздаёт
ограничение при каждом применении схемы: отдельный `alter` этот блок снял бы
следующим же прогоном. Совместимые роли (`component_maker` и `service`, `trader`
и `service`) — набор ролей компании, а не противоречие. Роль со статусом
`candidate` в подборе адресатов (этап 5) веса не имеет.

**Роль компании и тип предложения — разные вещи.** Трейдер может предложить
оригинал, изготовитель узла — деталь под своим брендом. `offer_kind` лежит на
строке цены, роль — на компании, и по одной котировке одно из другого не
выводится.

**Родовой адрес и деталь.** «Компания работает с брендом» (роль, `oem_brands`,
досье) и «у компании есть эта деталь» (КП по коду, проверка наличия по коду) —
разные утверждения (`CLAUDE.md`, «Числа в выгрузках владельцу»;
`DATA_SOURCE_MAP.md`, строка «Адресат по детали»). В карточках это разные
таблицы. В заголовок, в счётчик и в сумму идёт только второе.

**Наличие — четыре состояния, а не одно:** подтверждённый остаток на весь объём
(`covers_qty='full'` с датой проверки); наличие без покрытия количества;
«отгрузим, если есть»; запись прошлой проверки, не перепроверенная сейчас. Отдельно
от них и друг от друга — два отказа: «номер не найден» и «только у OEM»
(`lib_part_suppliers.verdict`). В сумму закупки идёт только первое состояние.

### Публичность

Репозиторий публичный, а pull request'ы находятся поисковыми машинами по номеру
детали (`SECURITY.md`, замер 18.09.2026). Решение Р-1: данные поставщиков только
за входом, в git ничего.

- Имена поставщиков, цены, роли конкретных компаний, их бренды и коды хранятся
  только в Supabase и в снимках KV за Cloudflare Access с правом `suppliers`.
  Контакты режутся правом `suppliers_pii`, условия и деньги — `suppliers_fin`, на
  сервере (`PERMISSION_MATRIX.md`).
- Числа таможенных деклараций (`usd_kg`, стоимость, число поставок, число брендов
  у экспортёра) на страницы не идут, и вход этого не меняет: условия подписки
  glbs.io перепубликацию запрещают (`data/catalog_notes.json`, запись
  `zip/customs/out/`; комментарий перед `lib_customs` в
  `library/supabase/schema.sql`; `library/load_customs.py`). В карточке только
  выведенный факт роли `inferred` с подписью «таможенные декларации», без чисел.
  Показ чисел за входом — решение владельца (Р-8).
- В репозиторий, журналы Actions, описания PR и `STATE.md` попадают только
  агрегаты: счётчики, доли, названия сегментов, собственные константы кода
  (правило 17). Разбивка по брендам с числами спроса и цен — тоже только в
  снимке: имя бренда публично, а спрос по нему нет.
- Корпуса тестов придумываются (правило 18).
- Новых наборов с именами поставщиков в репозиторий этот этап не добавляет.
  Загрузка в базу уже лежащих файлов (`zip/data/odm_suppliers.json`,
  `gt/data/ship_sellers.json`) их публичности не меняет; решение по ним за
  владельцем (`SECURITY.md`).

### Части этапа

Каждая часть — отдельный PR с проверяемым результатом. Каждый прогон, который
обходит базу или вложения, принимает число частей входом (10, 25 или 50), и
разбиение в нём ровно одно (правило дробления). Прогоны записи 8.2, 8.3, 8.4, 8.6
и 8.8 по умолчанию идут вхолостую, пишут только по `APPLY=1`, сами отменяют
запись при непройденных гейтах и ставят `run_id` в каждую запись.

Счётчик на этап один — `scripts/card_coverage.py`. Он читает базу, как
`scripts/cross_ref_coverage.py`, а не файлы, как `gpu/tools/coverage.py`. По
каждой карточке и каждому полю он считает, у скольких сущностей поле заполнено,
долю и статус: «закрыто» от 80 %, «частично» от 40 %, ниже — «дыра». Отдельно —
сколько фактов не привязано ни к бренду, ни к компании. Точки пишутся в
`lib_metric_runs` (образец записи — `scripts/codes_with_prices.py` с `WRITE=1`) и
показываются на `/counters` через `scripts/publish_counters.py` (`counters:v1`).
В журнал идут только агрегаты.

**8.1. Срез на имеющихся данных, без записи в базу (14–20 ч).** Карточка бренда
`/brands`: чистая сборка `library/brands.py`, публикатор `scripts/publish_brands.py`

отвергнуты отдельные страницы ODM. Новое расписание — только с согласия

из `OEM_JUNK` исключаются и считаются: по файлам выгрузки 23.09.2026 такой бренд
у 13 697 строк из 42 311 (из них «ОТСУТСТВУЕТ» — 12 139), бренд пуст ещё у 3 816.
Признаки: экспортёр не совпадает с брендом, число брендов у экспортёра, страна
отправления отличается от страны происхождения. Порог выбирается по сетке,
посчитанной за один проход (правило 4). Факты ставятся только со статусом
`inferred`. Экспортёры уже лежат в `lib_suppliers` с `kind='экспортёр'`
(`library/load_customs.py`) и связываются с `sup_entity` по правилу 8.4. На
страницу идёт только факт роли с подписью «таможенные декларации», без чисел
(раздел «Публичность»).
**Готово, когда:** сетка порогов напечатана таблицей; при выбранном пороге
измерены число экспортёров-трейдеров и доля, связанная с реестром; рядом сказано,
что охват — семь групп ТН ВЭД (8207, 8411, 8412, 8431, 8466, 8467, 8481) за
2023–2025, а не весь ввоз по бренду.

**8.9. Дата квотации и индексация на инфляцию (8–12 ч; основа сделана 24.09.2026).**
Распоряжение владельца 24.09.2026: «Важно иметь в виду месяц и год получения
квотации, чтобы индексировать их на инфляцию в конкретно выбранной стране». До
этого `lib_prices.price_date` у потока «разбор КП» не писался вовсе: 34 тыс. строк
цены КП без даты, а карточка номенклатуры показывала вместо даты предложения дату
разбора — цена двухлетней давности выглядела вчерашней.

*Дата квотации — с источником* (`price_date`, `price_date_src`, правило 16).
Источники по убыванию надёжности (`library/quote_date.py`):

| источник | откуда | точность |
|---|---|---|
| `документ` | дата в самом КП: «КП № 15 от 12.03.2025», «Дата:», «Quotation date:», «Исх. № … от» | день |
| `письмо` | дата письма .eml/.msg: сырой заголовок `Date:` (разбор без каскада) или строка читателя писем (с каскадом) | день прихода предложения |
| `карточка: создана` | `createdTime` карточки запроса СП-166 | нижняя граница: предложение приходит после запроса, обычно в пределах недель |
| `нет` | искали в тексте и на карточке — не нашли | — |

Даты загрузки файла среди источников нет, и это измерено: файловое поле CRM
отдаёт только `id` (файл CRM, «на Диске такого объекта нет»), `url` и
`urlMachine` — ни даты, ни автора (документация REST Битрикс24, скачивание файла
из поля элемента). `updatedTime` карточки меняется от любой правки, поэтому
датой файла не считается. Дата разбора не пишется никогда.

Извлечение принимает дату только закрытым списком подписей и отвергает дату с
чужим смыслом слева («действительно до», «срок поставки», «договор», «ГОСТ»,
«ваш запрос»), неоднозначную «03/04/2025», будущую и старше карточки больше
чем на два года. Разбор, распознавание скана (оба пути) и ежедневный проход
ставят дату одним правилом (`quote_date.проставить`, правило 14); колонка
источника в `price_store` необязательная — до миграции цены пишутся без неё, и
ночной разбор не падает.

*Досчёт для уже записанных строк* — `library/quote_dates_backfill.py`, прогон
«Библиотека — досчёт дат квотаций» (`library-quote-dates.yml`): дата карточки по
`rfq_id`, только в пустую `price_date`, с ключом `price_date_run`, по частям
(вход `shards`), вхолостую по умолчанию, откат `rollback=qd-…`. Нагрузка на
портал — номера пачками по 50 (`crm.item.list`, `@id`, `start=-1`): тысячи
карточек — десятки запросов. Дата документа у этих строк придёт с общим
переразбором 8.5 (`PARSER_VERSION` поднимается там, а не здесь: иначе два
переразбора подряд).

*Индексы цен по стране и месяцу* — `lib_cpi` (страна ISO alpha-3, месяц,
индекс, базовый период, источник, валюта страны, дата загрузки, `run_id` и
прежнее значение для отката). Источник — МВФ, набор CPI, SDMX 2.1 без ключа
(`https://api.imf.org/external/sdmx/2.1/data/CPI/.CPI._T.IX.M`): 190 стран
одним запросом, около 25 тыс. точек с 2015 года, у стран ЕС внутри — HICP
Евростата. Проверено 24.09.2026: OECD по России пуст (ряды остановлены в 2022),
ЕЦБ — только Европа, Всемирный банк — только годовые. Загрузчик
`library/load_cpi.py`, прогон «Библиотека — индексы цен по странам (МВФ)»
(`library-cpi.yml`), вхолостую по умолчанию, раз в месяц. База ряда у стран
разная (Россия 2010, Китай 2020, Италия и Турция 2025), поэтому
`lib_cpi_factor(страна, с, по)` делит только внутри одной базы и иначе
возвращает пусто. `lib_prices_indexed(месяц, страна)` отдаёт цену, приведённую к
месяцу, и оговорку у каждой строки.

*Оговорки, которые идут на страницу вместе с числом* (CLAUDE.md, «Числа в
выгрузках владельцу»): приведённая цена — расчёт, а не цена поставщика, и в
заголовок не идёт; валюта не пересчитывается — цена в евро, приведённая по
инфляции России, помечается «валюта цены не совпадает с валютой страны —
приведение без смысла» (пересчёт курса — отдельный вопрос: курсы ЦБ по дате
квотации, `lib_fx`, не заведены); индекс потребительский, а не цен
производителей — для промышленных деталей это приближение; месяц по дате
карточки помечается как нижняя граница.

*Страница `/brands` (и `/nomenclature`)*: у каждой цены — месяц и год квотации и
пометка источника (документ / письмо / карточка / нет) в том же виде, что пометки
базиса и оплаты («б|о|с|и» → добавляется «д»). Следующий шаг — переключатель
«привести к месяцу [ММ.ГГГГ] по инфляции страны [страна]»: по умолчанию выключен,
страна по умолчанию — страна валюты цены; приведённое значение стоит рядом с
исходным, с оговоркой, а не вместо него. Индексы в снимок страницы не кладутся
целиком: только множители нужных пар «страна × месяц».

**Готово, когда:** доля строк цены КП по источнику даты напечатана
(документ / письмо / карточка / нет); после досчёта строк без даты — только те, у
чьих карточек портал даты не отдал, и их число названо; `lib_cpi` загружена, и
последний месяц России, Китая и Германии не старше трёх месяцев; у каждой цены на
`/nomenclature` и `/brands` видны месяц и год квотации с источником.
