# План реализации

Оценка ТЗ — 300–500 часов. Разбито так, чтобы каждый этап давал работающий
вертикальный срез, а не слой, который нельзя проверить.

## Этап 0. Починка того, что обесценивает данные (сделано частично)

Дёшево, обратимо, разблокирует всё остальное.

| # | что | статус | цена |
|---|---|---|---|
| 0.1 | пагинация СП-166: `while not items` → полный проход | **сделано**, 3 теста | 1 ч |
| 0.2 | ключ поставщика — `rfq.supplier_id` вместо текста названия | не начато | 4 ч |
| 0.3 | сторона документа в джойне `brand_suppliers` — не зачитывать наш «Request file» | не начато | 2 ч |
| 0.4 | классификация стадий по `stageId`, а не по отображаемому имени | не начато | 3 ч |
| 0.5 | `days_med` переименовать в `days_to_stage_move` и убрать из вида «срок ответа» | не начато | 1 ч |
| 0.6 | гейт учит шаблоны ключей Supabase (`sb_publishable_`, `sb_secret_`) | не начато | 1 ч |
| 0.7 | кириллические двойники в `base/` — довести исправление от 18.09 | не начато | 2 ч |

ею пользуются как сроком ответа поставщика. Переименование честнее, чем сноска.

## Этап 1. Канонический Supplier Master (25–40 ч)

1. Таблицы `sup_entity`, `sup_identifier`, `sup_fact`, `sup_override`, `sup_review`.
   Защита по образцу `archive_*`: `FORCE RLS`, `REVOKE`, гранты только `service_role`.
2. Выдача вечных номеров `KV-S-…` по алгоритму `pnw/tools/kv_number.py`, реестр
   по устойчивому ключу — номера не переиздаются.
3. Сведение шести реестров: Bitrix `companyId` → `lib_suppliers` → `pnw` →
   `dossiers` → `ship_sellers` → `supplier_crm`. Все совпадения — строками
   `sup_identifier`, ни одно имя не перезаписывается.
4. **Измерить, а не оценить:** сколько сущностей получилось, сколько кандидатов,
   какое пересечение реестров. Счётчик по образцу `gpu/tools/coverage.py`.
5. Холостой прогон обязателен; запись отменяется сама при непройденных гейтах
   (`CLAUDE.md`, правило 3).

**Готово, когда:** у каждого поставщика из шести реестров есть один `sup_id`,
пересечение измерено числом, а не на глаз, и повторный прогон не создаёт дублей.

## Этап 2. Раздел только на чтение (20–30 ч)

Маршрут `/suppliers` в `public/_worker.js` по образцу `/library`, страница без
данных, `/api/suppliers/*` с серверной фильтрацией по правам. Список, карточка,
хронология из `rfq` и `activities`.

Права `suppliers`, `suppliers_pii`, `suppliers_fin`, `suppliers_edit` в
`access/acl.js` — с тестами в `access/test/`.

**Готово, когда:** сотрудник открывает поставщика, видит историю запросов и
ответов, а человек без `suppliers_pii` не получает контакты ни через экран, ни
прямым обращением к API.

## Этап 3. Котировка как документ и артикулы (30–45 ч)

`sup_quote`, `sup_quote_line` с `doc_side`, оригинальным артикулом, валютой,
единицей и `price_basis`. Одно правило нормализации артикула **с версией**, вместо
шести нынешних; обратная совместимость проверяется на существующем корпусе.

Перенос трёх осей наличия целиком — `verdict`, `stock_grade`, `covers_qty` — с
датой проверки. Обе недостающие колонки заводятся сразу.

**Готово, когда:** строка с неизвестной валютой или базисом цены видна, но
исключена из сравнения с текстовой причиной; сумма по `covers_qty = full`
воспроизводит замер 144 445 USD.

## Этап 4. Рабочая таблица спецификации (25–40 ч)

Главный рабочий экран: вставка сотен артикулов из Excel, поиск по многим номерам
сразу, закреплённые заголовки и колонки, клавиатура, устойчивое выделение при
виртуализации, сортировка по всей выборке, возврат из карточки с сохранением
позиции, боковая панель с источником.

Образца в репозитории нет: `library.html` — это карточки, не таблица на сотни
строк. Делается заново.

**Готово, когда:** сотрудник вставляет 100+ номеров, работает клавиатурой,
уходит в карточку и возвращается без потери фильтров, прокрутки и выделения.

## Этап 5. Подбор адресатов с объяснением (20–30 ч)

Иерархия доказательств из ТЗ §8.2, наполненная нашим методом: exact PN →
verified manufacturer → машина/семейство → изготовитель узла → внутренние
исследования → внешний поиск. Уровни не смешиваются.

У каждого кандидата: почему попал, уровень доказательства, последнее событие,
числитель и знаменатель отзывчивости, что известно и чего не хватает.

**Готово, когда:** по строке заявки система называет адресатов, и по каждому
числу можно дойти до породившей записи.

## Этап 6. Условия, юрлица, очередь решений (30–50 ч)

`our_entity`, `sup_terms` с областью действия и сроком, очередь решений
руководителя. Заполняется, когда владелец назовёт список юрлиц; колонки
заложены раньше.

## Этап 7. Инкрементальное обновление (25–40 ч)

Сегодня инкрементальности нет нигде: фильтр только по дате создания,
`DATE_MODIFY` сохраняется, но не используется. Вводится фильтр по изменению, кеш
по хешу содержимого и версии правила, `run_id` в каждой записи, отчёт прогона:
получено / создано / обновлено / пропущено / ошибок / в проверку.

**Готово, когда:** повторный прогон даёт тот же результат, один битый документ
не роняет пакет, корректировка человека переживает обновление, а противоречие
попадает в очередь, а не выбирается молча.

## Порядок и зависимости

```
0 ──▶ 1 ──▶ 2 ──▶ 3 ──▶ 4
             │      └──▶ 5
             └──▶ 6
      1 ──────────▶ 7
```

Этап 0 — до всего: без него считается корпус из пятидесяти карточек.
Этапы 4 и 5 идут после 3: без модели котировки таблице нечего показывать.
Этап 7 можно вести параллельно с 4–5.

## Риски

| риск | вероятность | что делаем |
|---|---|---|
| сведение реестров даёт много кандидатов и мало слияний | высокая | это нормально: кандидат лучше ошибочного слияния. Меряем числом, порог не подкручиваем задним числом |
| правило нормализации артикула ломает существующие связи | средняя | обратная совместимость проверяется на корпусе до включения; старый ключ хранится рядом |
| нет staging — правка едет сразу в прод | высокая | раздел за флагом до этапа 2; каждый мерж — деплой (`CLAUDE.md`, правило 2) |
| данные ЛУКОЙЛ окажутся единственным корпусом с тремя осями наличия | высокая | так и есть: 1 642 артикула из одной заявки. Не выдавать за общую статистику |
| владелец не назовёт юрлица | средняя | колонки заложены, интерфейс не показывает разрез до наполнения |

## Чего в плане намеренно нет

Платежи, фактические поставки, качество, рекламации. Источника нет, схему под
них заводим вместе с первым источником — пустая таблица выглядит фактом.
