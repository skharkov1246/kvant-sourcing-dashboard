## Этап 1. Канонический Supplier Master (25–40 ч)

1. **Сделано.** Таблицы `sup_entity`, `sup_identifier`, `sup_fact`, `sup_override`,
   `sup_review`, `sup_number_registry`, `our_entity` и представление
   `sup_effective` — `library/supabase/suppliers_schema.sql`. Защита по образцу
   `archive_*`: `FORCE RLS`, полный `REVOKE`, гранты только `service_role`.
   Применена на чистой базе, идемпотентна, закрыта восемью тестами
   (`tests/test_suppliers_schema_sql.py`). Автоматически ни одним workflow не
   применяется: сведение делается только после замера.
2. Выдача вечных номеров `KV-S-…` по алгоритму `pnw/tools/kv_number.py`, реестр
   по устойчивому ключу — номера не переиздаются.
3. Сведение шести реестров: Bitrix `companyId` → `lib_suppliers` → `pnw` →
   `dossiers` → `ship_sellers` → `supplier_crm`. Все совпадения — строками
   `sup_identifier`, ни одно имя не перезаписывается.
4. **Измерено 20.09.2026** — `scripts/supplier_registry_overlap.py`, пять файловых
   реестров (шестой, Bitrix, ждёт прогона владельца):

   | что | число |
   |---|---:|
   | строк во всех файловых реестрах | 3 874 |
   | разных нормализованных имён | 2 890 |
   | схлопнулось бы по имени | 984 |
   | досье ГТУ ∩ pnw по имени | 878 |
   | ship_sellers ∩ pnw по имени | 17 |
   | ship_sellers ∩ pnw **по домену** | **41** |
   | доменов с несколькими написаниями | 61 (144 написания) |
   | имён с разными доменами | 4 из 2 394 — 0,17 % |

   **Правило сведения выведено из этих чисел, а не придумано:**

   1. совпал домен → слияние, `evidence` = домен, `status` = `verified`;
   2. совпало имя и домены не противоречат → слияние, `status` = `inferred`;
   3. совпало имя, а домены разные → **не слияние**: строка в `sup_review`,
      `kind` = `ambiguous_match`. Таких 4;
   4. совпало только имя, домена нет ни у одной стороны → `status` = `candidate`,
      ждёт подтверждения человеком.

   Домен обязателен как основной признак: он находит 144 написания, которых
   сведение по имени не видит (`parkerhannifincorporation` и
   `parkerhannifingasturbine` — одна компания, один сайт). Обратная опасность
   мала, 0,17 %, но не нулевая, поэтому пункт 3 существует.

   **Самое слабое место — досье ГТУ:** 878 совпадений по имени и ни одного сайта
   во всём наборе, то есть проверить их доменом нечем. Это разряд `candidate`
   целиком, и он же самый крупный.
5. Холостой прогон обязателен; запись отменяется сама при непройденных гейтах
   (`CLAUDE.md`, правило 3).

**Готово, когда:** у каждого поставщика из шести реестров есть один `sup_id`,
пересечение измерено числом, а не на глаз, и повторный прогон не создаёт дублей.

## Этап 2. Раздел только на чтение (20–30 ч)

Маршрут `/suppliers` в `public/_worker.js` по образцу `/library`, страница без
данных, `/api/suppliers/*` с серверной фильтрацией по правам. Список, карточка,
хронология из `rfq` и `activities`.

Права `suppliers`, `suppliers_pii`, `suppliers_fin`, `suppliers_edit` в
`access/acl.js` — с тестами в `access/test/`.

**Готово, когда:** сотрудник открывает поставщика, видит историю запросов и
ответов, а человек без `suppliers_pii` не получает контакты ни через экран, ни
прямым обращением к API.

## Этап 3. Котировка как документ и артикулы (30–45 ч)

`sup_quote`, `sup_quote_line` с `doc_side`, оригинальным артикулом, валютой,
единицей и `price_basis`. Одно правило нормализации артикула **с версией**, вместо
шести нынешних; обратная совместимость проверяется на существующем корпусе.

Перенос трёх осей наличия целиком — `verdict`, `stock_grade`, `covers_qty` — с
датой проверки. Обе недостающие колонки заводятся сразу.

**Готово, когда:** строка с неизвестной валютой или базисом цены видна, но
исключена из сравнения с текстовой причиной; сумма по `covers_qty = full`
воспроизводит замер 144 445 USD.

## Этап 4. Рабочая таблица спецификации (25–40 ч)

Главный рабочий экран: вставка сотен артикулов из Excel, поиск по многим номерам
сразу, закреплённые заголовки и колонки, клавиатура, устойчивое выделение при
виртуализации, сортировка по всей выборке, возврат из карточки с сохранением
позиции, боковая панель с источником.

Образца в репозитории нет: `library.html` — это карточки, не таблица на сотни
строк. Делается заново.

**Готово, когда:** сотрудник вставляет 100+ номеров, работает клавиатурой,
уходит в карточку и возвращается без потери фильтров, прокрутки и выделения.

## Этап 5. Подбор адресатов с объяснением (20–30 ч)

Иерархия доказательств из ТЗ §8.2, наполненная нашим методом: exact PN →
verified manufacturer → машина/семейство → изготовитель узла → внутренние
исследования → внешний поиск. Уровни не смешиваются.

У каждого кандидата: почему попал, уровень доказательства, последнее событие,
числитель и знаменатель отзывчивости, что известно и чего не хватает.

**Готово, когда:** по строке заявки система называет адресатов, и по каждому
числу можно дойти до породившей записи.

## Этап 6. Условия, юрлица, очередь решений (30–50 ч)

`our_entity`, `sup_terms` с областью действия и сроком, очередь решений
руководителя. Заполняется, когда владелец назовёт список юрлиц; колонки
заложены раньше.

## Этап 7. Инкрементальное обновление (25–40 ч)

Сегодня инкрементальности нет нигде: фильтр только по дате создания,
`DATE_MODIFY` сохраняется, но не используется. Вводится фильтр по изменению, кеш
по хешу содержимого и версии правила, `run_id` в каждой записи, отчёт прогона:
получено / создано / обновлено / пропущено / ошибок / в проверку.

**Готово, когда:** повторный прогон даёт тот же результат, один битый документ
не роняет пакет, корректировка человека переживает обновление, а противоречие
попадает в очередь, а не выбирается молча.

## Порядок и зависимости

```
0 ──▶ 1 ──▶ 2 ──▶ 3 ──▶ 4
             │      └──▶ 5
             └──▶ 6
      1 ──────────▶ 7
```

Этап 0 — до всего: без него считается корпус из пятидесяти карточек.
Этапы 4 и 5 идут после 3: без модели котировки таблице нечего показывать.
Этап 7 можно вести параллельно с 4–5.

## Риски

| риск | вероятность | что делаем |
|---|---|---|
| сведение реестров даёт много кандидатов и мало слияний | высокая | это нормально: кандидат лучше ошибочного слияния. Меряем числом, порог не подкручиваем задним числом |
| правило нормализации артикула ломает существующие связи | средняя | обратная совместимость проверяется на корпусе до включения; старый ключ хранится рядом |
| нет staging — правка едет сразу в прод | высокая | раздел за флагом до этапа 2; каждый мерж — деплой (`CLAUDE.md`, правило 2) |
| данные ЛУКОЙЛ окажутся единственным корпусом с тремя осями наличия | высокая | так и есть: 1 642 артикула из одной заявки. Не выдавать за общую статистику |
| владелец не назовёт юрлица | средняя | колонки заложены, интерфейс не показывает разрез до наполнения |

## Чего в плане намеренно нет

Платежи, фактические поставки, качество, рекламации. Источника нет, схему под
них заводим вместе с первым источником — пустая таблица выглядит фактом.

## Блокер по пункту 0.2: нечем измерить

Перевод ключа поставщика с текста названия на `rfq.supplier_id` написать можно,
проверить — нельзя. `base/kvant.db` в репозиторий не коммитится
(`.gitignore:41-42`), а эффект перевода целиком зависит от данных:

- сколько карточек СП-166 имеют `supplier_id = 0` (поле пустое) — они схлопнутся
  в одну корзину, если не задать обратный ход на нормализованное имя;
- сколько написаний названия приходится на один `companyId` — от этого зависит,
  во сколько раз сократится число «поставщиков»;
- какое написание брать канонически для отображения.

При этом ключ читают ещё три таблицы, которых перевод коснётся:
`base/quote.py:58` джойнит `supplier_stats` к `supplier_prices` по тексту имени,
`:67` — к `brand_suppliers`, и обе построены `match_prices.py` и `file_cards.py`
из своих текстовых колонок. Перевод одной таблицы без остальных разорвёт джойн:
вариантное написание перестанет находиться вовсе, а сегодня оно находит хотя бы
расщеплённую строку.

`CLAUDE.md`, правило 3: правило сначала меряют, потом применяют; калибровка на
придуманном корпусе показывает верхнюю границу качества, а не рабочую. Поэтому
0.2 переносится в этап 1, где сведение реестров делается один раз, с замером
и таблицей соответствий имён, а не двумя несогласованными правками.

**Разблокировано 20.09.2026:** замер написан — `scripts/supplier_merge_stats.py`,
запускается кнопкой (Actions → «Поставщики — замер сведения») и читает выгрузку
`kb_rfq` в Supabase, поэтому локальная база не нужна. Ждёт запуска владельцем.
Он отвечает ровно на четыре вопроса этого раздела и печатает только агрегаты.

Прежние варианты разблокировки:
1. прогон `base/suppliers.py` на живой базе с холостым замером — сколько
   сущностей до и после, сколько карточек без `supplier_id`, распределение
   написаний на один `companyId`;
2. либо сразу этап 1: таблица `sup_identifier` как единственное место сведения,
   и все четыре таблицы `base/` смотрят в неё, а не друг на друга.

## Блокер по пункту 0.6: гейт покраснеет на нашем же ключе

Научить гейт шаблонам `sb_publishable_` и `sb_secret_` нельзя, пока публикуемый
ключ лежит в рабочем дереве: `zip/site/_worker.js:63`. Добавленный шаблон найдёт
его первым же прогоном и покрасит гейт на КАЖДОМ pull request, включая чужие.

Обходить исключением на эту строку — плохо: исключение переживёт удаление ключа и
перестанет защищать ровно то место, где он был.

Правильный порядок — тот же, что у ужесточения доступа к базе ЗИП, и первые два
шага общие:

1. задать `SUPABASE_SERVICE_KEY` в Cloudflare для проекта `kvant-zip`;
2. убедиться, что сайт ЗИП работает (воркер пойдёт сервисной ролью);
3. убрать `SUPA_FALLBACK_KEY` из `zip/site/_worker.js`;
4. **только теперь** добавить шаблоны в гейт — ему больше нечего находить.

Готовность к шагам 1–3 меряется `scripts/zip_rls_readiness.py`.

## Пункт 0.4: сделано второе лучшее, а не заявленное

Опознавать стадии по `stageId` вместо отображаемого имени нельзя: коды воронок
смарт-процесса задаются в портале (вида `DT166_16:UC_XXXXX`) и из репозитория
неизвестны. Поэтому сделано то, что закрывает саму опасность: неопознанная
стадия теперь СЧИТАЕТСЯ и попадает в сводку прогона числом и списком имён, а не
проваливается молча. Плюс заработал разряд `LOST` — он был объявлен и не
использовался, из-за чего карточка «выбрали не его» была неотличима от карточки
с переименованной стадией.

Чтобы закрыть пункт целиком, нужен список стадий из портала: его отдаёт
`crm.status.list` для `DYNAMIC_166_STAGE*` (уже вызывается в
`base/fetch_rfq.py:103`). Достаточно сохранить `stageId` рядом с именем в разряды
— один прогон с сетью.
