# Целевая архитектура раздела `/suppliers`

Решения владельца от 20.09.2026 зафиксированы в `DECISIONS.md` и заложены здесь.

## Главный принцип: не второй продукт, а раздел портала

`/suppliers` встраивается ровно так же, как уже встроен `/library`, и по тому же
образцу — он в репозитории проверен и работает:

```
браузер  ──(Cf-Access-Jwt-Assertion)──▶  public/_worker.js
                                          │ verify JWT (RS256, ключи команды)
                                          │ rightsFor(acl, email)   ← KV acl:v1
                                          │ audit(env, …)           ← журнал доступа
                                          ├─▶ /suppliers            страница (HTML, без данных)
                                          └─▶ /api/suppliers/*      данные, отфильтрованные по правам
                                                       │
                                                       ├─▶ KV-блобы (read-модель, как library:v2)
                                                       └─▶ Supabase service_key (живые срезы)
```

Чего здесь нет намеренно: ключей в браузере, прямого обращения из страницы к
Supabase, клиентской фильтрации по правам.

**Почему не отдельный проект Pages.** Восьмой проект — восьмой деплой, восьмой
набор секретов и восьмая копия блока прав. `access/acl.js` уже канонический и
сверяется тестами; раздел портала получает права даром.

**Почему не вкладка дашборда.** Вкладка не имеет URL (переключение чисто
джаваскриптовое), а её payload общий с «Реализацией» (`pay: ["CONTRACTS"]`) —
серверная резка не может отдать одну без другой. Рабочая таблица спецификации на
сотни строк требует ссылки, на которую можно вернуться, и своего среза прав.

Существующая вкладка «Поставщики» (оборот по СП-172) остаётся на месте и не
трогается: ломать работающее ТЗ запрещает (§1.2). Со временем она станет ссылкой
в новый раздел.

## Слои данных

ТЗ §4.1 требует шесть слоёв. Ложатся на существующее так:

| слой | где живёт | почему там |
|---|---|---|
| **1. Source/raw** | Bitrix (СП-166, СП-172, сделки, активности, вложения), таможня, витрины продавцов | не копируем, ссылаемся по стабильному ID |
| **2. Staging/extraction** | SQLite `base/kvant.db` + таблицы `lib_files`/`lib_demand` | здесь уже живёт разбор; **уничтожающий контур, ничего ценного не класть** |
| **3. Canonical/master** | новые таблицы `sup_*` в Supabase, рядом с `lib_*` | контур библиотеки — upsert, не уничтожает |
| **4. Human overrides** | `sup_overrides` — таблица-спутник по образцу `lib_row_junk` | образец проверен: пометка снимается одной командой, `run_id` обязателен |
| **5. Derived/analytics** | материализованные представления `sup_kpi_*` | во всей схеме сейчас нет ни одного mat. view — это первый |
| **6. Presentation** | `/api/suppliers/*` + `/suppliers` | своей истины не содержит |

**Жёсткое правило слоёв.** Импортированное значение и подтверждённая
корректировка хранятся раздельно. Эффективное значение даёт представление
`sup_effective_*`: `coalesce(override.value, imported.value)`, и исходное
остаётся читаемым. Следующий импорт корректировку не трогает; при противоречии
пишет строку в `sup_review`.

## Где держать данные: только за входом

Решение владельца: **в git — ничего, данные только в KV/Supabase.**

Следствия, обязательные к исполнению:

- В репозиторий идут код, DDL, обезличенные фикстуры и документация.
- Ни один набор `sup_*` не выгружается в `data/`, `public/` или каталог данных.
- Фикстуры в тестах — придуманные (правило 18 `CLAUDE.md`), не копии из базы.
- В журнал прогона — только агрегаты (правило 17).
- Гейт получает шаблон на ключи Supabase: сейчас `gate.yml:168` не знает ни
  `sb_publishable_`, ни `sb_secret_`.

## Личность поставщика: вечный бессмысленный ключ

Регламент `pnw/НУМЕРАЦИЯ.md` распространяется на поставщиков без изменений —
он уже обоснован нашими же случаями и проверен тремя пересборками.

```
KV-S-NNNNNN-C      юрлицо поставщика
KV-G-NNNNNN-C      корпоративная группа
```

Префикс `S`/`G` отличает род, шесть цифр подряд, контрольная цифра Луна.
Номер не содержит ни страны, ни имени, ни домена — **всё, что может измениться,
живёт в атрибутах**. Ребрендинг Atlas Copco → Epiroc уже показал, чего стоит
осмысленный ключ.

Номера-спутники поставщика, по образцу спутников детали:

| тип | что | пример |
|---|---|---|
| `bitrix` | `companyId` портала | 9634 |
| `inn` | ИНН / регистрационный номер | |
| `vat` | налоговый номер | |
| `domain` | домен сайта и почты | |
| `legal` | полное юридическое наименование | |
| `trading` | торговое наименование | |
| `alias` | встреченное написание | «ABC Germany» |
| `reestr` | ключ в одном из шести существующих реестров | `lib_suppliers.name_key`, слаг `pnw`, `seller_key` |

Слияние написаний — только через `alias` со ссылкой на доказательство; при
сомнении заводится кандидат, а не слияние. Слияние обратимо контролируемым
разделением, source ID не уничтожаются.

**Это снимает найденное противоречие:** сегодня `pnw/data/supplier_master.json`
ключуется слагом от сайта, а `lib_suppliers` — `norm(имя)`, то есть ровно
осмысленным ключом, от которого регламент отговаривает.

## Модель доказательства: обобщение метода ЛУКОЙЛ

Шесть состояний ТЗ §5.3 и выработанные на заявке разряды — одно и то же, записанное
в разных словах. Сводим:

| состояние ТЗ | что это у нас | пример из ЛУКОЙЛ |
|---|---|---|
| Verified | подтверждено документом, Bitrix, СП-172 | заказ размещён |
| Supplier stated | заявлено поставщиком | заявленный изготовитель в КП |
| Inferred | выведено системой | `кластер` — родовой адрес (775 строк) |
| Candidate | требует проверки | кандидат на слияние поставщиков |
| Rejected | проверено и отклонено | `pn_not_found` (782) |
| Superseded | заменено новой версией | проверка 08.2026, перекрытая 09.2026 |

Три оси наличия из метода переносятся в модель **как три отдельных поля, а не
одно**: `verdict`, `stock_grade`, `covers_qty`. Складывать их запрещено.
Именно на этом прежний расчёт дал 1 212 346 USD вместо 144 445.

**Дефект, который надо устранить при переносе:** `library/load_parts.py:160-171`
теряет `covers_qty` при загрузке в `lib_part_suppliers`, а в схеме нет колонки
даты проверки (`library/supabase/schema.sql:341-362` — только `created_at`).
Без этих двух полей строка не может участвовать в деньгах.

## Права: постепенно, финансы закрыты

Решение владельца: список, котировки и цены — всем, кто входит; финансы,
договоры, контакты и реквизиты — отдельным правом, по умолчанию ни у кого.

Реализуется расширением существующей модели, без второй системы прав:

```js
// access/acl.js — добавляются права раздела, не новая механика
{ id: "suppliers",      name: "Поставщики: список, котировки, цены" },
{ id: "suppliers_fin",  name: "Поставщики: договоры, условия, платежи" },
{ id: "suppliers_pii",  name: "Поставщики: контакты" },
{ id: "suppliers_edit", name: "Поставщики: корректировки и слияния" },
```

Проверка — серверная, по образцу `cutDashboard`: массив данных, который читает
только закрытая секция, вырезается из ответа до отдачи. Поле «Нет доступа» не
раскрывается через API, экспорт, HTML, кэш, логи и текст ошибки.

`suppliers_fin` и `suppliers_pii` по умолчанию не входят ни в одну роль, включая
`employee`, — это исправляет положение, при котором роли по умолчанию в коде дают
всё всем (`access/acl.js:73-91`).

Скоуп по нашему юрлицу закладывается колонкой `our_entity_id` во все таблицы
условий, заказов и платежей **сразу**, хотя список юрлиц ещё не готов
(решение владельца). Переделывать потом дороже.

## Отказ от альтернатив

| отвергнуто | почему |
|---|---|
| отдельный проект Cloudflare Pages | восьмая копия прав и секретов; `/library` доказал, что раздел портала работает |
| хранить мастер в SQLite `base/` | контур уничтожающий: `DROP TABLE` на каждом прогоне (`base/export_kb.py:141`) |
| единый AI-скор поставщика | ТЗ §1.9; и у нас уже есть обратный пример — три оси наличия вместо одного «на складе» |
| чинить `supplier_stats` на месте | таблица пересоздаётся `DROP TABLE` (`base/suppliers.py:45`); она витрина, а не мастер |
| писать данные в git, как сейчас | решение владельца 20.09.2026 |
| свести шесть реестров слиянием имён | именно это и даёт ошибку; сведение — только через `alias` с доказательством |
